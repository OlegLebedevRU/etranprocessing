## Почему короткий прогон проверяет прежнюю TTL-проблему

В проверенном исходнике TTL считается от `renewed_at`, а не постоянно
от первого `started_at`. Успешный renew активного сеанса обновляет
`renewed_at` и Redis TTL сеанса/маршрута. Истёкший либо чужой сеанс
получает 404; renew не оживляет закрытую сессию. MenuBuilder вызывает
renew после подтверждённого keepalive и совпадения текущего stream epoch.
Эта часть действует циклически, без отдельной ветви на 120-й минуте.

Текущий black-box прогон из исторического отчёта 17F:
13:01:30–13:11:47 UTC 2026-09-27, `player.currentTime=602`, 7332 кадра,
растущие RTP/bytes, `fresh_rtp=true`, `unrouted_packets=0`; затем штатный
stop и повторный start/stop. Он пересёк прежний TTL 600 секунд.
Новая сборка C tests дополнительно проверила renew до истечения TTL,
отказ после него и несовпадение SN. Это проверка механики, не новый
двухчасовой soak и не доказательство неограниченного uptime.

Исторический 120-минутный прогон: terminal 1000003, session 462,
2026-09-26 18:01:26–20:06:18 UTC, **7492 секунды (2:04:52)**.
Перед stop: fresh RTP, idle 0, route present, unrouted 0; пользователь
подтвердил живое видео без задержки и штатный stop. Route/transport
освобождены. Повтор session 465 длился 61 секунду; usage вырос на 61,
без повторного учёта длинной сессии. Источник — опубликованный журнал
конвергенции, экспортируемый контроллером в конечный data-only пакет.
Этот факт подтверждает медиатракт; окончательное списание всего дневного
usage в том наблюдении не проверялось.
