# L4Desk — план публичного лендинга

**Статус:** редакционный бриф для проектирования страницы, не утверждённый текст публикации.  
**Дата сводки:** 2026-09-30.  
**Предмет:** ценность L4Desk для оператора, команды поддержки и разработчика интеграции.  
**Источники:** только перечисленные в конце документы и реализация L4MCP/мобильного видеоинтерфейса. Новых проверок production в рамках этой сводки не проводилось.

**Визуальное дополнение:** [скриншоты и динамические хуки](l4desk-landing-visual-addendum.md) — адресная браузерная проверка тестового устройства 1000009 и варианты подачи для первого экрана.

## 1. Замысел

**Центральная идея — «Парк отвечает».** Удалённое устройство должно быть доступно человеку через браузер, а его состояние и разрешённые действия — собственным программным системам и AI-агентам через инструменты интеграции. Лендинг продаёт сокращение пути от вопроса «что произошло?» до проверяемого результата.

Предлагаемый первый экран:

> **Ваш парк отвечает. Где бы вы ни были.**  
> Откройте устройство в браузере — в том числе на смартфоне. Проверьте состояние, посмотрите экран, запустите диагностику. Подключите своего AI-агента через L4MCP или API, чтобы получать ответы и действовать быстрее.

Основное действие — **«Запросить демо»**. Второе — **«Обсудить AI/API-интеграцию»**. Эти действия подходят ограниченному техническому выпуску: открытая регистрация и общая коммерческая активация в последнем изученном отчёте выключены.

```yaml
positioning:
  product: L4Desk
  hook: "Парк отвечает"
  promise: "Браузерный доступ к устройствам и управляемый путь к AI/API-интеграции"
  primary_cta: "Запросить демо"
  secondary_cta: "Обсудить AI/API-интеграцию"
  tone: [ясный, уверенный, конкретный]
  avoid: [вымышленные цифры экономии, ложные отзывы, неподтверждённый SLA]
```

## 2. Кому и зачем

| Посетитель | Его вопрос | Показываемая ценность |
| --- | --- | --- |
| Продуктолог распределённого толстого приложения | «Как встроить удалённую поддержку в мой продукт?» | Браузерный доступ для человека; задачи, события и вебхуки для своего приложения. Бизнес-правила могут оставаться у клиента. |
| Саппорт-инженер | «Почему конкретный терминал не работает?» | Состояние устройства, удалённая консоль, потоковый вывод команды, экран и адресная диагностика. |
| Инженер и DIY-автоматизатор | «Как связать событие устройства с действием?» | REST API, события, вебхуки; L4MCP как готовый набор инструментов для ряда терминальных задач. |
| DevOps распределённого парка | «Как видеть и обслуживать много удалённых узлов?» | Проверка присутствия и готовности, адресные действия, единый способ получить результат. Массовую оркестрацию показывать как пример интеграции через API, не как текущий инструмент L4MCP. |

Изображения контроллеров и камер допустимы в блоке API-интеграции. Установщик и браузерный удалённый десктоп в изученных материалах относятся прежде всего к Windows-компьютерам и терминалам. Не следует переносить эти функции на любую камеру или контроллер без отдельного контракта.

## 3. Доказуемые опоры продукта

### 3.1. Человек работает через браузер

Оператор выбирает устройство, проверяет состояние, открывает консоль или удалённый экран. Отдельное настольное приложение для **оператора** не требуется. Браузер можно открыть и на смартфоне; у страницы видеонаблюдения есть мобильная раскладка, выдвижной список устройств и адаптивные элементы управления. Удобство полного консольного ввода на телефоне требует отдельной UX-проверки перед более сильным обещанием.

На **управляемом Windows-устройстве** нативный комплект устанавливается. Слова «без клиента вообще» использовать нельзя. Корректная формулировка: **«Без отдельного клиента удалённого доступа на рабочем месте оператора»**.

### 3.2. Устройство подключается и поддерживается

Единый установщик `l4setup` разворачивает комплект утилит; предусмотрены PIN и сертификат устройства, проверка готовности и машиночитаемый итог установки. `l4con` выполняет адресную диагностику Windows с выводом и завершением задачи. `l4desk` обеспечивает удалённый экран и ввод, а `leo4proxy` создаёт защищённые соединения с серверным контуром. `l4sql` даёт локальные ограниченные запросы к БД терминального приложения; это пример возможной глубокой диагностики через консоль, но отдельного SQL-инструмента L4MCP в рассмотренной реализации нет.

Простая визуальная цепочка для страницы: **«Создать устройство → получить PIN → установить комплект → увидеть online → открыть консоль или экран»**. На публичной странице она должна выглядеть как пользовательский путь, без схемы внутренних сервисов.

### 3.3. L4MCP уже работает

L4MCP предоставляет проверку готовности **конкретного** терминала, запуск одной ограниченной консольной команды, сведения о сертификатах и операции с PIN, отчёты по платежам, балансам и инкассации. Каждый вызов разрешает пользователя через MenuBuilder; данные ограничиваются организацией пользователя. Консоль требует точный идентификатор устройства и предварительную проверку; запросы отчётов требуют конкретные устройства или ограниченный период. Операции, меняющие состояние, отделены от чтения. Для повторного выпуска PIN при действующем сертификате предусмотрено явное подтверждение человека.

Показывать L4MCP как **существующие инструменты для агентной работы с терминалами**. Он не является универсальным MCP-доступом ко всем функциям любых устройств. Пример обёртки IoT API в MCP из внешней документации — схема для интегратора, а не перечень инструментов действующего L4MCP.

### 3.4. API даёт второй путь к AI

LEO4 API описывает создание задач для устройств, чтение статуса доставки, событий и телеметрии, а также вебхуки для реакции на результаты. Его можно включить в собственный agent harness через function calling или MCP-обёртку. Возможный пользовательский сценарий: **«сигнал → анализ → разрешённое действие → отдельная проверка результата»**. API допускает программную работу с несколькими устройствами; пример массовой отправки команд в руководстве — образец клиентской интеграции, не готовая функция L4Desk UI или L4MCP.

Ключевой смысл для доверия: статус задачи `DONE` в описанном IoT-контракте подтверждает **доставку команды**, а физическое действие подтверждается отдельным событием устройства. Лендинг может сказать: **«Получайте не только статус отправки, но и событие, подтверждающее результат там, где устройство его предоставляет»**.

### 3.5. Две границы доверия

На границе **устройство ↔ сервер** используется сертификат устройства и взаимная TLS-аутентификация (`mTLS`) для описанных MQTT/HTTPS и медиасоединений. На границе **пользователь ↔ сервис** производственный контур MenuBuilder использует JWT с асимметричной подписью RSA (`RS256`) и проверкой токена. Для API-интегратора предусмотрены организационные API-ключи. Изоляция по организации и проверка конкретного устройства дополняют транспортную защиту.

Для публичного текста: **«Устройства подтверждают свою подлинность сертификатами; пользователи входят с токенами, подписанными RSA-ключом»**. Слово «сквозной» относится к защите *границы устройства и сервера*. Оно не означает, что весь путь от устройства до браузера зашифрован одним непрерывным mTLS-сеансом: браузерный тракт устроен отдельно.

```yaml
verified_capabilities:
  operator:
    - "Консоль и удалённый экран в браузере"
    - "Мобильная раскладка страницы видеонаблюдения"
  managed_windows_device:
    - "Единый установщик и проверка готовности"
    - "Сертификатное подключение и mTLS на границе с сервером"
    - "Удалённая консоль, экран и ввод"
  agent_integration:
    - "Действующий L4MCP с ограниченным набором терминальных инструментов"
    - "LEO4 REST API, события и вебхуки для собственной интеграции"
  user_authentication: "JWT RS256 в производственном контуре MenuBuilder"
  evidence_level: "код и документация; не новый production E2E этой задачи"
```

## 4. Сценарий страницы

1. **Первый экран — «Парк отвечает».** Крупный экран устройства, рядом телефон и короткий фрагмент ответа агента. Один ясный тезис, две кнопки.
2. **Проблема без драматизации.** «Устройство далеко. Сбой виден пользователю раньше, чем инженеру. Для ответа приходится переключаться между системами». Не придумывать время простоя или денежные потери.
3. **Одна ситуация, три способа действия.** Переключатель «Оператор / AI-агент / Моя система»: оператор открывает экран и консоль; агент вызывает доступные инструменты L4MCP; система получает событие и запускает разрешённый API-сценарий.
4. **Браузер там, где находится инженер.** Показать ноутбук и смартфон с настоящей структурой видеоинтерфейса. Плашки: «Браузер», «Экран устройства», «Консоль». Не имитировать проверенную поддержку жестов или виртуальной клавиатуры, пока не выполнен мобильный UX-тест.
5. **Путь подключения.** Пять пользовательских шагов от создания устройства до online и первого сеанса. Отдельно сказать, что установщик работает на управляемом Windows-устройстве.
6. **AI и API без магии.** Показать конкретный безопасный запрос к выбранному устройству и цикл задачи с событием результата. Разделить «работает в L4MCP» и «можно построить через API».
7. **Доверие.** Две границы: mTLS устройства и RS256 JWT пользователя; выбор устройства, ограничение доступа и проверяемый результат. Детальную криптографическую схему оставить для технической страницы.
8. **Сценарии по ролям.** Короткие карточки для продуктолога, поддержки, инженера/DIY и DevOps.
9. **Финальный призыв.** «Покажите свой парк и типовую проблему — разберём сценарий на демо». Форма: роль, тип устройств, количество устройств диапазоном, интерес к браузеру/MCP/API и способ связи. Не собирать пароли, PIN, ключи или адреса устройств.

## 5. Три маркетинговые обёртки

### A. «Парк не ждёт, пока вы вернётесь к ноутбуку»

**Образ:** инженер вне офиса открывает состояние терминала на смартфоне; рядом увеличенный фрагмент экрана устройства. **Плашки:** «Браузер на телефоне», «Экран устройства», «Консоль». **Текст:** «Увидели проблему — открыли устройство — начали разбираться». Подходит для блока о мобильном браузере. Не изображать мобильный ввод как уже доказанно удобный в каждом сценарии.

### B. «Спросите парк, что случилось»

**Образ:** разговор с агентом превращается в три карточки: выбранное устройство, проверка готовности, результат диагностики. **Плашки:** «Работающий L4MCP», «Точное устройство», «Результат команды». **Текст:** «Ваш агент получает инструменты для диагностики, а команда — ответ, с которого можно начать действовать». Рекомендуемый образ первого экрана.

### C. «От сигнала до подтверждения»

**Образ:** компактная временная линия «событие → решение → команда → событие результата». **Плашки:** «API и вебхуки», «mTLS для устройств», «RSA JWT для пользователей». **Текст:** «Знайте не только то, что команда отправлена. Узнайте, что произошло после неё». Подходит для технической и доверительной части страницы.

Комбинация: **B на первом экране, A в разделе браузерного доступа, C в разделе API и безопасности**. Это три главы одной истории, а не три несовместимых визуальных стиля.

## 8. Перед публикацией

1. Получить короткое мобильное видео и console UX-доказательство на распространённых размерах смартфонов. До него обещать доступ к браузеру и мобильную страницу видео, а не беспроблемную работу с клавиатурой в любой консоли.
2. Сверить текущие release flags и путь заявки. В последнем изученном отчёте общая коммерческая активация выключена.
3. Проверить формулировку «без выделенного IP» для поддерживаемой сетевой схемы. Документы показывают исходящие соединения к общим серверным endpoint, но не дают универсальной проверки каждой сети.
4. Для каждого изображения реального UI сохранить соответствие работающему интерфейсу; концептуальные экраны AI явно обозначать как иллюстрацию сценария.
