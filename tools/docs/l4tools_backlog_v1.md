ЭТАП 1. L4PIN: NTE_PERM И БЕЗОПАСНОСТЬ КЛЮЧЕЙ

Исследуй сбой создания машинного RSA-ключа: NCryptFinalizeKey возвращает 0x80090010 (NTE_PERM) для контейнера EtranTerminalKey. Установи по коду, где выбирается machine/user store, какие права нужны, как создаётся и переиспользуется контейнер, какие дескрипторы могут оставаться открытыми и что происходит при частично завершённой операции. Не объявляй причиной отсутствие повышения прав или «залипший» контейнер без подтверждения.

Улучши диагностику: операция, контекст хранилища, безопасный идентификатор контейнера, код ошибки и понятное действие для оператора. Разделяй локальную ошибку CNG и ошибку обращения к CA. Не утверждай, что PIN точно не израсходован, пока это не подтверждено контрактом и фактическим этапом обмена.

Не реализуй безусловное «при NTE_PERM удалить контейнер и повторить». Удаление допустимо лишь после проверки принадлежности ключа, отсутствия зависимости действующего сертификата от него и безопасного сценария восстановления. Не уничтожай рабочий ключ ради ретрая. Добавь тесты отказа в правах, повторного запуска, частичного создания ключа и сохранения действующего сертификата после ошибки.

ЭТАП 2. L4PIN: UI ПО УМОЛЧАНИЮ И CLI БЕЗ UI

Сделай запуск l4pin без CLI-параметров графическим. UI должен быть крупным и удобным для сенсорного экрана: читаемый список сертификатов, найденных по действующему условию поиска l4pin, с достаточными для выбора сведениями и сроками действия; поле ввода PIN; галочка «Удалить старые», включённая по умолчанию; галочка «Force», соответствующая действующему смыслу CLI --force; понятные состояния выполнения и результат. После успешной установки обнови список и покажи новый сертификат. PIN маскируй и не сохраняй в логах.

Правило запуска замены:
- Если обе галочки выключены и среди найденных сертификатов есть хотя бы один со сроком действия более 30 дней, новый сертификат не устанавливать; показать причину.
- Во всех остальных случаях при валидном PIN выполнить замену: удалить относящиеся к этой операции старые сертификаты и установить новый.
- Не трактовать «валидный PIN» как достаточную гарантию готовности нового сертификата: сначала получить и проверить новый сертификат и связь с ключом, затем безопасно переключить использование и удалить только сертификаты/ключи, подпадающие под точное условие поиска. При отказе сохранять работоспособный старый сертификат либо выполнять доказуемое восстановление.

Обрати внимание на необычную семантику флажка: по сформулированному правилу выключенная галочка «Удалить старые» сама по себе не запрещает удаление при разрешённой замене. Сделай последствия явными в UI до подтверждения; если безопасную и непротиворечивую трактовку реализовать нельзя, остановись и запроси решение владельца, а не меняй правило молча.

По умолчанию для работы с Machine-хранилищем запрашивай UAC-повышение сразу, с понятной обработкой отказа. Проверь совместимость способа повышения с CLI и --store user: не ломай автоматизированный запуск и не требуй повышения для user-сценария без технической необходимости. Сохрани документированный способ запуска полностью без UI с действующими CLI-опциями и корректными кодами возврата. Протестируй матрицу обеих галочек, сроков более/менее/ровно 30 дней, отсутствие сертификатов, ошибки PIN/CA/CNG, отказ UAC, machine/user store и без-UI режим.

ЭТАП 3. L4SETUP: РЕВИЗИЯ MOSQUITTO И ЗАПУСКА СЛУЖБ

Сначала, без правок, восстанови точную последовательность install, upgrade, repair и verify. Изучи как минимум engine.c, services.c/services.h, unpack.c в tools/l4setup, подготовку каталогов и конфигурации в tools/l4superv, способ регистрации Mosquitto, фактический ImagePath и log_dest file. Составь таблицу: фаза, действие, предпосылки, возможный отказ, текущая обработка. Установи, существуют ли к моменту создания log-каталога <dest>, <dest>\mosquitto, payload, итоговый mosquitto.conf и MOSQUITTO_DIR. Проверь реальный порядок старта Leo4Proxy, Mosquitto, L4Con, L4Superv и прочих служб, не полагаясь на описанную предполагаемую последовательность.

Если подтверждён риск с <dest>\mosquitto\log, обеспечь идемпотентную подготовку полной цепочки каталогов после распаковки payload и до запуска Mosquitto, в том числе для install/upgrade/repair и при необходимости перед повторным стартом. Отличай существующий каталог от файла на его месте; ACL применяй после создания, проверяй результат Win32 API, возвращай ошибку вызывающему коду и сообщай путь и код. Дай служебной учётной записи необходимый доступ к конфигу и логу; не добавляй Everyone:(F) без доказанной необходимости. Не создавай второй источник истины для mosquitto.conf: согласуй порядок и путь с l4superv.

В ожидании старта службы SERVICE_RUNNING означает успех; SERVICE_STOPPED после StartServiceW — немедленный неуспех даже при нулевых SCM exit codes. Для ошибки показывай имя, elapsed time, dwCurrentState, dwWin32ExitCode, dwServiceSpecificExitCode, PID при наличии, checkpoint и wait hint при необходимости. SERVICE_START_PENDING ожидай без busy-wait и только в пределах ограниченного timeout. Уже работающую службу не перезапускай. Проверь также логику остановки, меняя её только при подтверждённом дефекте. Не запускай следующие зависимые службы как будто предыдущая успешно работает.

Проверь дополнительные возможные причины отказа: готовность Leo4Proxy и автономность старта Mosquitto при временно недоступном bridge; наличие, кодировку и путь конфига; занятие 127.0.0.1:1883; регистрацию службы и запуск старого/внешнего exe; момент записи MOSQUITTO_DIR в Machine environment и окружение, видимое процессу через SCM; подтверждённые гонки с l4superv/recovery. Не вводи сетевое ожидание или глобальный mutex без доказанной необходимости. При отказе сохраняй первичную ошибку в диагностике.

Добавь изолированные тесты для отсутствующего родителя log-каталога, повторной подготовки, файла вместо ожидаемого каталога, ошибок создания/ACL и всех состояний службы: RUNNING, STOPPED с нулевыми/ненулевыми кодами, START_PENDING с ограничением времени, already running. Если SCM нельзя честно замокать, выдели чистую функцию решения по SERVICE_STATUS_PROCESS; не выдавай её unit-тест за проверку реального SCM.

ЭТАП 4. L4SETUP: БЛОКИРОВКА КАТАЛОГА L4PIN ПРИ ОБНОВЛЕНИИ

Разбери отказ обновления с Win32 error 32 (ERROR_SHARING_VIOLATION) при переносе действующего каталога <dest>\l4pin в rollback-каталог. По журналу отказ происходил в Phase 4: Update и повторялся после восстановления предыдущей версии. Проверь текущие unpack.c, drainage.c, сценарий install_cert.cmd, предпроверку занятых файлов и порядок файловой подмены. Подтверди по коду и на изолированном стенде, какие процессы и дескрипторы реально мешают операции: работающий l4pin.exe, открытый файл либо текущая директория cmd/PowerShell или другого процесса внутри l4pin. Error 32 подтверждает конфликт доступа, но сам по себе не устанавливает конкретного владельца блокировки.

Предпроверка только перечисленных .exe не должна считаться доказательством возможности переименовать каталог. Предусмотри раннюю диагностику занятого каталога и понятное сообщение с путём и действием для оператора. Если используешь пробное открытие каталога с правом DELETE, сначала проверь применимость метода на поддерживаемых Windows; успешная проба не устраняет гонку между проверкой и MoveFileExW. Фактический результат перемещения остаётся решающим.

При обнаруженной блокировке не начинай или безопасно приостанови файловую подмену; сохрани целостность уже работающей версии, конфигурации и rollback-состояния. Предложи закрыть использующие каталог программы и повторить операцию с ограниченным числом попыток. Не завершай все процессы с именем l4pin.exe или cmd.exe автоматически: действующая выдача сертификата может быть в критической фазе. Возможное штатное завершение принадлежащего именно этой установке процесса реализуй только после проверки происхождения процесса, его состояния и безопасного завершения операции; иначе запроси действия пользователя. Не выполняй Stop-Process -Force как автоматическое средство восстановления.

Проверь install_cert.cmd: интерактивный pause не должен оставлять автоматизированный сценарий бессрочно запущенным с CWD внутри заменяемого каталога. Раздели интерактивный и unattended режимы без потери диагностики; перед выходом освобождай зависимость от каталога установки. Учитывай также текущий и будущий графический режим l4pin из этапа 2.

Предупреждение PendingFileRenameOperations показывай как дополнительный сигнал о возможной необходимости перезагрузки, а не как доказательство причины error 32. Перезагрузка может снять дескрипторы текущих процессов, но не гарантирует исправления первопричины или очистки всей очереди; не выполняй её автоматически.

Добавь регрессионные тесты: открытая консоль с CWD внутри l4pin при свободном l4pin.exe; работающий l4pin; открытый файл в каталоге; отсутствие блокировки; повторная попытка после освобождения каталога; отказ на промежуточном шаге подмены и восстановление; повторный запуск после прерывания. Проверяй исходный и целевой каталоги и содержимое rollback до и после ошибки. Выполняй сценарии только на временном тестовом дереве; в отчёте отделяй подтверждённую причину конкретного сбоя от других возможных источников error 32.

Предоставь:
