# Реализация подписок L4Desk и понятного финансового интерфейса

Дата: 2026-10-03. Статус: реализовано по стекам и выпущено в production, ревизия 8bb0359, schema029, YooKassa OFF. [Релиз](../.agent-context/tasks/completed/2026-10-03-l4desk-terminal-subscriptions-release.md), [реализация и проверки](../.agent-context/tasks/completed/2026-10-03-l4desk-terminal-subscriptions-handoff.md). Правила и переход: [документ реализации](../docs/menu_bill-terminal-subscription.md).

Исходный документ: `D:/repo/platerra/Public/etranprocessing/plans/menu_bill-terminal-subscription-plan.md`, вариант A, ревизия 2. Дополнения пользователя имеют приоритет. Каскад L4D принимается завершённым для совместимых технических механизмов; повторное прохождение всего каскада не является условием этой переработки. Исторические production-флаги не определяют целевое поведение.

## Основное решение

Пользователь покупает срок работы конкретного терминала. Денежного баланса, почасовой оплаты, финансовой квоты, месячного начисления по online и tenant-wide grace больше нет. Первый неудалённый терминал бесплатен без ограничения времени. Остальные доступны по подписке и трёхдневному льготному периоду после её окончания.

Управление сессиями и измерение их длительности остаются самостоятельным техническим ядром. Время используется для статистики владельца, не для цены, задолженности или решения о доступе.

`YOOKASSA_ENABLED` — единственный переключатель коммерческой доступности. Его включение открывает покупку подписок и использование оплаченных дополнительных терминалов автоматически, без второго billing/enforcement-флага. Само включение не выдаёт подписку, не списывает деньги и не создаёт рекуррентные платежи.

## Уточнения исходного плана

| Пункт | Предложение и причина |
|---|---|
| Раздел 0 говорит о session-only блокировке, разделы 1 и 3 требуют транспортную | Принимаем два уровня: admission/stop и MQTT/RTP policy; устраняем противоречие в тексте |
| Использование `Terminal.is_active` для подписки | Оставляем поле административным выключателем. Подписка добавляет отдельное вычисляемое ограничение transport policy. Тогда оплата не может отменить отключение администратором |
| Новый persisted transport flag | Не нужен при вычисляемой policy: не храним вторую копию состояния и не возвращаем `is_active=True` из payment worker |
| ADD-миграция четырёх колонок | Рекомендуем один nullable `paid_until` в L4DeskTerminal. Назначение заказа — существующий audit JSON; старые модели сохраняем. Ни новых таблиц, ни drop, ни конвертации балансов |
| Модель якобы определяется в MenuBuilder | Меняем declarative ORM в shared; MenuBuilder re-export не содержит отдельной модели |
| Заморозка metering целиком | Сохраняем duration/cursor/epoch/waiver и дневную статистику; удаляем денежный расчёт и posting из активного пути |
| `stop_outbox` без изменений | Сохраняем механизм, но выбираем сессии конкретного terminal, проверяем актуальность причины при retry |
| `l4desk_billing_enabled` включает оплату независимо | Убираем из решения о доступности покупок; backend и UI получают одинаковое вычисленное состояние YooKassa |
| Скрыть кнопки при отключённых оплатах | Показываем объяснение и недоступное действие «Оплата пока недоступна», чтобы пользователь понимал причину |
| Старые уведомления переориентировать без изменения схемы | Таблица имеет обязательный cycle FK и ограниченный набор типов. Замораживаем старую доставку, не создаём фиктивные циклы ради писем |
| Manual payments со storno без ledger | Старая таблица требует ledger transaction. Не переиспользуем её для бесплатной административной выдачи месяцев; выдача и коррекция — отдельные audit-операции |

Изменение транспортной policy ProcessingBackend расширяет исходное «только миграция» осознанно: небольшая проверка устраняет необходимость менять все административные writers `is_active` и хранить конфликтующее состояние. Native-клиент не меняем, используем существующий ответ policy и `terminal_inactive`; задержка применения клиентом остаётся задержкой поллинга, мгновенность обещаем только для server admission.

## Правила доступа и покупки

Порядок проверки: ownership/permissions → административное состояние и удаление → бесплатная льгота → коммерческая доступность → срок подписки. Бесплатная льгота не отменяет административную блокировку.

| Состояние | Сессии и транспорт | Что видит пользователь |
|---|---|---|
| Бесплатный терминал | Разрешены при технической готовности | «Бесплатно, без ограничения времени» |
| Дополнительный, YooKassa выключена | Запрещены, даже если сохранён будущий срок | «Платные подключения пока недоступны»; сохранённый срок показываем отдельно |
| Дополнительный, YooKassa включена, `paid_until=NULL` | Запрещены; grace нет | «Требуется подписка» → «Подключить» |
| `now < paid_until` | Разрешены | «Оплачен до …» → «Продлить» |
| `paid_until <= now < grace_until` | Разрешены | «Продлите до …, чтобы сохранить доступ» → «Продлить» |
| `now >= grace_until` | Новые запрещены, текущие адресно останавливаются | «Подписка закончилась» → «Восстановить доступ» |
| Администратор отключил терминал | Запрещены независимо от срока | «Отключён администратором»; оплату не предлагаем как способ разблокировки |

Не сохраняем enum состояния: он вычисляется из даты, бесплатной льготы и gates. Отключение YooKassa закрывает новые покупки и платный доступ, но не стирает оплаченные даты. Уже созданные платежи сверяем и применяем при подтверждённом успехе даже после выключения покупок; иначе деньги будут получены без выдачи права. Выданное право остаётся временно недоступным до включения коммерции. Для новых покупателей не обещаем остановку хода срока при выключении шлюза; длительные отключения требуют явной административной компенсации, а не скрытого продления.

Без доступной активной платной подписки разрешены максимум три неудалённых терминала. Grace не считается активной подпиской для расширения лимита. При выключенной YooKassa действует лимит три. Если уже создано больше, лишние записи не удаляем; запрещаем дальнейшее создание до выполнения условия. Удалённые не считаются. Проверка и создание сериализуются по tenant, чтобы одновременные запросы не обошли лимит.

Вторичные создаются с полной provisioning/PIN saga, но с запретом сессий и MQTT/RTP по policy. `is_active` сохраняет административную семантику. Перенос бесплатной льготы при удалении первого вычисляется по ordinal, не копирует даты и не требует финансового начисления. Для нового free-terminal снимается именно подписочное ограничение; административное остаётся.

Продление: `base=max(provider_succeeded_at, current_paid_until)`, затем календарное прибавление выбранных 1/3/6/12 месяцев. Используем один стабильный UTC момент подтверждённого успеха provider, не время повторного webhook. Прибавляем пакет M сразу, с нормализацией последнего дня месяца; результат сохраняем в UTC, показываем в timezone tenant. Grace — три календарных дня в согласованной timezone. Изменение timezone не должно неожиданно сокращать действующий grace: сохраняем необходимый timezone snapshot в audit операции и используем его для этого продления.

Продление в grace начинается от успешной оплаты, если старый срок уже прошёл: оставшиеся льготные дни не вычитаются из покупки. Никогда не оплачиваем сутки online или часы сеанса.

## Хранение и минимум изменений схемы

В текущей L4DeskTerminal нет подходящего срока подписки или универсального JSON. Ни `last_online_at`, ни PIN/certificate поля, ни лицензии другого продукта не подходят. Дата подписки в audit как единственный источник потребует поиска последней версии, восстановления состояния и дополнительных механизмов синхронизации. Это экономит миграцию, но противоречит цели простого кода.

**Рекомендация: одна маленькая ADD-миграция `paid_until TIMESTAMPTZ NULL`.** Это предлагаемый компромисс с пожеланием избегать миграций, а не уже согласованное изменение. Все текущие значения NULL; схемы старых таблиц не меняются. При строгом запрете любых миграций альтернативой будет audit-backed состояние за repository adapter, с tenant lock для всех операций и пакетным чтением snapshot. Этот вариант следует выбирать явно; не маскировать дату в поле другой сущности.

Уточнение пользователя: миграции допустимы только по обоснованным причинам. Для предлагаемой колонки обоснование такое: дата — основной durable атрибут права конкретного терминала; она нужна payment application, admission и transport policy; существующего подходящего атрибута нет. Прямое чтение даты проще и надёжнее восстановления состояния из событий. Колонка nullable и additive, не требует переписывать старую историю. На этапе реализации подтвердить необходимость индексирования измерением запросов, а не добавлять индексы заранее. Любые дополнительные колонки/таблицы должны получить отдельное обоснование; пакет ADD из исходного плана автоматически не переносится.

Переиспользуем:

- `FinPayment`: сумма, provider identity, operation id, статус, confirmation URL, verified/succeeded timestamps. `ledger_transaction_id` для новых подписок NULL, старые записи неизменны.
- `L4DeskAuditEvent.details`: версионированный snapshot заказа — назначение, items, месяцы, цена, сумма, timezone, hash; событие применения — old/new paid_until каждого item и payment id. `receipt_snapshot` остаётся снимком чека, не превращается в контейнер состояния подписки.
- `L4DeskRemoteSession`: состояние, provider epoch, cursor и завершение.
- `FinUsageDaily`: длительности без денег, как adapter к существующей схеме.

Операцию заказа и pending FinPayment сохраняем атомарно до обращения к provider. Unique `(tenant_id, operation_id)` FinPayment остаётся ключом заказа. Проверка повторного запроса сравнивает весь snapshot, не только сумму. Событие применения и все новые сроки фиксируются в одной транзакции со статусом payment; аудит не становится самостоятельной второй таблицей подписок.

Старые платежи считаются тестовыми по исходному плану: никаких grants из старого баланса и top-up. Всё равно отличаем subscription order по назначению/версии audit, чтобы поздний старый webhook не выдал новые права. Для существующих дополнительных терминалов NULL означает неоплаченную подписку; массовой выдачи права из истории нет.

## UI для обычного пользователя

Основной экран называется «Подписки», статистика — «Использование». Не показываем бухгалтерские термины «entitlement», «ledger», «anchor» и «grace» в пользовательском тексте.

Вверху «Подписок» — короткое объяснение: «Один терминал бесплатно. Каждый дополнительный — X ₽ в месяц. Время использования не влияет на стоимость». Ни баланса, ни задолженности, ни индикатора минут бесплатной работы.

Когда YooKassa выключена: «Сейчас доступен один бесплатный терминал. Ещё два можно подготовить, но подключить их получится после запуска оплаты». Цена может показываться как текущая цена подключения; покупка недоступна с понятной причиной. Не показываем ложное действие «Пополнить баланс».

Когда YooKassa включена: сводка «1 бесплатный · 2 оплачены · 1 требует продления». Первым показываем самое срочное действие, например «Продлите “Касса 2” до 8 октября, чтобы сохранить доступ». Объясняем отсутствие автосписания: продление выполняет пользователь.

Список терминалов содержит название, понятный статус, точную дату окончания/отключения, цену и одно основное действие. «Не в сети», «Настройка не завершена» и «Отключён администратором» идут отдельными техническими признаками, не изображаются как финансовая задолженность. Состояние «Платёж проверяется» отличается от «Оплачен». Возврат со страницы оплаты не считается подтверждением.

Корзина: выбранные терминалы, пакет 1/3/6/12 месяцев, цена каждой позиции, общая сумма, прогноз нового срока и одна кнопка «Оплатить N ₽». Free-terminal не продаём. Изменившиеся данные пересчитываем перед оплатой; server quote задаёт цену и назначение. Удалённый или ставший free терминал не теряем при уже успешной оплате: заранее фиксируем правила разрешения таких случаев и показываем требующее внимания состояние заказа.

История показывает «Продление терминалов», сумму, дату, результат и позиции. Старые тестовые top-up не смешиваются с новой историей подписок. Ошибка оплаты предлагает понятное повторное действие; timeout создания предлагает проверить тот же заказ, а не создать второй.

«Использование»: период, терминалы, время видео, время консоли и сумма длительностей, график по дням. Показываем качество данных/неподтверждённые интервалы при наличии. Время сессий — показатель использования, не фактические CPU, трафик или стоимость. Для общей длительности параллельных ресурсов поясняем способ суммирования, не обещаем уникальное настенное время.

API отдаёт status, reason, available_action, purchase availability, даты и цену. UI не восстанавливает финансовую политику самостоятельно по роли или набору env-флагов. Ошибка загрузки не превращается в «бесплатно» или нулевую сумму.

## Учёт времени без денег

Из `remote_session_metering` меняем только зависимость от финансового обработчика: новый duration service принимает подтверждённый интервал и обновляет дневные секунды. Сохраняем границы суток, timezone, session cursor, атомарность обновления и защиту от повторов. Сохраняем provider epoch и waiver недоказанного хвоста. Оплата никогда не вызывается из heartbeat, close, reconnect или online.

Без изменения схемы новые строки FinUsageDaily заполняем так: `source=video+console`, `free_seconds=source`, `billable_seconds=0`, денежные поля и rounded hours = 0, ledger/posting = NULL. `free_seconds` здесь только adapter для старого CHECK, в новых DTO это поле не публикуем. Обязательный tariff FK заполняем существующим/техническим snapshot без обращения к актуальному тарифу при каждом checkpoint. Присутствие FK не делает статистику платной.

Старые строки с финансовыми значениями не обнуляем. Для текущих суток на переключении обновляем только duration, сохраняя старые денежные snapshot, без новых денежных delta. Новый period marker фиксируем audit-событием запуска; денежные поля не попадают в новую статистику. Проверяем сценарий смешанного дня отдельным тестом.

Старый `metering_close_worker` публикует деньги, поэтому его удаляем из startup и активного package API. Финансовое закрытие суток для новой статистики не нужно. Технический reconcile/close сессий и stop engine сохраняем. Не добавляем периодических проверок денег в hot path и не удаляем существующие технические locks под предлогом отсутствия тарификации.

## Шаги по стекам и порядок интеграции

### 1. Контракты и сценарии

Владелец — MenuBuilder. Зафиксировать приведённые правила, API summary/quote/order/payment/status/usage, даты и ошибки. L4D session/lease/video/MQTT контракты оставляем базой. Решить удаление/free-transfer терминала с pending payment: рекомендуется запрет удаления и переноса льготы затрагивающим заказ терминалам до сверки заказа; неопределённый timeout сверяем, не снимаем блокировку только по локальному таймеру.

Предусмотреть bounded reconciliation pending orders через тот же payment worker; provider cancellation/success обрабатывается прежде освобождения ограничения. Проверить многопозиционный заказ и удаление первого free-terminal, которое меняет роль оплачиваемого второго. После успеха хранить оплаченные даты даже если terminal впоследствии стал free; льгота не выдаёт возврат автоматически.

### 2. Shared и ProcessingBackend schema

При принятии рекомендованного хранения — одна ADD-миграция paid_until, ORM и schema compatibility revision. Никакого billing business logic в shared DB package. Проверить два backend consumer, backward-compatible чтение и NULL. Не создавать transport/meta колонки и дополнительные fin-модели. Модели старых циклов/балансов остаются декларативными и помеченными историческими.

### 3. MenuBuilder backend техническое ядро

Сначала выделить duration service и проверить сохранность metering. Отключить вызов `process_device_online_monthly_charge` в consumer; online остаётся техническим фактом для presence/readiness. Убрать `pending_finance` обработку начислений из активного consumer, корректно завершать старый backlog техническим результатом без списаний. Checkpoint/quarantine/replay не удалять.

### 4. MenuBuilder backend подписки

Сделать компактный `subscriptions` service/repository/DTO: free resolution, terminal status, purchase capabilities, quote и extension. Удалить balance/quota/cycle из новой policy. Применять одинаковую policy к video/console/input/новым console commands, не разрушая protocol command-aware stop.

Установить tenant lock для onboarding/delete/payment application, затем payment/terminal locks в стабильном порядке; сетевые запросы выполнять вне этих коротких транзакций. Лимит и ordinal выделять внутри одной локальной транзакции. Не проектировать новую распределённую lock-систему.

### 5. ProcessingBackend transport policy

Сохранить административное `Terminal.is_active`, существующее mTLS распознавание и служебный HTTPS. Для L4Desk terminal policy добавляет вычисляемый subscription allowance; `mqtt_rtp_allowed = administrative_active AND subscription_allowed`. Старые terminal без L4Desk принадлежности продолжают прежнее поведение.

Проверять принадлежность L4Desk по надёжному серверному критерию профиля/организации, не по browser role и не просто наличию session-generated L4DeskTerminal: технические сеансы Classic также могут создавать такие записи. Критерий scope одинаков для MenuBuilder и ProcessingBackend и не должен включать Classic по ошибке.

Одинаковые small test vectors для двух backend: free, unpaid, active, grace boundary, provider disabled, deleted, admin-disabled. Production setting YooKassa должен согласованно попадать в оба consumer: один release/config source, startup validation, без независимого коммерческого тумблера. Поллинг proxy обеспечивает eventual применение; новые server sessions блокируются сразу.

### 6. YooKassa и заказы

Переиспользовать HTTP client и существующие safeguards, убрать top-up/ledger/anchor. Backend сам считает стоимость и назначение. Provider metadata содержит идентификатор/версию заказа, не является единственным хранилищем корзины. До применения сверяем provider success, identity, currency, сумму и локальный snapshot.

Атомарно применяем все items ровно один раз через locked FinPayment + persisted applied event + paid_until. Webhook/poll/retry пользуются одной функцией, не дублируют extension. После commit обновлённые права сразу видны admission/policy, отдельная auto-activation `is_active` не нужна. Worker нужен для старых сессий и сверки pending, не для превращения успешной оплаты в доступ.

При enabled=true и неправильной конфигурации provider deployment/startup сообщает ошибку; UI/API не обещают доступную покупку. При кратковременной network error уже оплаченные подписки остаются доступными: network health не является entitlement. Исправить old receipt description «Пополнение баланса» и receipt snapshot под подписку; проверить состав позиций до live включения.

### 7. Stop worker и административные действия

Один subscription worker: выбор expired/disabled дополнительных терминалов → адресный stop engine → retries/reconciliation. Перед stop повторно проверять актуальную подписку и provider epoch. Retry по старому состоянию после продления не гасит новую сессию. Не останавливать free или соседние paid terminals из-за одного истёкшего.

Audit admin grant/correction с actor, operation id, причиной и old/new dates. Пока YooKassa выключена, административная выдача срока не обходит запрет платных возможностей. Это не регистрация оплаты и не банковский документ. Автоматическое «вычесть месяцы по storno» не переносим: оно может уничтожить последующие покупки. Коррекция учитывает исходную операцию и текущее право; реальный refund — отдельный подтверждённый provider flow, не изменение даты по кнопке.

Напоминания в UI обязательны для v1. Email 7/3/1 — отдельный последующий шаг с подходящей существующей общей delivery/outbox инфраструктурой после её аудита. Старую cycle-bound FinNotificationDelivery не используем через поддельные циклы. Так не увеличиваем обязательную миграцию ради уведомлений, которые не нужны для доступности подписок.

### 8. MenuBuilder frontend

Реализовать отдельные subscription DTO/API client, страницу «Подписки», статусы в списке и карточке терминала, корзину и payment return/poll, затем «Использование». В Settings onboarding объяснять лимит до создания. В console/video/input показывать server reason и ссылку на нужное действие. AdminHub перевести на терминальные подписки и duration, старую бухгалтерию убрать из основной навигации.

UX сначала проверить на состояниях отключённой YooKassa, отсутствии терминалов, admin-disabled, pending/error платежах и нескольких разных сроках. Mobile: одно основное действие, даты полностью читаемы, статус понятен без цвета. Не копировать Classic billing API и mock checkout.

### 9. Уборка и завершение

Удалять старые вызовы и startup wiring в том же изменении, которое заменяет функцию. Маркер FROZEN без отключения call path недостаточен. Удалить неиспользуемые сервисы/API/DTO/flags/tests, если они больше не нужны историческому чтению; сохранить минимальное admin-only чтение истории при необходимости. Таблицы и ORM не удалять, старые данные не перезаписывать.

Обновить документацию, контекст и CHANGELOG; проверить rg по старым finance call sites. Деплой нового поведения сначала с YooKassa off. Затем включение одного YOOKASSA_ENABLED в согласованной конфигурации consumer открывает коммерцию. Повторный deployment технического каскада L4D не требуется.

## Выпуск и критерии готовности

Одна подготовительная schema ADD, если принят рекомендуемый вариант, затем совместимый выпуск двух backend и frontend с YooKassa off. Старые денежные workers/call paths остановлены до начала новых duration writes; технические сессии закрыты/переведены согласованно, confirmed usage сохранён. Не производить production schema/build/credential действия в рамках этого документа.

Готовность: один бесплатный terminal работает неограниченно; дополнительные подготовлены, но не доступны без YooKassa; после её включения покупка доступна автоматически и подтверждённая оплата сразу даёт срок; worker не может погасить соседнюю или новую сессию; длительности учитываются независимо от денег; старые finance writes недостижимы; пользователь видит своё состояние и понятное действие.

Rollback после первых новых платежей не означает возврат старого top-up образа. Нужен совместимый предыдущий subscription image или отключение покупок с сохранением прав и возможности сверки новых orders. Финансовая история и paid_until не откатываются ради отката кода.
