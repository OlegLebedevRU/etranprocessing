# Целевая архитектура многотенантной аутентификации и авторизации (MenuBuilder)

## 1. Обзор и архитектурные принципы

В платформе **etranprocessing / MenuBuilder** пользователи взаимодействуют с тенантными сущностями (терминалы, варианты меню, группы услуг, биллинг, отчёты).
Платформа обеспечивает строгое разграничение доступа между обычными пользователями организаций и суперпользователями (администраторами платформы), которым требуется оперативно переключаться между организациями (тенантный контекст) и работать на общеплатформенном уровне.

### Ключевые архитектурные принципы:
1. **Tenant-in-token (Вариант A)**: `orgId` и `org` являются неотъемлемыми claims JWT. Nginx (`auth_jwt`), backend MenuBuilder, ProcessingBackend и любые downstream-сервисы считывают тенант напрямую из криптографически проверенного токена без дополнительных запросов в базу данных.
2. **Единый контур доверия (RS256 External Issuer)**: Все токены выпускаются внешним асинхронным JWT issuer'ом (Yandex Cloud Function на базе RS256). Локальная подпись токенов в production строго исключена.
3. **Один активный токен у клиента**: У клиента всегда ровно один рабочий токен. Концепция параллельного «локального master-токена» полностью упразднена: платформенный контекст суперпользователя — это токен с claims `orgId=0, org="0", is_superuser=true`.
4. **Правило авторизации №1 (Права по claim, а не по типу токена)**: Доступ к суперпользовательским ручкам (`/api/admin/*`, `/api/devices/*`) проверяется исключительно по флагу `is_superuser` (через FastAPI dependency `require_superuser`), а не по `token_type`. Суперпользователь внутри тенанта сохраняет непрерывный доступ к административным сервисам без необходимости переключения в платформу.
5. **Правило авторизации №2 (Изоляция тенанта)**: Тенант для обычного пользователя определяется строго из токена (`resolve_org_id`). Любой `org_id`, приходящий в параметрах запроса (query/body), валидируется: при несовпадении с активным токеном возвращается `403 Forbidden`.
6. **Сервер-сессия — источник истины про активный тенант**: Активный тенант суперпользователя сохраняется в базе данных в серверной сессии (`user_sessions.active_org_id`). При `POST /api/auth/refresh` тенант берётся из `session.active_org_id`, что исключает нежелательный сброс тенанта у суперпользователя при фоновом обновлении токена.
7. **Гейт mock-путей и правило «Mock = зеркало контракта»**: Внутренний mock-генератор токенов обязан быть точной копией контракта внешнего issuer'а v2. Fallback-пути валидации токенов по HS256 (`mock_secret`) и чтение unverified claims намертво закрыты флагом `jwt_issuer_mock_enabled` и физически недоступны в production.
8. **Проверка аудитории и издателя (Audience & Issuer Validation)**: Флаг `jwt_verify_audience=True` гарантирует проверку claims `aud="menubuilder"` и `iss="external-jwt-issuer"`. Поддельные токены сторонних систем отклоняются.

## 2. Контракт внешнего JWT Issuer v2

Внешний issuer (Yandex Cloud Function) работает по контракту v2 (полная обратная совместимость с v1):
- Запрос подписывается с использованием HMAC-SHA256 (`secret = service_to_yc_service_secret`).
- Сигнатура запроса: `sha256(timestamp.nonce.requestBody)`.
- Верхнеуровневый словарь `params` содержит 8 обязательных полей:
  `orgId, userId, roleId, clientId, aud, iss, nonce, timestamp, signature, requestBody, (kid)`.
- Опциональные поля передаются **исключительно** внутри compact JSON строки `requestBody` (без пробелов, ключи в camelCase):
  - `username` (str): логин пользователя;
  - `origSub` (str): исходный субъект (для аудита имперсонации);
  - `isSuperuser` (bool): флаг суперпользователя (по умолчанию `roleId == 1`);
  - `isImp` (bool): флаг имперсонации (по умолчанию `isSuperuser and orgId > 0`);
  - `sid` (str | int): идентификатор серверной сессии `user_sessions.id`;
  - `accessTtlMinutes` (int, 1..240, по умолчанию 60 мин);
  - `refreshTtlDays` (int, 1..90, по умолчанию 30 дней).

## 3. Транспорт токенов, cookies и защита от CSRF

### 3.1. HttpOnly Cookie как единственный транспорт браузера
Браузерный клиент (`MenuBuilder/frontend`) полностью переведён на безопасный cookie-транспорт:
- **`accessToken`**: передается в HttpOnly cookie с `Path=/`, `SameSite=Lax`, `Max-Age=3600` (60 минут), флагом `Secure` при HTTPS.
- **`refreshToken`**: передается в HttpOnly cookie со строгим ограничением области видимости `Path=/api/auth`, `SameSite=Lax`, `Max-Age=2592000` (30 дней), флагом `Secure`. Ограничение `Path=/api/auth` гарантирует, что браузер никогда не передает долгоживущий refresh token на общеприкладные API-эндпоинты (`/api/catalog`, `/api/billing`, `/api/reports` и т.д.).
- **Поддержка заголовка `Authorization: Bearer <token>`**: сохраняется в бэкенде исключительно для внешних интеграций, CLI-утилит и автоматических тестов.

### 3.2. Почему маршрут переключения тенанта размещён под `/api/auth/`
Поскольку `refreshToken` имеет атрибут `Path=/api/auth`, браузер принципиально не отправляет эту куку на адрес `/api/admin/tenants/switch`. 
Чтобы исключить рассинхронизацию сессии и обеспечить надежное переключение:
1. Создан маршрут-алиас `POST /api/auth/switch-tenant` (внутри `admin_tenants.auth_alias_router`), на который браузер гарантированно передает куку `refreshToken`.
2. Вспомогательный хелпер `_resolve_current_session` разрешает активную сессию по следующему приоритету:
   - Если в access-токене передан claim `sid` -> выполняется прямой поиск по первичному ключу `get_session_by_id(sid)` (кука `refreshToken` не требуется).
   - Если claim `sid` отсутствует (например, первый запрос сразу после логина) -> сессия находится по значению `refreshToken` из куки или тела запроса.
3. Сохранен маршрут `POST /api/admin/tenants/switch` для обратной совместимости и сценариев вызова с заголовком Bearer.

### 3.3. Защита от CSRF
Для предотвращения атак межсайтовой подделки запросов (CSRF) действует middleware в `app/main.py`:
- Все мутирующие HTTP-методы (`POST`, `PUT`, `PATCH`, `DELETE`), аутентифицированные через cookie (при отсутствии заголовка `Authorization`), обязаны содержать заголовок:
  ```http
  X-Requested-With: XMLHttpRequest
  ```
- Запросы без этого заголовка отклоняются со статусом `403 Forbidden` (`detail: CSRF check failed`).
- Эндпоинты аутентификации `/api/auth/login` и `/api/auth/refresh` исключены из проверки (не требуют сессионной авторизации перед выполнением).

### Аудит действий суперпользователя (Impersonation Audit)
При выполнении мутирующих HTTP-методов (`POST`, `PUT`, `PATCH`, `DELETE`) суперпользователем, находящимся внутри тенанта (`is_imp=True`), в лог системы автоматически записывается структурированное событие аудита:
```
audit impersonated action user=<username> orig_sub=<orig_sub> org=<org_id> method=<method> path=<path>
```
Это обеспечивает полную прозрачность и соответствие требованиям безопасности финансовых систем.

## 6. Отвергнутые альтернативы

### Альтернатива: Server-Side Tenant Context (Хранение контекста исключительно на сервере)
- **Суть предложения:** Access JWT выпускается только с идентификатором пользователя (`userId`), а активная организация (`orgId`) хранится исключительно в сессии сервера в Redis/Postgres или передается заголовком `X-Org-Id`.
- **Почему отклонено:**
  1. **Нарушение автономности сервисов:** Микросервисы платформы (ProcessingBackend, сервисы генерации отчетов, шлюзы Nginx) не могут полагаться на заголовок клиента без дорогостоящего синхронного запроса в базу данных или сессионный кэш на каждый запрос, что уничтожает горизонтальную масштабируемость и stateless-природу API.
  2. **Риск подмены тенанта (Tenant Spoofing):** Доверие пользовательскому заголовку `X-Org-Id` на периметре Nginx создает критический вектор атаки на разграничение доступа между организациями.
  3. **Трассировка и финтех-аудит:** Claims токена (`org`, `is_imp`, `orig_sub`), подписанные доверенным закрытым ключом RS256, однозначно фиксируют контекст платежной операции непосредственно в логах Nginx и обработчиков очередей.
- **Итоговое решение:** Выбран подход **Tenant-in-token**, а задержка внешнего генератора токенов (2–3 секунды) полностью нивелирована:
  - Увеличением срока жизни access-токена до 60 минут;
  - Упреждающим тихим обновлением токена в фоне за 5 минут до истечения срока;
  - Single-flight дедупликацией параллельных запросов в `JwtIssuerClient`.
