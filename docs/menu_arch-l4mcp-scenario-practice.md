# Практика l4mcp: события как память удалённых сценариев

Дата: 2026-10-01. Основание: обсуждение практической пользы событий900–999
после внедрения l4mcp и исправления l4con1.9.4. Документ фиксирует рассуждения
и предложения; предлагаемые инструменты и соглашения ещё не реализованы.

## Границы документа

Это документационная задача: оценка текущих возможностей, минимальные
дополнения и пример обслуживания нескольких Windows-клиентов.
Изменения API, native tools, БД, планировщиков и production здесь не выполняются.

Владельцы: l4con исполняет удалённую команду и отправляет события через
существующее MQTT-соединение; IoT сохраняет события и их tenant;
MenuBuilder проверяет доступ и обращается к IoT через internal-интеграцию;
l4mcp предоставляет инструменты вызывающему ИИ. Новые миграции не предлагаются.

Инварианты: tenant isolation, UUID как корреляция, а не авторизация,
существующий console lease/TTL/Job, отсутствие автоматических повторов
изменяющих команд по отсутствию события. Проверка документа — соответствие
действующему контракту и явное отделение предложений от реализованных функций.

## 1. Что уже умеет система

Сейчас это основа для памяти удалённых сценариев, но не самостоятельный
движок их выполнения. MCP предоставляет команды и историю; вызывающий ИИ
выбирает сценарий, интерпретирует результаты и решает, что делать дальше.

| Возможность | Практическая польза |
|---|---|
| console_run | Выполнить явную удалённую команду через штатный console flow |
| console_send_event | Отправить переданный результат900–999 с446/447/448 |
| terminal_events_search | Прочитать сохранённые события конкретного устройства в текущем tenant |
| UUID448 | Связать несколько этапов одного запуска |
| IoT event ID, время и cursor | Получить доказательство записи и последовательно читать историю |
| Чтение без online/lease | Восстановить предыдущие результаты даже при недоступном устройстве |

E2E подтвердил несколько событий с одним UUID, чтение из нового MCP-сеанса,
фильтрацию и пагинацию. Выбор сценариев, понимание этапов, расписание и
восстановление исполнения автоматически пока не реализованы.

Текущие ограничения:

- Коды900–999 не имеют закреплённого глобального смысла.
- UUID связывает записи, но сам не описывает этап, попытку и версию сценария.
- console_send_event записывает переданный результат, но не проверяет,
  действительно ли описанное действие состоялось.
- correlation_id в console_run возвращается в результате, но не добавляет
  вызов l4con в произвольную команду автоматически.
- payload446 — текст до1024 UTF-8 байт, а не хранилище полного вывода консоли.
- Нет встроенного планировщика и гарантии однократного исполнения действия.

Для диагностического факта предпочтительно, чтобы сам выполняющийся скрипт
собрал наблюдение и вызвал l4con --send-event внутри той же удалённой команды.
Отдельная отправка через console_send_event полезна для явно обозначенного
резюме, но не заменяет проверку состояния устройства.

## 2. Минимальный формат результатов сценария

Предложение: использовать небольшой JSON внутри строки446 без новых тегов.
Пример ниже — логическое содержимое строки446, а не изменение её типа:

```json
{
  "v": 1,
  "scenario": "app-health",
  "revision": 1,
  "step": "observe",
  "attempt": 1,
  "status": "warning",
  "facts": {
    "disk_free_gb": 8,
    "logs_size_gb": 14,
    "app_version": "5.4"
  }
}
```

При отправке JSON сериализуется в строку и проверяется по UTF-8 размеру.
Это соглашение конкретных сценариев; произвольные текстовые payload остаются
допустимыми по текущему контракту.

| Поле | Назначение |
|---|---|
| device_id и tenant context | Конкретное устройство и граница доступа |
| 448 | UUID конкретного запуска сценария |
| scenario + revision в446 | Повторяемый сценарий и версия его правил |
| step + attempt в446 | Этап и номер попытки |
| 447 | Числовой результат этапа |
| IoT event ID и время | Подтверждение сохранения и порядок получения |

Один сценарий имеет много запусков с разными UUID. Один запуск содержит
несколько этапов с одним UUID. Так можно продолжать известный незавершённый
запуск и сравнивать результаты ежедневных запусков одного устройства.
Номер attempt описывает попытку; он не разрешает повтор действия сам по себе.

В446 хранятся компактные факты с понятными единицами и контекстом измерения.
Полные логи туда не помещаются. Значения447=-1/-2 уже используются для ошибок
аргументов и размера; прикладным кодам предлагается выделять положительные
значения, а0 трактовать по правилам конкретного этапа.

Нужно различать три результата: завершение удалённого процесса, CLI результат
отправки события и подтверждённую запись в IoT. Успешная отправка описанного
результата не доказывает корректность самого описания.

## 3. Сценарии как инструкции для вызывающего ИИ

Первое дополнение — несколько документированных сценариев с одинаковым
порядком работы:

1. Прочитать предыдущие результаты конкретного устройства.
2. Проверить их возраст, версию сценария и сопоставимость условий.
3. Выполнить короткую проверку через штатную удалённую консоль.
4. Записать наблюдение из самой удалённой команды.
5. Подтвердить наличие события в IoT.
6. Сравнить с историей и выбрать следующий этап.

История должна разделять наблюдение, решение и результат действия:
«служба работает», «предложен перезапуск», «после перезапуска проверка прошла»
означают разные вещи. Иначе продолжение сценария по истории ненадёжно.

Для начала достаточно соглашения по нескольким кодам9xx в документации
сценариев. Это предложение, а не существующая таблица значений900–999 в IoT.
Полный каталог, workflow engine и новую БД для результатов сейчас не требуется.

## 4. Инструмент сборки контекста сценария

Предлагаемый terminal_scenario_context мог бы возвращать:

- подходящие наблюдения и их возраст;
- последний подтверждённый этап заданного UUID;
- ошибки и этапы без подтверждённого завершения;
- изменения версии ПО или правил сценария;
- исходные event IDs, на которых основан контекст.

Он собирает проверяемые данные, а ИИ формирует выводы по ним. При ограничении
выборки инструмент сообщает, что история прочитана частично. История остаётся
tenant-scoped; знание чужого UUID не даёт доступа к ней. Перенос устройства
в другой tenant не должен возвращать старую историю прежнего владельца.

Первую версию можно сделать поверх текущего чтения событий с ограниченным
просмотром страниц. Текущий API не фильтрует по scenario внутри446, поэтому
такой сборщик должен явно ограничивать период и объём просмотра. Для
эффективного поиска за месяцы впоследствии может понадобиться отдельное
расширение контракта поиска. Новая БД результатов для этого не нужна.

Отсутствие завершающего события означает «результат неизвестен», а не
«выполнить действие заново». Перед повтором изменения проверяется фактическое
состояние устройства. Event ID/cursor задают порядок получения записей;
они не доказывают точное время изменения состояния ОС при задержках доставки.
Payload остаётся недоверенными данными, а не инструкциями для ИИ.

## 5. Пример: предупредить отказ ПО перед выходными

Условный пользователь обслуживает три Windows-клиента с прикладной службой.
Запрос пользователя к ИИ:

> Проверь клиентов перед выходными. Найди тех, кто может перестать работать
> до понедельника. Покажи доказательства из истории, предложи обслуживание
> и после моего решения проверь результат.

Сценарий собирает компактные факты:

- версию ПО и состояние службы;
- свободное место и размер согласованных каталогов журналов;
- размер очереди заданий, если ПО предоставляет такую проверку;
- количество ошибок приложения за определённый период;
- время работы Windows и наличие ожидающей перезагрузки, если это умеет
  проверять согласованный скрипт.

Конкретные команды, источники ошибок и признаки pending reboot зависят от
версии Windows и обслуживаемого ПО; этот документ не заявляет их готовность.
Устройства анализируются отдельно, в разрешённом tenant контексте.

Ниже гипотетические результаты, не факты диагностики реальных терминалов:

| Клиент | Накопленная история | Решение |
|---|---|---|
| А | Свободное место16 →12 →8 ГБ за два дня; растёт каталог журналов | ПО ещё работает, но при сохранении темпа место закончится примерно через два дня |
| Б | Три аварийных завершения после обновления ПО; место стабильно | Проверить связь с новой версией; очистка диска не объясняет эти сбои |
| В | Метрики стабильны, ошибок нет | Продолжить наблюдение без вмешательства |

Для клиента А последовательность:

```text
Наблюдение → сравнение с историей → предложение обслуживания
    → разрешённое действие → повторная проверка → проверка следующего дня
```

Очистка выполняется только для согласованного каталога архивных журналов
по правилам конкретного ПО. После неё сохраняются свободное место, объём
удалённых архивов и результат проверки приложения. На следующий день
оценивается, устранена ли причина роста или лишь временно освобождено место.

Если разговор прервётся, новый сеанс восстанавливает по устройству и UUID,
что обнаружили, что выполнили и что осталось проверить. Если устройство
недоступно, история остаётся доступной, но вывод учитывает возраст данных.

Это сначала предупреждение по наблюдаемым тенденциям. Надёжность прогнозов
нужно оценивать на накопленных сопоставимых данных. При отсутствии истории
выдаётся первичная диагностика без выдуманного прогноза. Обновление ПО,
перезагрузка Windows или смена правил измерения могут нарушать сопоставимость.

## 6. Рекомендуемый следующий этап

1. Зафиксировать формат результатов и написать два-три сценария:
   проверка здоровья ПО, тенденция расхода диска, проверка после обслуживания.
2. Прогнать их вручную: события → новый MCP-сеанс → восстановление контекста
   → следующий этап. Проверить неизвестный результат и недоступное устройство.
3. Добавить сборку контекста сценария поверх существующего поиска истории,
   с явными пределами выборки и сохранением ссылок на исходные записи.
4. После проверки пользы отдельно определить инициатора периодических запусков,
   расписание, разрешённые действия и условия продолжения.

MCP сейчас не является планировщиком. Право отправки событий l4con действует
только во время удалённой команды и её дочерних процессов в пределах Job/TTL.
Документ не предлагает фоновый локальный отправитель или обход этого права.
Регулярный запуск — отдельный слой, который стоит добавлять после проверки
пользы сценариев вручную.
