# Архитектура удалённого управления терминалом: Remote Input Control

Дата: 2026-09-09.  
Статус: Внедрено (Alpha).  
Компоненты: `MenuBuilder/frontend`, `MenuBuilder/backend` (BFF), `iot-rpc-rest-app` (`app1`), `RabbitMQ`, `leo4proxy`, `Mosquitto bridge`, `tools/l4desk`, `tools/l4superv`.

---

## 1. Концепция: разделение Video Plane и Control Plane

Система удалённого управления терминалом строится на строгом разделении потоков данных реального времени (видео) и команд управления (ввод):

```text
                                  +---------------------------------------+
                                  |         Браузер оператора             |
                                  |  (/video: React 19, antd 6, Canvas)   |
                                  +---------+--------------------+--------+
                                            |                    |
                 WebRTC Video Stream        |                    | WebSocket (Lease WSS)
                 (H.264/RTP over WSS)       |                    | + REST API
                                            v                    v
                                   +-----------------+  +-------------------------------+
                                   |  nginx :3000    |  |  nginx :3000                  |
                                   |  /janus-ws      |  |  /api/v1/video/               |
                                   +--------+--------+  +---------------+---------------+
                                            |                           |
                                            v                           v
                                   +-----------------+  +-------------------------------+
                                   |  l4media-janus  |  |  menubuilder-backend (BFF)    |
                                   +-----------------+  +---------------+---------------+
                                            ^                           |
                                            | RTP (UDP :6000+)          | Internal API / WS (http://app1:8000)
                                            |                           v
+-------------------------------+  +-----------------+  +-------------------------------+
|  Терминал (Windows 7/10/11)   |  | l4media-ingress |  |  iot-rpc-rest-app (app1)      |
|                               |  +-----------------+  +---------------+---------------+
|  ffmpeg.exe                   |           ^                           |
|  (gdigrab desktop -> RTP) ----+-----------+                           | AMQP publish / consume
|                                                                       v
|  l4desk.exe                   |                       +-------------------------------+
|  (SendInput: move & click) <--+-- Mosquitto bridge <--+  RabbitMQ 4 (Native MQTT)     |
|                               |   (srv/<SN>/ctl in,   |  (amq.topic srv.<SN>.ctl,     |
|  l4superv (SYSTEM watchdog) --+    dev/<SN>/ctl out)  |   queue ctl <- dev.*.ctl)     |
+-------------------------------+                       +-------------------------------+
```

1. **Video Plane (Видеотрансляция)**:
   - Захват экрана на терминале: `ffmpeg -f gdigrab -i desktop`.
   - Доставка: RTP через UDP на `l4media-ingress`, далее Janus WebRTC Gateway и воспроизведение через WebRTC в браузере.
   - Полная изоляция: через видеопоток **не передаются** команды управления, события мыши или метаданные.

2. **Control Plane (Управление вводом)**:
   - Передача команд от браузера через WebSocket-прокси MenuBuilder BFF в Internal API `app1`.
   - `app1` публикует команды в MQTT/AMQP-топик `srv/<SN>/ctl`.
   - Терминальный агент `l4desk.exe` получает команду через локальный брокер Mosquitto, проверяет валидность и исполняет через Win32 API `SendInput`.
   - Подтверждение (ACK/NACK) отправляется в `dev/<SN>/ctl` и транслируется обратно в браузер.
   - Изоляция шины: топики `ctl` полностью отделены от очередей событий `evt/eva`, шины интеграции и командной строки `l4con` (`tsk/rsp`).

## 2. Матрица ответственности компонентов

| Компонент | Зона ответственности | Что делать запрещено |
|---|---|---|
| **MenuBuilder frontend** | Вычисление фактической области экрана (`desktopRect`), нормализация координат `0..65535`, троттлинг перемещения курсора (≤10/с), явное подтверждение включения оператором, показ статусов ACK/NACK/Timeout, автоосвобождение аренды (release) при остановке видео или закрытии вкладки. | Прямой доступ к MQTT/RabbitMQ, хранение ключей сервиса, знание структуры очередей. |
| **MenuBuilder backend (BFF)** | Проверка JWT, организации (`org_id`), прав доступа (роли 1–3, запрет viewer), владения терминалом, вызов только Internal API `app1`, проксирование WebSocket с валидацией входящих сообщений. | Генерация MQTT-топиков, прямое подключение к RabbitMQ/MQTT, утечка внутренних ключей на фронтенд. |
| **iot-rpc-rest-app (`app1`)** | Управление жизненным циклом аренды (Lease TTL 60с, 1 аренда на SN), публикация команд в `srv.<SN>.ctl`, приём и корреляция ACK/NACK/Presence из очереди `ctl`, аудит действий оператора, Internal API. | Отображение UI, хранение видеокадров, повторные попытки клика. |
| **RabbitMQ 4** | Маршрутизация Native MQTT и AMQP топиков, топиковые ACL (`^srv.<SN>.*` read, `^dev.<SN>.*` write), буферизация очереди `ctl`. | Бизнес-логика валидации координат. |
| **Mosquitto bridge** (терминал) | Локальный брокер (`127.0.0.1:1883`), проброс `srv/<SN>/# in 1` и `dev/<SN>/# out 1` через `leo4proxy` на сервер. | Модификация payload сообщений. |
| **`l4desk.exe`** (терминал) | Zero-dependency C агент в сессии пользователя, приём команд `srv/<SN>/ctl`, проверка дедупликации, проверка доступности интерактивного экрана (`OpenInputDesktop`), выполнение `SendInput`, отправка ACK/NACK и Presence. | Доступ в интернет в обход localhost, использование TLS внутри агента, публикация в `dev/<SN>/svc|app|evt`. |
| **`l4superv`** (терминал) | Служба под SYSTEM, запуск `l4desk.exe` в активной интерактивной сессии пользователя через `session_proc` (`WTSQueryUserToken` + `CreateProcessAsUser`), перезапуск при смене сессии и сбоях. | Запуск `l4desk` в Session 0. |

## 3. Координатная модель: object-fit, padding ffmpeg и виртуальный экран

Для обеспечения пиксельной точности кликов фронтенд выполняет двухэтапную коррекцию координат:

1. **Коррекция `object-fit: contain`**:
   - Контейнер плеера имеет фиксированный или адаптивный размер (например, `W_c x H_c`).
   - Видеокадр имеет соотношение сторон $A_v = W_v / H_v$.
   - Вычисляется `contentRect` — прямоугольник видеоизображения за вычетом внешних полос (letterbox/pillarbox).

2. **Внутренний padding кадра ffmpeg**:
   - При захвате рабочего стола через ffmpeg с фильтром `scale=force_original_aspect_ratio=decrease,pad=(ow-iw)/2:(oh-ih)/2` внутри видеокадра могут образовываться внутренние чёрные поля.
   - По данным `presence.screen` (`virtual_width`, `virtual_height`) вычисляется соотношение сторон реального экрана терминала $A_d = W_{virt} / H_{virt}$.
   - Внутри `contentRect` центрируется результирующий прямоугольник `desktopRect` с соотношением сторон $A_d$.
   - Если геометрия экрана ещё не получена от `l4desk`, принимается `desktopRect = contentRect` и выводится предупреждение оператору.

3. **Нормализация координат**:
   - Клики и перемещения за пределами `desktopRect` игнорируются (не отправляются в сеть).
   - Внутри `desktopRect`:
     $$X_{norm} = \text{clamp}\left(0, 65535, \text{round}\left(\frac{P_x - \text{left}}{\text{width}} \times 65535\right)\right)$$
     $$Y_{norm} = \text{clamp}\left(0, 65535, \text{round}\left(\frac{P_y - \text{top}}{\text{height}} \times 65535\right)\right)$$
   - На стороне `l4desk.exe` Win32 API `SendInput` с флагом `MOUSEEVENTF_VIRTUALDESK | MOUSEEVENTF_ABSOLUTE` напрямую принимает нормализованный диапазон `0..65535`, охватывающий все мониторы виртуального рабочего стола.

## 4. Жизненный цикл аренды (Lease), уровни Scope и UX-состояния

### 4.1. Единый реестр аренды (Unified LeaseRegistry в `app1`)
Вся монопольная аренда терминала централизованно управляется в сервисе `iot-rpc-rest-app` (`app1`). BFF `MenuBuilder` не хранит локального состояния аренды и не дублирует логику захвата; он транслирует контекст пользователя через обязательные заголовки `X-User-Id`, `X-Role`, `X-Org-Id`, `X-Session-Id` (извлекаемый из claim `jti` / `session_id` в JWT).

Иерархия и разграничение уровней аренды (`scope`):
1. **`console`**: Удалённая диагностическая командная консоль (`DeviceConsoleTab`). Доступна **строго суперадминистраторам** (роль 1 или `role: "superuser"`).
2. **`input`**: Полноценное удалённое управление терминалом (мышь + клавиатура). Доступно операторам (роли 1, 2, 3). Требует активного видеопотока в режиме рабочего стола (`mode: "desktop"`).
3. **`stream`**: Управление видеотрансляцией (запуск, остановка, переключение источников). Доступно операторам (роли 1, 2, 3).
4. **`view`**: Просмотр запущенного видеопотока. Доступно операторам (роли 1, 2, 3) и наблюдателям (роль 4 с правом `video:view`). Для роли 4 аренда выдаётся только при наличии уже запущенного видеопотока (`stream_not_running` -> 409).

**Взаимоисключение (Mutual Exclusivity):**
Консоль диагностики (`console`) и видеотрансляция / управление (`stream` / `input` / `view`) **взаимоисключены** на уровне `app1`. Попытка открыть консоль при активной трансляции или запустить трансляцию при открытой консоли возвращает `409 Conflict (lease_taken)` с указанием роли и маскированного имени текущего владельца.

### 4.2. UX-состояния в веб-интерфейсе
1. **`idle`**: Сессия видео не активна, аренда свободна.
2. **`acquiring`**: Отправлен запрос `POST .../control/lease` на получение аренды выбранного уровня (`scope`).
3. **`active`**: Аренда получена, медиапоток и/или канал ввода активны.
4. **`busy`**: Терминал занят другим пользователем (`409 lease_taken`). Отображается явный отказ без автоповторов: «Терминал занят: <роль> (<владелец>) до <время>».
5. **`stream_not_running`**: Наблюдатель (роль 4) пытается получить аренду `view`, но оператор ещё не запустил поток. Отображается сообщение «Трансляция не запущена оператором».
6. **`agent_offline`**: Агент `l4desk` не присылает presence или отключён (LWT offline).
7. **`desktop_locked`**: Рабочий стол терминала заблокирован Windows (`Winlogon`, скринсейвер, окно UAC). Инъекция кликов и клавиш заблокирована до входа в систему.
8. **`error`**: Ошибка соединения или отказ терминала (с расшифровкой NACK: `source_unavailable`, `ffmpeg_missing`, `terminal_timeout` и др.).

### 4.3. Таймауты, Keepalive и автоосвобождение
- **Время жизни аренды на сервере `app1`**: 60 секунд.
- **Интервал keepalive**: клиент (BFF / Frontend) продлевает аренду каждые 10 секунд через `POST .../control/keepalive`.
- **Автоматическое освобождение (Release)**:
  - При закрытии вкладки / навигации со страницы срабатывает `pagehide` / `beforeunload` с отправкой запроса на освобождение аренды.
  - При выходе из системы (`POST /api/auth/logout`) BFF вызывает `DELETE /api/internal/v1/remote-input/leases/by-owner`, освобождая все активные аренды сессии пользователя.
  - При отзыве аренды (`lease_revoked`) по WebSocket плеер и оверлей немедленно останавливаются с отображением причины.

## 5. Поддержка устройств ввода

- **Мышь**: поддерживаются перемещение курсора (`pointer_move`) с нормализацией координат `0..65535` и левый одиночный клик (`mouse_click`, `button: "left"`).
- **Клавиатура**: захват клавиш при фокусе на окне видеотрансляции (`keydown` / `keyup` -> событие `key` с параметрами `kind: "down" | "up" | "press"`, `vk: number`, `text?: string`).
- **Защита в режиме камеры**: при трансляции USB-камеры (`mode: "usb-camera"`) оверлей управления вводом принудительно отключается с информационным предупреждением.

## 6. Roadmap развития

1. **Redis для распределённого состояния `app1`**:
   - В alpha-версии состояние аренды хранится in-memory при условии `WEB_CONCURRENCY=1`.
   - При масштабировании воркеров gunicorn (`WEB_CONCURRENCY > 1`) состояние аренды и pending-команд будет вынесено в Redis.
2. **Динамическое согласование параметров ffmpeg**:
   - Передача параметров видеозахвата (разрешение экрана, частота кадров, отключение pad-фильтра) через control flow при включении управления для снижения задержки.

## 7. Диагностика и устранение неполадок (Troubleshooting)

При возникновении проблем последовательно проверяйте логи компонентов:

1. **`MenuBuilder/backend`**:
   - Логи WebSocket прокси и запросов аренды:
     ```bash
     sudo docker logs --tail=100 -f menubuilder-backend
     ```
   - Проверьте наличие `WebSocket session finished ... reason=...`.

2. **`iot-rpc-rest-app` (`app1`)**:
   - Лог команд удалённого ввода: `logs/remote_input.log` внутри контейнера `app1`:
     ```bash
     sudo docker exec -it app1 tail -f logs/remote_input.log
     ```
   - Фиксируются `command_id`, время прохождения, статус `injected` / `nack`, задержка (latency).

3. **Локальный брокер Mosquitto на терминале**:
   - Файл: `C:\l4tools\mosquitto\log\mosquitto.log`.
   - Проверьте подключение клиента `svc_desk` к `127.0.0.1:1883` и подписку на `srv/<SN>/ctl`.

4. **Агент `l4desk` на терминале**:
   - Файл: `C:\l4tools\l4desk\log\l4desk.log`.
   - Проверьте строки:
     - `Process running in Session ID: <N>` (должно быть > 0).
     - `Published presence [online]: ...`.
     - `Click injected at (X, Y) for cmd=...`.
   - Если отображается `interactive desktop unavailable` — экран терминала заблокирован.

5. **Супервизор `l4superv` на терминале**:
   - Команда: `C:\l4tools\l4superv\l4superv.exe --status`.
   - Проверьте строку: `l4desk : RUNNING (pid <PID>, session <N>)`.
