# Руководство инженера: Развертывание и эксплуатация комплекса Leo4 Tools (l4setup)

Настоящее руководство предназначено для сервисных инженеров, технических специалистов и администраторов платёжных терминалов экосистемы **etranprocessing**. Документ описывает целевой процесс развертывания по принципу **Zero-Touch («Скачать → проверить хэш → запустить → прочитать итог»)**, поведение установщика во всех начальных состояниях Windows (S1–S10), диагностику, откат и решение типовых инцидентов.

При истечении сертификата MQTT/RTP блокируются локально, независимо от policy
доступности. Просроченный сертификат восстанавливается старым ручным setup flow.
Подробности: [фактические контракты и timing matrix](term_arch-rpc7011-flow-matrix.md).

## 1. Концепция развертывания: Zero-Touch («Нажал и забыл»)

Комплекс утилит терминала L4 Suite включает компоненты:
- **`Leo4Proxy`** — локальный mTLS SChannel HTTPS/RTP-прокси и источник метаданных (`http://127.0.0.1:18443/_leo4/info`);
- **`mosquitto`** — локальный MQTT-брокер (с мостом во внешнюю шину при наличии сертификата);
- **`L4Con`** — агент удаленной диагностики по MQTT;
- **`L4Superv`** — системный супервизор, сторожевой таймер (Watchdog) и оркестратор сессий;
- **`l4desk`** — служба захвата экрана и трансляции удаленного управления в консольной сессии пользователя;
- **`l4pin`** — встроенный модуль и CLI-утилита выпуска и проверки сертификатов mTLS;
- **`ffmpeg`** — автономный статический медиадвижок RTP-видеопотока.

Целевой установщик **`l4setup.exe`** представляет собой единый автономный бинарный модуль (Single-Binary Bootstrapper), автоматически определяющий разрядность операционной системы (x86 или x64), подготавливающий системное окружение, проверяющий состояние сертификата и запускающий службы без ручного конфигурирования.

> ⚠️ **Важное замечание о версионировании и обновлениях в Этапе 1:**  
> В релизе Этапа 1 автономное самообновление по сети (Update Agent в `l4superv`) **не входит в состав релиза** и запланировано к реализации в Этапе 2. Установка новых версий комплекса выполняется инженером аналогично — запуском актуального файла `l4setup.exe`.

## 2. Получение дистрибутива и верификация целостности

Дистрибутивные пакеты публикуются в публичном Generic-реестре артефактов и не хранятся в Git-репозитории.

### 2.1. Загрузка из реестра
Дистрибутив конкретной версии (`1.10.2`) загружается по прямому HTTPS-адресу:
- **Установщик:** `https://l4tools-generic.ar.cloud.ru/l4tools/<semver>/l4setup.exe`
- **Манифест релиза:** `https://l4tools-generic.ar.cloud.ru/l4tools/<semver>/l4tools-release.json`
- **Контрольные суммы:** `https://l4tools-generic.ar.cloud.ru/l4tools/<semver>/SHA256SUMS`

Пример загрузки через командную строку Windows:
```cmd
curl.exe -O https://l4tools-generic.ar.cloud.ru/l4tools/1.10.2/l4setup.exe
curl.exe -O https://l4tools-generic.ar.cloud.ru/l4tools/1.10.2/SHA256SUMS
```

### 2.2. Проверка контрольной суммы (SHA-256)
Перед запуском на терминале обязательно проверьте целостность файла `l4setup.exe`:

```cmd
certutil -hashfile l4setup.exe SHA256
```

Сравните хэш полного скачанного файла со строкой `l4setup.exe` в `SHA256SUMS`
и хэшем выпуска выше. HEAD `digest` не заменяет проверку скачанных bytes.
Проверьте подпись в PowerShell:

```powershell
$signature = Get-AuthenticodeSignature .\l4setup.exe
$signature | Select-Object Status, TimeStamperCertificate
```

Для опубликованного 1.10.2 ожидаются `Status = Valid` и непустой timestamp certificate.

**Что делать при несовпадении контрольной суммы:**
1. Немедленно удалите поврежденный файл `l4setup.exe`.
2. Проверьте стабильность интернет-канала и отсутствие кэширующих корпоративных прокси.
3. Повторите загрузку. Запуск поврежденного файла заблокирован или приведет к ошибке распаковки (код возврата `23`).

## 3. Запуск инсталлятора

`l4setup.exe` требует прав Администратора. При интерактивном запуске он автоматически запросит повышение привилегий через Windows UAC Elevation.

### 3.1. Интерактивный запуск (GUI / двойной клик)
- При запуске двойным кликом открывается графическое окно.
- Если на машине **уже есть действующий сертификат** (состояние S9), инсталлятор выведет информацию об обнаруженном сертификате (серийный номер и срок действия) и **не будет запрашивать PIN**. Для завершения установки достаточно нажать кнопку «Установить».
- Если сертификат **отсутствует**, появится поле ввода 6-значного PIN-кода и кнопка **«Пропустить — ввести позже»** (для отложенной активации).

### 3.2. Автоматический запуск из скриптов (`--silent`)
Для систем удаленного развертывания и фоновых скриптов используется тихий режим:

```cmd
:: Автоматическая установка с использованием существующего сертификата или отложенным вводом PIN:
l4setup.exe --silent

:: Автоматическая установка с первичным выпуском сертификата по PIN:
l4setup.exe --silent --pin "%L4TOOLS_CERT_PIN%"
```

> **Поведение `--silent` без `--pin`:**
> Если ключ `--pin` не передан, режим `--silent` автоматически эквивалентен `--no-pin`: при наличии валидного сертификата он переиспользуется, а при отсутствии — установка успешно завершается в режиме `Standby` с активным ожиданием (код `10`).

### 3.3. Полный перечень параметров командной строки

```text
l4setup.exe [ОПЦИИ]
```

| Параметр | Короткий | Описание |
|---|---|---|
| `--pin <PIN>` | `-p` | 6-значный одноразовый PIN-код для выпуска клиентского сертификата mTLS. При наличии валидного сертификата игнорируется (выводится предупреждение `cert_reused_pin_ignored`). |
| `--force-reissue` | — | Разрешить принудительный перевыпуск сертификата, даже если текущий сертификат валиден (требует обязательного указания `--pin`). **Внимание:** приводит к смене thumbprint и отпечатков! |
| `--no-pin` | — | Не запрашивать PIN; если сертификат отсутствует, завершить установку в режиме Standby (код `10`). |
| `--silent` | `/S` | Тихий фоновый режим без открытия окон и интерактивных диалогов. |
| `--dest <DIR>` | `-d` | Целевой каталог установки (по умолчанию `C:\l4tools`, либо значение `installer_base_path` из `state.json`). |
| `--repair` | — | Принудительная переустановка файлов и служб даже при совпадении установленной версии. |
| `--smoke-only` | — | В 1.10.2 — read-only discovery/SCM/local/TLS; без CA/enrollment/config/services/state изменений. Пишет log/summary. Несовместим с PIN, repair, force-reissue, payload и network options. В 1.10.1 безопасный диагностический запуск не гарантировался. |
| `--version` | — | Вывести версию установщика (из `VERSIONINFO`) и завершить работу с кодом `0` (не требует прав UAC). |
| `--help` | `-h`, `/?` | Вывести краткую справку по опциям и кодам возврата (не требует прав UAC). |
| `--resolve-auto` | — | Убрать ручные адреса и включить SRV; bootstrap IP сохраняется. |
| `--no-srv` | — | Отключить только SRV, сохранить policy/default/IP fallback. |
| `--policy-bootstrap-ip <IP>` | — | Публичный IPv4 для recovery GET policy с прежним TLS-именем. |
| `--mqtt-remote`, `--http-remote`, `--stream-remote`, `--rtp-remote` `<host:port>` | — | Ручной upstream; не включает выключенный канал. |
| `--preview-ui` | — | Предпросмотр GUI без installer engine и изменения установки. |

В примере silent/PIN переменная `L4TOOLS_CERT_PIN` должна быть заранее задана
оператором в окружении; значение PIN не хранится в репозитории.

### 3.4. Настройки сети и upstream TLS

Диалог «Сеть…» задаёт Auto или manual host:port для канала, bootstrap IP и
отключение SRV. В выпущенный setup bootstrap IP включён заранее.
Upgrade/Repair без изменения сети сохраняет SCM options; изменение сети также
сохраняет остальные CLI options. `leo4proxy/service-args.txt` зеркалирует SCM
ImagePath для watchdog/repair, существующий SCM остаётся authoritative.

Auto: SRV → verified SRV LKG → fresh policy host → default → fresh policy IP.
Explicit remote приоритетнее Auto; SRV target `.` запрещает обход канала.
Bootstrap IP используется только для recovery GET policy. Numeric fallback
сохраняет логическое TLS/SNI/Host имя, проверки встроенного CA, имени, срока и
serverAuth. Отключение проверки сертификата как «последний шанс» не реализовано.
CRL/OCSP не проверяются; локальное время должно быть корректным.

При активном client cert verify запускает `leo4proxy --check-upstream` с
service args: общий budget 8 секунд, ожидание процесса до 8.5 секунд.
`probes.upstream_tls` содержит mqtt/https/l4stream/l4rtp verdicts:
`valid`, `skipped` (канал выключен), `policy_blocked`, `cert_invalid`,
`probe_failed`, `timeout`; непроведённые пробы — `not_run`.
Проверка делает TLS handshake, не MQTT CONNECT или video session.
Media endpoint в `/_leo4/info` может быть пуст до первого потока: media
connection служба открывает по требованию.

`probes.network` в 1.10.2 выводится из фактических upstream TLS результатов:
`reachable`, `unknown` или `not_run`. Каждый канал получает независимый 8-секундный
budget; transport failures допускают до трёх попыток с паузой 5 с внутри Verify
budget 60 с. Trust failures не повторяются автоматически. Нет отдельной DNS-пробы
`iot.leo4.ru`, которая в 1.10.1 могла дать ложный degraded при работающем IP recovery.
Смотрите также verdicts каналов, не только общий статус.

## 5. Чтение результатов установки и диагностика

По окончании работы `l4setup.exe` формирует структурированный отчет и подробный лог в целевом каталоге `C:\l4tools\`.

### 5.1. Файл итогов `C:\l4tools\install_summary.json`
Файл содержит исчерпывающий снимок состояния и доступен для автоматизированного анализа мониторингом:

```json
{
  "schema": 2,
  "timestamp": "2026-10-04T14:18:46Z",
  "installer_version": "1.10.1",
  "installed_version": "1.10.1",
  "os": "Windows 10 Home (10.0.19045) x64",
```

#### Значения полей `status`:
- **`ready`** (код `0`) — критерии установщика выполнены, включая TLS-пробы включённых каналов при активном сертификате. Это не доказательство MQTT application flow, декодирования видео или удалённого ввода E2E.
- **`activation_required`** (код `10`) — службы запущены в режиме Standby, комплекс ожидает активации; старое название — `standby_waiting_pin`.
- **`ready_for_online`** (код `11`) — установка выполнена оффлайн, PIN зашифрован в `pending_pin.json`, ожидает подключения к сети.
- **`degraded`** (код `12`) — DNS-проба не прошла, l4desk не появился в активной пользовательской сессии или TLS включённого upstream дал `cert_invalid`, `probe_failed` либо `timeout`; причина в `error_reason`. Старое название — `ready_with_warnings`.
- **`failed`** (коды `20..30`) — критическая ошибка установки (см. таблицу кодов возврата).
- **`cancelled`** (код `31`) — отмена на границе этапа, состояние служб проверяется по summary.

Пример выше сокращён. Schema 2 также содержит `phase`, `error_reason` и фактические
состояния `services`; непроведённые пробы обозначаются `not_run`, неизвестные
состояния — `unknown`/`null`, а не успешным значением по умолчанию.
`pending_reboot_detected` может сопровождать `ready` / 0: наличие предупреждения
не равно провалу установки и не доказывает успешный запуск после перезагрузки.

В лог-файл поминутно записываются все фазы работы, вызовы подсистем и ошибки. Внимание: PIN-коды и секретные ключи **никогда** не записываются в лог и маскируются как `******`.

## 6. Повторный запуск, восстановление и smoke-проверка

### 6.1. Идемпотентный повторный запуск
Если версия `l4setup.exe` совпадает с установленной в `state.json.installed_version` и исполняемые файлы не повреждены, повторный запуск:
```cmd
l4setup.exe --silent
```
автоматически пропускает фазы дренажа, распаковки и перерегистрации служб, выполняя только проверку сертификата (фаза 3) и экспресс-тестирование работоспособности. Это экономит ресурсы и предотвращает лишний рестарт служб.

### 6.2. Принудительное восстановление (`--repair`)
Если файлы утилит были повреждены или службы удалены вручную, используйте флаг `--repair`:
```cmd
l4setup.exe --repair
```
Инсталлятор принудительно перезапишет все бинарные файлы из встроенных ресурсов и перерегистрирует службы в Windows SCM. При этом действующий сертификат терминала сохраняется и не затрагивается.

### 6.3. Диагностический запуск 1.10.2 и историческое ограничение 1.10.1

В 1.10.2 выполните `l4setup.exe --smoke-only --dest C:\l4tools`. Этот режим
не устанавливает сертификаты, не меняет службы/конфигурацию/state и не запускает
enrollment; сохраняет только log/summary. Параметры upstream читаются из SCM.
На установленном 1.10.1 проверка новой сборкой дала ready/0 без изменения четырёх
service PID и installed_version. Это не проверка Upgrade до 1.10.2.

История 1.10.1:

CLI разбирает `--smoke-only`, но engine не использует поле `smoke_only`.
Операция определяется installed/target version и целостностью: при отличающейся
версии возможен Upgrade, при повреждении — Repair, при отсутствии — Install.
Даже Verify проходит Prepare, certificate phase и service start checks.
Этот флаг не гарантирует отсутствие установочных изменений.

Для проверки без installer engine используйте:

```cmd
curl.exe --noproxy "*" http://127.0.0.1:18443/_leo4/info
C:\l4tools\leo4proxy\leo4proxy.exe --check-upstream --rtp-tunnel --policy-bootstrap-ip 87.242.100.34
```

Передайте свои network/service options в probe, если они отличаются.
Проверка не пишет routing cache и не управляет службами, но делает TLS handshakes.
При повторном запуске l4setup оценивайте выбранную операцию до нажатия кнопки.

## 7. Резервное копирование и процедура отката (Rollback)

При выполнении установки инсталлятор автоматически создает резервную копию заменяемых бинарных файлов и конфигураций в подкаталоге:
```text
C:\l4tools\rollback\
```

### Автоматический откат
Если на этапе распаковки (фаза 2) или регистрации служб происходит критический сбой, установщик восстанавливает предыдущие версии файлов из папки `rollback` и запускает исходные службы.

### Ручной откат при нештатных ситуациях
Если требуется вручную вернуть предыдущее состояние утилит:
1. Остановите службы комплекса:
   ```cmd
   net stop L4Superv
   net stop L4Con
   net stop mosquitto
   net stop Leo4Proxy
   ```
2. Скопируйте файлы из каталога последней резервной копии `C:\l4tools\backup-<date>\` (или `C:\l4tools\rollback\`) обратно в `C:\l4tools\`.
3. Запустите службы:
   ```cmd
   net start Leo4Proxy
   net start mosquitto
   net start L4Con
   net start L4Superv
   ```
4. Клиентский сертификат в хранилище `LocalMachine\MY` при этом остается нетронутым.

## 8. Часто задаваемые вопросы (FAQ)

### Вопрос 1: Windows SmartScreen блокирует запуск `l4setup.exe` («Система Windows защитила ваш компьютер»)
Выпуск 1.9.6 подписан Authenticode с меткой времени; SmartScreen также учитывает
репутацию и политику Windows. Сначала сверяйте SHA-256 с записью релиза и подпись:

```powershell
Get-AuthenticodeSignature .\l4setup.exe | Format-List Status, SignerCertificate, TimeStamperCertificate
```

Ожидаются `Valid`, согласованный издатель и timestamp. Ошибку подписи не следует
обходить. Порядок подписи каждого нового выпуска закреплён в [release runbook](../tools/release/README.md).

### Вопрос 2: Терминал в MenuBuilder UI отображается как `offline` после установки
**Причина 1:** Установка завершилась в режиме `Standby` (код `10`), так как сертификат не был установлен, а PIN не вводился.  
*Решение:* Запустите ввод PIN командой:
```cmd
C:\l4tools\l4setup.exe --pin <ВАШ_PIN>
```
или выполните `C:\l4tools\l4pin\l4pin.exe <ВАШ_PIN>`. Через 15 секунд терминал перейдет в `active` и станет `online`.

**Причина 2:** На терминале заблокирован исходящий сетевой трафик к серверу `dev.leo4.ru:8883` или `iot-processing.ru:443`.  
*Решение:* Проверьте доступность серверов через `powershell -c "Test-NetConnection dev.leo4.ru -Port 8883"`.

### Вопрос 3: Требуется перевыпустить сертификат на терминале (смена SN или компрометация)
**Решение:** Для принудительного перевыпуска сертификата запустите установщик со специальным флагом `--force-reissue`:
```cmd
l4setup.exe --force-reissue --pin <НОВЫЙ_PIN>
```
> ⚠️ Перевыпуск создаёт новый ключ и меняет serial/Thumbprint. Старые распознанные терминальные сертификаты очищаются только после проверки нового. Если очистка профилей не завершилась, новый проверенный сертификат сохраняется; исследуйте ошибку, прежде чем расходовать ещё один PIN.

### Вопрос 4: Как проверить текущее состояние терминала без открытия окон?
Выполните команду проверки статуса супервизора:
```cmd
C:\l4tools\l4superv\l4superv.exe --status
```
или прочитайте файл `C:\l4tools\install_summary.json`.

## 9. Чего категорически НЕЛЬЗЯ делать сервисному инженеру

1. ❌ **НЕ запускайте `l4pin.exe --force` без служебной необходимости.**  
   Force разрешает перевыпуск и смену серверной привязки. Нужен новый действующий PIN; очистка прежних терминальных сертификатов выполняется после проверки нового. Ошибка очистки требует диагностики, а не повторного перевыпуска вслепую.
2. ❌ **НЕ удаляйте сертификаты вручную из оснастки `certmgr.msc` / `Cert:\LocalMachine\My`.**  
   Это приведет к рассинхронизации состояния с `state.json` и сбросу терминала супервизором при проверке клонирования.
3. ❌ **НЕ передавайте PIN-коды и приватные ключи в незашифрованном виде** (через открытые чаты, скриншоты или тикеты). Одноразовый PIN действует ограниченное время и привязывается к первому активировавшему его терминалу.
4. ❌ **НЕ переименовывайте папки внутри `C:\l4tools\`** (`leo4proxy`, `mosquitto`, `l4superv`). Службы Windows SCM зарегистрированы по фиксированным абсолютным путям.
