# Спецификация требований к корзине лицензий, правилам калькуляции и настройкам организаций

## 1. Контекст и цели документа

Настоящий документ фиксирует бизнес-логику, пользовательский опыт (UX), правила расчета стоимости лицензий и параметры организаций для платформы **etranprocessing**. 

Данные требования расширяют существующий механизм биллинга с учетом различных сценариев работы тенантов:
1. Оплата по факту возникновения задолженности (пост-оплата / льготный период).
2. Фиксированные и минимальные периоды продления (например, строго +1 мес или шаги +3, +6, +12 мес).
3. Тарификация, привязанная к сертификату (лицензия синхронизируется со сроком действия mTLS-сертификата).
4. Контактные данные организаций (`email`, `phone`) и признак почтовых уведомлений (`notify_by_email`).
5. Настройки калькуляции по умолчанию в личном кабинете тенанта, управляемые из суперадмин-панели.

## 2. Расширение модели данных организаций (`Org` и `OrgBillingSettings`)

### 2.1. Поля сущности `Org` (Контакты и коммуникации)
В таблицу `orgs` добавляются контактные атрибуты для идентификации ответственных лиц и будущей подсистемы уведомлений:
* **`email`** (`VARCHAR(255)`, nullable): официальный контактный email организации для отправки счетов, актов и уведомлений о лицензиях.
* **`phone`** (`VARCHAR(50)`, nullable): контактный телефон организации/администратора.
* **`notify_by_email`** (`BOOLEAN`, NOT NULL, default `True`): флаг разрешения отправки почтовых уведомлений (напоминания об истечении лицензий, чеки, акты).

### 2.2. Поля сущности `OrgBillingSettings` (Правила калькуляции и биллинга)
В таблицу `org_billing_settings` добавляются параметры, определяющие поведение корзины и калькулятора:
* **`billing_mode`** (`VARCHAR(30)`, default `'standard'`):
  * `'standard'`: стандартная предоплата. Доступен выбор любого числа авансовых периодов.
  * `'post_factum'` (по факту задолженности): организация оплачивает лицензии только при возникновении задолженности (`lapsed`). Терминалы продолжают работать до блокировки, в корзине по умолчанию рассчитывается только задолженность.
  * `'cert_linked'` (по сертификату): лицензия не тарифицируется отдельно, а привязана к сроку mTLS-сертификата. Оплата взимается за выпуск/перевыпуск сертификата (PIN), а дата окончания лицензии (`expires_at`) выставляется равной дате истечения сертификата (`cert_not_valid_after`).
* **`min_billing_periods`** (`INTEGER`, default `1`): минимальное количество периодов для единовременной оплаты (например, `1` для ежемесячной, `3` для квартальной).
* **`allowed_billing_periods`** (`VARCHAR(50)`, nullable, например `'1'` или `'3,6,12'`): список разрешенных шагов продления в месяцах.
  * Если задано `'3,6,12'`, пользователь может продлить терминал только на 3, 6 или 12 месяцев.
* **`default_selection_mode`** (`VARCHAR(30)`, default `'all_due'`): режим выделения терминалов по умолчанию на странице биллинга:
  * `'only_lapsed'`: по умолчанию отмечены галочками только терминалы с задолженностью (для режима `'post_factum'`).
  * `'all_due'`: отмечены терминалы с задолженностью и истекающие в ближайшие 30 дней.
  * `'all'`: отмечены все терминалы организации.

## 3. Сценарии расчета и UX корзины (Use Cases)

### Сценарий 1: Оплата по факту возникновения задолженности (Пост-оплата)
* **Пример настройки:** Организация 424 (`billing_mode = 'post_factum'`, `min_billing_periods = 1`, `allowed_billing_periods = '1'`).
* **Поведение в интерфейсе:**
  1. Терминал имел срок действия лицензии до 01.09.2026.
  2. 01.09.2026 терминал переходит в статус задолженности (`lapsed`), но продолжает обслуживание благодаря льготному периоду.
  3. 02.09.2026 тенант заходит в личный кабинет `/billing`.
  4. По умолчанию система автоматически выбирает для оплаты **только** терминалы с задолженностью. Другие терминалы (активные, без долга) не выделены (галочки сняты).
  5. В селекторе периода по умолчанию выставлен 1 месяц продления.
  6. Калькулятор рассчитывает сумму:
     $$\text{Сумма} = 1 \text{ период} \times \text{monthly\_price\_minor}$$
     Новая дата окончания пролонгируется на +1 месяц от анкора (до 01.10.2026).
  7. Тенант может вручную отметить дополнительные терминалы или добавить авансовые месяцы, если это не запрещено строгим `allowed_billing_periods`.

### Сценарий 2: Фиксированная сетка продления (+3, +6, +12 месяцев)
* **Пример настройки:** Организация с контрактным квартальным/годовым обслуживанием (`allowed_billing_periods = '3,6,12'`, `min_billing_periods = 3`).
* **Поведение в интерфейсе:**
  1. В селекторе авансовых периодов доступны только значения **3 мес**, **6 мес**, **12 мес**.
  2. Тенант может оплатить как заблаговременно (до истечения текущей даты), так и при возникновении задолженности.
  3. Дата окончания рассчитывается строго с шагом 3/6/12 месяцев от текущей даты окончания (или от даты закрытия задолженности).

### Сценарий 3: Лицензирование, привязанное к сертификату (`cert_linked`)
* **Пример настройки:** Организация со спец-тарифом на сертификаты (`billing_mode = 'cert_linked'`, `cert_billing_mode = 'per_operation'`).
* **Поведение в интерфейсе:**
  1. Стоимость регулярной лицензии за месяц отображается как 0 ₽ (или «включено в сертификат»).
  2. При заказе нового PIN-кода сертификата взимается стоимость генерации PIN (`cert_price_minor`).
  3. При успешной установке сертификата на терминале (`/api/certificates/?function=setup`) дата окончания лицензии автоматически приравнивается к `cert_not_valid_after` (например, +1 или +2 года).

## 4. Административный интерфейс управления организациями (Admin UI)

Формы создания и редактирования организаций (`/admin/organizations`) расширяются следующими блоками:

1. **Основные данные:**
   * Название организации (`org_name`, `name`).
   * Контактный Email (`email`).
   * Контактный телефон (`phone`).
   * Флаг «Отправлять уведомления на почту» (`notify_by_email` — checkbox).

2. **Лицензирование и биллинг:**
   * Ежемесячная стоимость лицензии (`monthly_price_minor`, руб.).
   * Модель биллинга (`billing_mode`):
     * Стандартная (предоплата)
     * По факту задолженности (пост-оплата)
     * Привязана к сертификату
   * Разрешенные периоды оплаты (`allowed_billing_periods`): выпадающий список или мультиселект (`1 мес`, `3 мес`, `6 мес`, `12 мес`, `любой`).
   * Минимальный период оплаты (`min_billing_periods`).
   * Настройки сертификатов: режим тарификации (`cert_billing_mode`), цена за PIN (`cert_price_minor`), право тенанта генерировать PIN (`tenant_pin_creation_enabled`).

## 5. Архитектурное разделение и статус реализации

1. **Первый шаг (Реализовано):**
   * Перенос роутера `billing.py`, сервисов и схем из `ProcessingBackend` в `MenuBuilder`.
   * Добавление полей `email`, `phone`, `notify_by_email`, `billing_mode`, `min_billing_periods`, `allowed_billing_periods` в модели и схемы `MenuBuilder`.
   * Реализация эндпоинта `GET /api/ListMenuFile` в `ProcessingBackend` для обслуживания mTLS-терминалов.
   * Настройка роутинга в `nginx.conf`.
2. **Второй шаг (Реализовано):**
   * Доработка клиентской корзины (`CheckoutModal.tsx`) и фильтров `/billing` в соответствии со сценариями 1–3.
   * Адаптивная сетка прогноза задолженности/продления по периодам (`minmax(160px, 1fr)`).
   * Поддержка тарификации PIN-сертификатов (`CertificatePinModal.tsx`).
   * Code Splitting, фиксированная навигация и стандартизация дизайн-токенов в `MenuBuilder/frontend` (см. `docs/menu_ui-frontend-architecture.md`).
3. **Третий шаг (Следующие задачи):**
   * Интеграция боевого платежного шлюза (эквайринг, вебхуки, 54-ФЗ).
   * Реализация реестров платежей для тенантов и административных сервисов контроля оплат.
