Уточнение целевой архитектуры к уже известному контексту:
проект etranprocessing.
БД etranprocessing - уже есть на сервере.
Обязательно улучшить архитектуру, не копировать тупо из исходного легаси проекта.
Контейнеризация приложения обязательна, используем docker compose.
Процессы и описание флоу в системе:
терминалы как https клиенты обращаются к АПИ через уже настроенный nginx (его не трогаем).
nginx терминирует TLS, передает в бекенд поля из сертификата (сейчас можно избыточно передавать) - это уже настроено для некоторых сервисов в nginx-mutual.
бекенд на любой входящий запрос содержит depends (middleware) для проверки CN (=SN) и серийника сертификата по базе данных, тем самым получая привязку к тенантности (Org) для случаев, если функция запроса требует проверки дополнительного статуса Org (активен, заморожен, блокирован).
отношение Org к терминалам как 1:M, терминал может принадлежать только 1 Org.
licensebilling - биллинг лицензии должен проверять дату в БД, где должна быть дата истечения лицензии по данному терминалу и статус Org.
GateGauge -это техническая информация в легаси формате - ее нужно укладывать в отдельную таблицу, где важно время фиксации, device_id (или sn терминала), и тело с информацией, которую нужно предварительно распарсить - преарвтить в JSON (аккуратно с применением fallback в связи с легаси форматом) и хранить в поле JSONB; при этом, не нужно хранить всю историю этих сообщений, а нужно сделать кольцевой буфер на 24 записи по каждому терминалу.
TechGate - аналогично GateGauge, НО хранить ВСЕ сообщения, не удалять историю.
