### Анализ реальной выдачи API по устройству 6209

Предоставленный JSON-ответ идеально иллюстрирует работу новой подсистемы защиты:
- Зафиксирован инцидент безопасности `SN_COLLISION` (попытка работы двух устройств с разными сертификатами под одним `SN`).
- Устройство автоматически заблокировано (`is_blocked: true`, `last_checked_result: false`, `conn_name: null`).
- Структурированные детали инцидента выведены в `violation_details` (зафиксировано 30 попыток циклического переподключения, приведены оба конфликтующих сертификата и оба IP-адреса).
- В `recent_audit_events` сохранён первичный снимок события с меткой `actor: "system/detector"`.

На основе анализа этой структуры сформирован список рекомендаций и дополнений для документации API (`docs/api-device-connection-and-audit-guide.md`).

### Что рекомендуется добавить и скорректировать в документации API

#### 1. Детализация схемы объекта `violation_details`
В текущей документации `violation_details` описан обобщённо как `object | null`. Потребителям API (фронтенд, интеграции, системы мониторинга) необходима детальная спецификация вложенных полей:

| Поле | Тип | Описание | Пример |
|---|---|---|---|
| `violation_type` | `str` | Тип нарушения: `SN_COLLISION` или `DEVICE_CLONE` | `"SN_COLLISION"` |
| `reason` | `str` | Человекочитаемое описание причины инцидента | `"Multiple conflicting TLS certificates active for the same SN"` |
| `detected_at` | `datetime (ISO 8601)` | Время первого обнаружения инцидента и срабатывания блокировки | `"2026-08-30T09:56:11.931003+00:00"` |
| `flapping_count` | `int` | Суммарное количество зафиксированных попыток переподключения/коллизий | `30` |
| `cert_validities` | `list[str]` | Список сроков действия конфликтующих сертификатов | `["2026-06-02T12:34:07Z - 2027-06-02T12:34:07Z", "2026-08-07T06:42:22Z - 2027-08-07T06:42:22Z"]` |
| `conflicting_hosts` | `list[str]` | Список конфликтующих IP-адресов/хостов источников | `["{0,0,0,0,0,65535,21485,65262}", "{0,0,0,0,0,65535,23538,54545}"]` |

---

#### 2. Документирование формата Erlang-кортежей для IP-адресов (`peer_host` / `conflicting_hosts`)
В выдаче адреса представлены в формате Erlang IPv4-mapped IPv6 кортежей: `"{0,0,0,0,0,65535,21485,65262}"`.

В документации для потребителей API важно отразить:
- **Почему такой формат**: Брокер RabbitMQ и плагин `rabbitmq_mqtt` передают сырые сетевые типы Erlang.
- **Как расшифровывать IP**:
  - Первые 5 нулей и `65535` (`0xFFFF`) обозначают префикс IPv4-mapped IPv6.
  - Последние два числа — шестнадцатеричные пары байт IPv4 (например, `21485` $\to$ `0x53ED` $\to$ `83.237`, `65262` $\to$ `0xFEE6` $\to$ `254.238` $\to$ `83.237.254.238`).
- **Где взять готовый строковый IP**: В поле `details.name` всегда присутствует готовая строка с публичным IP и портом: `"83.237.254.238:53420 -> 172.18.0.2:8883"`.

#### 3. Детализация схемы элементов массива `recent_audit_events`
Описать полную схему событий в журнале аудита:

| Поле | Тип | Описание |
|---|---|---|
| `id` | `int` | Уникальный глобальный идентификатор записи аудита в `tb_device_audit_logs` |
| `device_id` | `int` | Идентификатор устройства |

| `details` | `object \| null` | Снимок контекстных данных события (параметры коллизии или метаданные провиженинга) |
| `created_at` | `datetime (ISO 8601)` | Метка времени фиксации события в UTC |

#### 4. Поведение полей состояния при активной блокировке (`is_blocked = true`)
Для разработчиков клиентских приложений и UI полезно зафиксировать инварианты состояния при блокировке:

1. `last_checked_result` всегда становится `false`, так как активный сокет принудительно разрывается, а новые попытки подключения отклоняются на уровне брокера.
2. `details.conn_name` переходит в `null` (активного сокета нет).
3. `is_app_available` и `is_svc_available` при `is_blocked = true` гарантированно возвращают `false` (или `null`, если LWT не поддерживается устройством).
4. `checked_at` обновляется при каждой новой попытке заблокированного устройства постучаться на брокер (инкрементируя `flapping_count` в `violation_details`), при этом повторные записи в аудит-лог `recent_audit_events` не спамятся (идемпотентность).
