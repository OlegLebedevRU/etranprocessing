# Эксплуатация платформы Etran, IoT и терминальных агентов

**Срез на 24 ноября 2026 года.** Руководство связывает публичные входы, владельцев состояния, параметры конфигурации и выпуск. Для действующего релиза записывают отдельно Git SHA, digest образа, состав Compose overlays, версию прошивки или Windows-пакета. Версия примера конфигурации сама по себе не подтверждает настройку узла.

## Куда идёт запрос

| Вход | Маршрут и граница доверия | Где искать результат |

## JWT, refresh и допуск в консоль

1. MenuBuilder устанавливает пользовательский контекст и вызывает отдельный процесс `app.jwt_signer:app` в приватной сети. Запрос к `POST /etranprocessing/jwt` подписан HMAC-SHA256 по timestamp, nonce и точным байтам requestBody. У signer собственные `JWT_ISSUER_INTERNAL_SECRET`, `JWT_ISSUER_CLIENT_ID`, `JWT_ISSUER_AUD`, `JWT_ISSUER_ISS`, `JWT_ISSUER_KID`; backend знает тот же контекст и `JWT_ISSUER_INTERNAL_URL`.
2. Signer подписывает access token RS256, возвращает непрозрачный refresh token, ограничивает TTL и проверяет повтор nonce. Окно свежести по умолчанию 120 секунд, допустимое опережение 30 секунд. Кэш повтора локальный; для этого контракта нужен один worker. При рестарте кэш теряется. Сверять часы при отказах свежести. Хранение, ротацию и отзыв refresh-сессий ведёт MenuBuilder.
3. Nginx проверяет cookie `accessToken` на защищённых location. MenuBuilder проверяет прикладную идентичность и допуск канала; WS ограничен сроком JWT. У API-токенов и login есть отдельные location. Список путей и извлекаемых claims сверяют с действующей конфигурацией ingress. `org_id` нормализуется на auth-границе перед SQL.
4. Закрытый RSA-ключ подключается только signer read-only; публичный ключ получают backend и nginx. Сверять `JWT_PUBLIC_KEY` с встроенным ключом и обеими конфигурациями ingress. Для overlay используются `JWT_SIGNER_PRIVATE_KEY_HOST_FILE`, `JWT_SIGNER_ENV_FILE` и `MENUBUILDER_BACKEND_IMAGE`. Резерв через `JWT_ISSUER_FALLBACK_ENABLED` имеет собственный секрет. Его готовность требует проверки подписи тем же публичным ключом.
5. При смене ключа согласовать issuer, kid, все verifier и порядок обновления; проверить login, refresh, смену арендатора, logout, отказ старому токену и переподключение вкладки. При штатном выпуске signer и backend обновляются согласованно. При адресном выпуске одного контейнера сверить отдельно ревизии и совместимость signer. Для диагностики доступен внутренний `GET /health`.

**Обычная последовательность серверного релиза**

1. Принять PR, записать полный SHA основной ветки. Для нового межсервисного формата сначала выпустить совместимого потребителя, затем производителя и UI. Проверить исходную ревизию и совместимость схемы БД.
2. На builder вызвать установленный launcher от `github-runner`. Например, `sudo -n -u github-runner -H python3 /opt/etran-beta/launcher.py --component menubuilder-backend --build-only`. Опция build-only заканчивает работу на артефакте. Проверить поля component, revision и digest. При другой ревизии в manifest выяснить, какой main забрал launcher.
3. Применить адресный deploy по утверждённому сценарию компонента. Для существующих production overrides поддерживается [проверяемый адресный helper](../deploy/processing_fm_release.py). При изменении signer применять совместный сценарий из его runbook. Инструменты builder обновляются установочным пакетом проекта.
4. Проверить непосредственно запущенный revision, HTTP health, отсутствие очереди повторных ошибок и один пользовательский сценарий. Сохранить время, SHA, digest и результат rollback/приёмки в журнале выпуска. Простой git push документации не запускает ручной production launcher.

## Первичная диагностика дежурного

| Наблюдение | Последовательность |
|---|---|
| 401 на входе, после refresh или при открытии вкладки | Уточнить location и стадию отказа. Проверить время, signer health, kid, public key, JWT audience/issuer и наличие подходящей refresh-сессии. Для 403 проверить роль, организацию и конкретную аренду. |
| Вкладка открылась, данные устарели | Проверить Upgrade и срок JWT, открытие логической подписки, consumer/backlog временной очереди и часы участников HMAC. Для инцидентов и заказов проверить commit производителя, LISTEN и повторное чтение после reconnect. |
| Камера видна по MAC, но нет кадра | Разделить физику port-2, HTTP камеры, авторизацию OpenIPC, наличие RTSP-видеодорожки и Janus. Проверить настройку домена и фазу старта после подачи питания. Однократное аппаратное восстановление допускается политикой платы. |
| Видео есть, ввод или консоль не работают | Проверить владельца, scope и TTL аренды, capability агента и ACK. Для консоли проверить отдельный допуск и diagnostics WS. При повторной попытке ввода учитывать риск повторного действия. |
| Оплата завершена у провайдера, UI показывает pending | Проверить сверку webhook/worker и commit статуса, затем организацию подписки и обновление экрана. Повторное создание платежа не является способом обновить экран. |
| Рост нагрузки | Снять одинаковые окна с числом зрителей, GET состояния/качества, AMQP publish/deliver, backlog, SQL и временем владения соединением. Отделить старт и STOP от стабильной фазы. Для 773 использовать +10…+55 секунд от аренды успешно запущенного потока с непрерывным просмотром. |

В выпуске 24 ноября три backend ответили HTTP 200, frontend прошёл сверку с nginx; оператор подтвердил видео и экраны. Короткий прогон рабочего стола длился 13 секунд с одним начальным GET качества. Предыдущая база — 10 GET за 45 секунд. Для оценки изменения нагрузки БД и процента экономии нужны сопоставимые окна. Подробности и границы замера — в [журнале приёмки](etran_arch-portal-tab-signaling-review.md).

## Проверки на узле без вывода секретов

Следующие команды читают состояние. Имена контейнеров и разрешённый SSH-профиль берут из принятого runbook площадки. Сравнивать показатели следует с одним и тем же интервалом наблюдения.

```sh
sudo -n docker inspect --format '{{.Name}} {{.State.Status}} {{index .Config.Labels "org.opencontainers.image.revision"}}' app1 menubuilder-backend processing-backend
sudo -n docker exec rabbitmq rabbitmqctl list_queues name consumers messages_ready messages_unacknowledged
sudo -n docker exec nginx-default nginx -t
```

- **Сертификат на диске.** `openssl x509 -in "$PUBLIC_CERT_FILE" -noout -subject -issuer -serial -dates -fingerprint -sha256` показывает только публичные атрибуты. Сопоставить с сертификатом, предъявленным клиенту. Для mTLS отдельно подтвердить приложение и ACL штатным запросом от терминала.
- **Ошибки после выпуска.** Ограничить временной интервал журнала моментом переключения. Разделить ожидаемое ожидание готовности при старте и повторные ошибки после readiness. В выгрузке оставлять время, тип события и код ответа; query string и заголовки могут содержать идентификаторы сессий и секреты.
- **Резервирование и восстановление.** Для восстановления PostgreSQL нужны резервная копия и совместимые версии схем обоих владельцев. Для восстановления доверия отдельно нужны защищённые материалы signer/CA, конфигурация TLS и ACL брокера. Снимок образа этих данных не содержит. После восстановления проверяют вход и refresh, клиентский mTLS, один RPC и возврат подписки после reconnect. Периодичность резервирования, сроки хранения и дата последнего проверенного восстановления устанавливаются площадкой; текущий документ их не подтверждает.

## Инцидентный срез 24 ноября 2026 года

**MQTT CONNECT.** За 24 часа до 09:08:13 UTC шесть терминальных SN дали 31 587 записей об отказе проверки учётных данных; за последний час — 1 367. Каждый из шести SN отсутствовал в списке пользователей RabbitMQ. В Etran все шесть терминалов активны, у пяти флаг iot_provisioned снят, у одного установлен. В инвентаре app1 найдены четыре из шести, в журнале операций tb_device_provisionings по этим SN записей нет. Отсутствие записи операции не исключает старого или ручного способа создания. Ещё два отказа за сутки относились к существующей служебной учётной записи подписчика портала; за последний час у неё отказов не было. Несовпадение MQTT client ID с сертификатом учитывается отдельно. Адресный список SN передан оператору; этот релиз не изменял устройства, права и provisioning.

**Терминальный ingress.** До изменения в контрольном часовом окне nginx записал 545 таймаутов подзапросов legacy mirror, из них 366 GateGauge, 178 payment/etran и один TechGate. 24 ноября в 09:11:36 UTC применён конфиг из PR 171 с reload только терминального nginx. Отключены фоновые копии для /payment/, /payment/etran.ashx, /GateGauge/main.ashx и /techgate/etran.ashx. Основные proxy_pass ведут в ProcessingBackend, обычный fallback остальных legacy-маршрутов сохранён. Старое внутреннее пространство /_mirror_ возвращает 404. При необходимости отката вернуть предыдущий конфиг на тот же bind mount, выполнить nginx -t и адресный reload.

Хеши файла на хосте и в контейнере сверены. В действующей конфигурации ноль директив mirror. С 09:11:36 по 09:12:57 UTC зарегистрированы четыре основных запроса Payment и два GateGauge, все с HTTP 200; новых ошибок зеркальных подзапросов за этот интервал не было. HTTP-ответ здесь подтверждает работу маршрута. Финансовые исходы транзакций этим замером не проверялись.

**Оставшиеся наблюдения.** Отдельного разбора требуют попытки с несовпадающим MQTT client ID, нулевые по байтам TCP-сессии на media ingress и чтения качества после команд адаптации рабочего стола. В текущем выпуске менялся только терминальный ingress. RabbitMQ после reload имел одного portal-watch consumer и пустую очередь в момент проверки.
