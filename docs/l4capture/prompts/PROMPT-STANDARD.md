# Обязательный стандарт выполнения промптов каскада L4Capture

**Версия стандарта:** `1.1.0` (2026-09-23: релизное исключение L4C-11 и юридические вопросы вне каскада)

Этот документ является обязательной нормативной частью каждого промпта каскада L4Capture. Архитектурный источник требований: `../l4capture_arch_final.md`. Единственный нормативный источник межагентной передачи фактически принятых контрактов: `contract-handoff.md` в текущем каталоге.

---

## 1. Непереговорные правила

1. **Строгое разделение каталогов:**
   - **Документация, промпты, контроллер каскада и handoff-журнал:** `docs\l4capture\` (`docs/l4capture/prompts`, `docs/l4capture/handoffs`, `docs/l4capture/contracts`).
   - **Код, скрипты сборки, тесты и результаты работы:** `tools\l4capture\`; для полной поставки L4C-11 действует узкое исключение п. 3.
2. **Строгий запрет `l4desk-service`:**
   - **Категорически запрещено использовать `l4desk-service` для размещения файлов проекта `l4capture`.**
   - Проект `l4capture` полностью автономен от сервиса L4Desk.
3. **Один запуск — один scope:**
   - Для шагов L4C-01..04, L4C-07..10 разрешённый scope реализации — строго `tools/l4capture`.
   - Для шага L4C-05 (адаптер) разрешённый scope — `tools/l4desk` + `tools/l4capture`.
   - Для шага L4C-06 (M-1 верификация) — подготовка evidence в `tools/l4capture` и чтение штатных статусов.
   - Для L4C-11 основной scope — `tools/l4capture` плюс закрытый релизный allowlist [L4C-11-RELEASE-PACKAGE §2](L4C-11-RELEASE-PACKAGE.md): существующие build/staging/installer, минимальная интеграция адаптера, publisher, метаданные и документация полного tools suite 1.8.0. Это не разрешение изменять произвольный код tools или серверы.
4. **Контрактный допуск (Contract Gate):**
   - Межпроектный контракт существует для агента только тогда, когда в `docs/l4capture/prompts/contract-handoff.md` имеется ровно один завершённый блок требуемого `handoff_id` со статусом `ACCEPTED`.
   - Для первого шага `L4C-01-FRAMEWORK` входных handoff нет; проверяется статус журнала `READY_FOR_L4C_01`.
5. **Формат передачи DETACHED_V1:**
   - Все шаги каскада L4Capture используют раздельный формат передачи `DETACHED_V1`:
     - Отчёт размещается в `docs/l4capture/handoffs/<PROMPT_ID>-report.md`.
     - Окончательный candidate-блок размещается в `docs/l4capture/handoffs/<PROMPT_ID>-candidate.md`.
     - Candidate включает путь к отчёту в `artifact_paths` и контрольную сумму SHA-256 зафиксированных байтов отчёта (разрыв циклической зависимости digest).
6. **Milestone M-1 Gate (L4C-06):**
   - Веха M-1 требует не только технического прохождения тестов, но и обязательного личного подтверждения владельца («НОРМ»). Без явного согласия владельца каскад останавливается.
7. **Инварианты C-кода и сборки:**
   - Собственный код пишется на чистом C (C99/C11 MSVC).
   - Статическая компоновка `/MT` (без внешних зависимостей и VC Redistributables).
   - Поддержка Windows 7 SP1 x86/x64 — обязательный базовый путь (GDI + OpenH264).
   - Запрет неконтролируемых очередей и зависаний: deadline-контроль ≤500 мс при stop/lease expiry.
8. **Юридические вопросы вне каскада:**
   - По решению владельца от 2026-09-23 юридическое заключение/патентный допуск не является gate сборки, приёмки или публикации. Не заявлять юридическое одобрение как результат технических проверок.
   - Лицензии/уведомления в поставке, SBOM, SHA-256 и supply-chain проверки сохраняются. Технические gaps не снимаются этим исключением.
9. **Финальный релиз:**
   - L4C-11 требует полный tools suite 1.8.0, фактическую публикацию в реестр, проверку скачанных байтов и установки, а не только локальную сборку l4capture. Production rollout не входит в шаг.
   - Предыдущий `ACCEPTED` не заменяет отсутствующее runtime-evidence: обязательные незакрытые проверки должны быть подтверждены перед выпуском.

## 2. Порядок выполнения задачи агентом (Agent Workflow)

### Шаг 1. Contract Gate
1. Открыть `docs/l4capture/prompts/contract-handoff.md`.
2. Проверить наличие `required_handoff_id` со статусом `ACCEPTED`.
3. Сверить контрольные суммы и версии входных артефактов. При несовпадении или отсутствии входа — вернуть `BLOCKED_CONTRACT`.

### Шаг 2. Разработка и локальные проверки
1. Работать только внутри назначенного `scope_project` и явно разрешённого исключения соответствующего шага (для L4C-11 — его §2).
2. Для исправлений — сначала падающий тест, затем фикс.
3. Провести сборку (`build.cmd` x86 и x64), запустить тесты (`tests/`), проверить отсутствие сторонних DLL-зависимостей (`dumpbin /dependents` и `/imports`). Для L4C-11 дополнительно обязательны полная сборка suite и release gate G1–G11 его промпта.
4. Все проверки должны быть успешными (0 errors, 0 failures).

### Шаг 3. Оформление отчёта и candidate
1. Создать отчёт `docs/l4capture/handoffs/<PROMPT_ID>-report.md`.
2. Зафиксировать в отчёте: scope, перечень изменённых файлов, коммиты, результаты тестов, evidence.
3. Вычислить SHA-256 реальных байтов отчёта.
4. Создать `docs/l4capture/handoffs/<PROMPT_ID>-candidate.md` со всеми полями канонического формата YAML и SHA-256 отчёта в `artifact_sha256`.

## 3. Допустимые финальные статусы

- `ACCEPTED` — все обязательные проверки, тесты и артефакты подготовлены и соответствуют требованиям.
- `BLOCKED_CONTRACT` — входной контракт отсутствует, не принят контроллером или повреждён.
- `BLOCKED_TESTS` — сбой сборки или падение тестов.
- `BLOCKED_SCOPE` — требуемое изменение выходит за рамки разрешённого каталога.
- `REJECTED` — решение нарушает архитектурные ограничения или безопасность.
