## 1. Цель и архитектурная миссия

Ты выступаешь в роли **Ведущего системного инженера адаптивного видеоконвейера и контроллеров качества (L4Capture-ProfilesDegrade-Agent)** в рамках комплекса `tools suite`.

Твоя задача — реализовать в целевой директории `tools\l4capture\` полную шкалу профилей качества **540p / 720p** и **алгоритм монотонной деградации** при перегрузке согласно §7 архитектуры, без добавления нового UI-профиля и без нарушения safety-политики удалённого ввода.

### Архитектурный контекст и системная ценность

Ожидаемый вход шага — принятый после M-1 тракт **base_480p**, DXGI (L4C-07) и MFT с fallback на OpenH264 (L4C-08). До реализации подтвердить это по Contract Gate и коду: запись в журнале сама по себе не доказывает работоспособность hardware на текущем стенде. Базовые latest-frame, bounded queues и safety/watchdog уже обязательны; L4C-09 добавляет профили и управляемое снижение качества, а не откладывает защиту от перегрузки до этого шага.

Для платёжных терминалов самообслуживания это означает два системных риска:
1. **Недостаточная чёткость** при наблюдении оператором (`default` должен уметь отдавать `1280×720`, а не всегда 480p);
2. **Неконтролируемая деградация** при пиковой загрузке: рост encode p95, drops, задержки UI платёжного приложения и невозможность честно остановить поток без «лечения» бесконечными drop-циклями.

Реализация **L4C-09-PROFILES-DEGRADE** закрывает оба риска:
- Вводятся внутренние профили `premium_540p` и `premium_720p` (540p — **только внутренняя ступень**, в UI не выводится);
- Включается детектор перегрузки и **лестница деградации** `сброс опоздавших raw → FPS 15→10 → растр 720→540→480`;
- Смена растра/кодера сопровождается очисткой pending raw/AU и **первым IDR + SPS/PPS**; D0 и pacing-only D1 не требуют переинициализации кодера (§4.2.3);
- Повышение качества **в текущей сессии запрещено** (анти-осцилляция);
- Политика ввода сохраняется: **автодеградация `default` до 480p НЕ даёт права ввода**.

   - Автодеградация `default → 480p` **не включает** ввод.
   - При неизвестном фактическом профиле или геометрии ввод запрещён.

## 4. Архитектурные требования и техническая спецификация

Реализуй подсистему профилей и контроллер деградации в строгом соответствии с §7 архитектуры и существующими C-контрактами (`types.h`, `encoder_backend.h`, `capture_backend.h`, `ipc_protocol.h`).

### 4.1. Модель профилей качества (`include/l4capture/video_profile.h`)

Добавь `video_profile.h` и `src/pipeline/video_profile.c`, переиспользуя существующие типы. Здесь задаётся **поведение**, а не новый wire ABI:

- Раздели неизменяемый `requested` (`low`/`default`), подтверждённый `actual` (480p/540p/720p), действующий FPS и стадию контроллера. Не вычисляй requested из actual.
- Таблица параметров содержит ID, видимые width/height, номинальный FPS (480p — 10, premium — 15), floor FPS (10), min/target/max bitrate. Действующий FPS хранится отдельно: получение параметров 540p не должно вернуть конвейер с 10 на 15 FPS.
- Если используется поле `input_allowed`, оно означает только **пригодность профиля**, не разрешение ввода. Весь gate принадлежит агенту `l4desk` (§4.3).
- Lookup (например, `l4c_profile_params`) возвращает явную ошибку/`NULL` для неизвестного ID; парсер отклоняет неизвестный requested, не приводит его к `low`. До успешного init actual не считается подтверждённым.
- Чистый helper пары профилей (например, `l4c_profile_input_gate_allows`) допустим для проверки контракта: true только для (`low`, `base_480p`), false для неизвестных значений. Он не заменяет внешний input-gate и не добавляет обработку ввода в `l4capture`.

**Матрица старта (политика выбора, не обещание hardware):**

| Запрос / платформа | Стартовый actual / FPS |
|---|---|
| `low`, любая поддержанная ОС | 480p / 10 |
| `default`, Win7 | 480p / 10, ввод запрещён |
| `default`, Win8+, проверенная конфигурация MFT 720p | 720p / 15 |
| `default`, Win8+, OpenH264 с проверенной конфигурацией 720p | 720p / 10 |
| `default`, Win8+, 720p не поддержан проверкой конфигурации | 480p / 10 при успешном базовом init; иначе диагностированный отказ |

540p не выбирается на старте. GDI или отсутствие MFT на новой ОС **не означают Win7** и сами по себе не запрещают 720p на OpenH264. Проверяется реальный init/media type/SPS в принятом startup-бюджете, не название GPU. Причина ограничения старта фиксируется локально с существующим error mapping, без выдуманного wire enum. Автоматически повышать качество после старта нельзя.

#### 4.1.1. Канонические параметры профилей (§7.1) — обязательная таблица

| Профиль | Видимый растр | FPS | min / target / max, кбит/с H.264 | `input_allowed` | Назначение |
|---|---|---:|---:|---|---|
| `base_480p` | `854×480` | 10 | 500 / 500 / 700 | **true** | `low`, Win7, единственный профиль для ввода |
| `premium_540p` | `960×540` | 10–15 | 600 / 700 / 900 | false | **Только внутренняя ступень** |
| `premium_720p` | `1280×720` | 10–15 | 600 / 800 / 1000 | false | `default`, наблюдение |

Инварианты:
- `low` **никогда** не повышается автоматически.
- `default` задаёт **верхнюю границу** качества, не обещание аппаратного ускорения.

- Видимый растр кодируется без crop/letterbox (stretch-fit, §5.2); macroblock padding не меняет видимые 854 / 960 / 1280 пикселей — cropping проверяется по SPS.

### 4.2. Контроллер деградации (`include/l4capture/degrade_controller.h`, `src/pipeline/degrade_controller.c`)

#### 4.2.1. Детектор перегрузки и единицы измерения

Контроллер получает монотонное время и снимок метрик через тестируемый C-интерфейс, без прямой зависимости от Win32/MFT/IPC. Его решение — одно действие либо отсутствие действия; применение остаётся обязанностью pipeline.

1. Окна — **неперекрывающиеся полные интервалы по 3000 мс** одной активной конфигурации. Первый интервал начинается после её активации. Окно `[t, t+3000)` закрывается при достижении правой границы; данные на границе относятся к следующему окну. Неполные/пропущенные интервалы нельзя превращать в несколько синтетических bad-окон.
2. Для каждого класса `drop_fraction = dropped / (passed + dropped)` по завершённым исходам стадии в этом окне. Один исход считается ровно один раз внутри своего класса; классы **не суммируются**:
   - raw: `passed` — передан на encode, `dropped` — отброшен до encode из-за опоздания/замены latest-frame;
   - encoder: `passed` — готовый AU, `dropped` — завершённый encode без AU (frame skip/восстановимый сброс); `NEED_MORE_INPUT` и ожидание асинхронного результата не являются drop;
   - transport: единица — **AU**, `passed` — отправлен целиком, `dropped` — сорвана отправка AU, даже если часть RTP уже ушла. Пакеты и FU-A фрагменты не становятся отдельными drops.
3. Плановый переход 15→10 FPS не создаёт пять «потерянных кадров» в секунду. Очистки при смене конфигурации/stop учитываются отдельно от нагрузочных drops. При нулевом знаменателе класс — no-data, не 100% и не деление на ноль. Накопительные счётчики преобразуются в дельты безопасно; reset/смена поколения не создаёт огромный unsigned drop.
4. `processing_p95` = capture→ready-AU, включая ожидание raw/асинхронного MFT; сопоставление по PTS/идентификатору кадра, без wall clock. Это **не** `encode_p95`: обе метрики подписываются отдельно. Для N завершённых кадров p95 — элемент с рангом `ceil(0.95*N)` в упорядоченной выборке; N=0 — no-data. Хранилище ограничено и подготовлено до горячего цикла; переполнение не замалчивается.
5. Bad-окно: хотя бы один валидный класс drops **строго >20%** **или** `processing_p95 > 1000/current_fps` мс. Ровно 20% и ровно интервал — не превышение. Используй точное сравнение/достаточную точность, а не усечение 15 FPS до 66 мс. Причина bad в двух окнах может различаться. No-data относится ко всему окну только при отсутствии всех пригодных измерений; отсутствие одного класса не отменяет bad по другому.
6. Действие разрешается после **двух последовательных bad-окон**. Good/no-data окно разрывает последовательность; отсутствие media-progress контролирует существующий watchdog (3 с), а не бесконечное ожидание статистики. Фатальные ошибки и safety-события не проходят через overload detector.
7. После успешного действия D0..D3 обнули историю детектора, начни новые окна и hold-off **6000 мс от завершения действия**. Нужны два свежих bad-окна после действия; внутри hold-off собираются измерения, **не очередь отложенных действий**. Старые окна, метрики прежнего FPS/растра и поздние callbacks старого поколения не разрешают следующий шаг.

#### 4.2.2. Лестница действий (ровно один шаг за раз, §7.3)

```text
сброс опоздавших raw-кадров → FPS 15→10 → снижение растра 720→540→480
```

| Шаг | Условие применения | Действие | Новое состояние |
|---|---|---|---|
| D0 | Два bad-окна, D0 ещё не выполнен в этой сессии | Однократно сбросить просроченные pending raw и подтвердить latest-frame/deadline policy | `NOMINAL`; отметить D0 выполненным, даже если сбрасывать нечего |
| D1 | После D0 и hold-off снова два bad-окна, FPS == 15 | Throttle pacing: **15 → 10 FPS** (interval 66⅔→100 мс) | `FPS_THROTTLED` |
| D2 | После предыдущего действия и hold-off снова два bad-окна, actual == 720p и FPS == 10 | Смена растра **1280×720 → 960×540**, FPS остаётся 10 | `DEGRADED_540P` |
| D3 | После D2 и hold-off снова два bad-окна, actual == 540p и FPS == 10 | Смена растра **960×540 → 854×480**, FPS остаётся 10 | `DEGRADED_480P` |
| STOP | На 480p после D0 (если старт в 480p) либо D3 (если спуск) — пять последовательных bad-окон, всего **15 секунд** | Закрыть допуск RTP и выполнить terminal stop; `HIGH_LOAD` через существующий mapping ошибки и локальную диагностику | terminal stop, без собственного recovery-цикла |

Внутренний признак выполнения D0/следующее действие отделён от диагностического enum: сохранение `NOMINAL` не должно зациклить D0. Исходный 480p/10 остаётся `NOMINAL` до stop, а не ложно объявляется результатом D3. D0 не выключает latest-frame до первого срабатывания: ограниченная очередь действует с самого старта.

Если стартовали с 10 FPS, D1 пропускается **без фиктивного действия и дополнительного hold-off**: после D0 и двух новых bad-окон на 720p выполняется D2. На исходном 480p нет D1/D2/D3. Отсчёт floor-overload начинается с первого полного bad-окна после D0/D3; первые два окна входят в 15 с, а не добавляются к ним. Good/no-data сбрасывает floor-streak, но не выполненные ступени. STOP/expiry/watchdog не откладываются ради очередного действия или метрик.

Эталон для fake clock, мгновенного применения и непрерывных bad-окон: старт 720p/15 в t=0 → D0 в 6 с → D1 в 12 с → D2 в 18 с → D3 в 24 с → HIGH_LOAD stop в 39 с. Для старта 480p/10: D0 в 6 с → stop в 21 с. В реальном прогоне добавляется измеренное время применения; старые окна не используются повторно.

Обязательные свойства:
1. **Монотонность FPS/растра:** при уменьшении растра FPS **не увеличивается**. Если сессия стартовала с 15 FPS и был D1, на 540p/480p остаётся 10 FPS. Если старт был сразу с 10 FPS — D1 пропускается (нечего снижать).
2. **Анти-осцилляция:** повышение ступени в текущей сессии **запрещено**. Никаких recovery-up по таймеру, по «успокоению» метрик или по request UI.
3. **Один шаг за раз + hold-off 6 с** между D0..D3.
4. **Битрейт — не первое средство:**
   - Отдельный срез `target_bitrate` к min допустим **только** при подтверждённом delivery constraint либо превышении `bitrate_max_kbps`. Измерять произведённый H.264 payload всех готовых AU, включая SPS/PPS, без RTP/RTCP/IP/TLS overhead, по полному скользящему окну **10 с одной конфигурации** (§13.2); transport drops не должны скрывать превышение кодера. IDR burst/пик 1 с записывать отдельно, не принимать за нарушение среднего. `1 кбит/с = 1000 бит/с`.
   - Источник, валидность и свежесть delivery feedback должны быть доказаны; без существующего канала он считается недоступным. Loopback `sendto`/transport drop не доказывают внешнюю полосу.
   - Применение штатного target нового профиля при D2/D3 — не такой срез; ранее уменьшенный target не повышать (ограничить min/target нового профиля). Срез не заменяет D0..D3 и не совмещается с ними в одно действие; при одновременной готовности приоритет у лестницы/STOP.
   - После среза — hold-off 6 с и свежие окна перед следующим управляющим действием. **Отдельный** floor-overload счётчик на 480p при изменении только bitrate не сбрасывается, его полные 3-с окна продолжаются; иначе срез мог бы бесконечно отодвигать STOP. Повторный запрос уже установленного min — no-op, не новый hold-off. При reinit действуют требования §4.2.3, safety/watchdog не приостанавливаются.
5. **Source mapping / геометрия ввода не меняются** при автодеградации растра (одна ступень не инвалидирует `RECT`); смена монитора/поколения геометрии — отдельный safety-путь §5.2.

#### 4.2.3. Смена конфигурации кодера (D2/D3 и init)

Смена — транзакция media-worker с внутренним поколением конфигурации, не новая lease/stream epoch:
1. Приостановить публикацию старой конфигурации; очистить **все** pending raw и **уже закодированные, но не отправленные AU**, корректно освободив их владение. Drain с отправкой старого хвоста запрещён. Поздние результаты MFT старого поколения не отправляются.
2. Проверить размеры, stride/alignment, переполнения и бюджет **до** новых allocations. Сохраняются максимум один обрабатываемый + один ожидающий raw, AU ≤2 МиБ и общий admission-бюджет 128 МиБ, включая временное перекрытие ресурсов. I420 для OpenH264, NV12 для MFT; BT.601 limited, видимый растр и SPS cropping проверяются для всех трёх профилей. Allocation разрешён при bounded init/reconfigure, но не на каждом кадре.
3. Переинициализировать scaler/encoder с новым растром, **текущим**, а не номинальным FPS и допустимым target bitrate. Штатный D2/D3 сохраняет backend. Если MFT реально отказал/не принял конфигурацию, применяется **существующий bounded fallback L4C-08**, без роста FPS/растра и без нового recovery-цикла; ошибка и её причина не маскируются как успешный D2/D3. Неудача fallback — stop.
4. Проверить первый новый AU: актуальные SPS/PPS + настоящий IDR, совместимость `42e01f`, без B-кадров/reorder. До этого не публиковать новый actual как активный и не отправлять P-цепочку. Только при успешном допуске/отправке первого AU зафиксировать actual/state и начало новых окон; в ближайшем `EVENT_METRICS` (≤1 с) сообщить подтверждённую конфигурацию. Не создавать повторный `EVENT_READY`, если принятый контракт разрешает его только на старте.
5. Старт/смена конфигурации не откладываются force-IDR coalescing. Периодический IDR остаётся **не реже 2 с монотонного времени** при любом FPS и frame skip; прежний GOP в кадрах не должен превратить 2 с в 3 с после D1.
6. **SSRC / sequence / timestamp продолжаются** внутри процесса: sequence на каждый реально отправленный RTP-пакет modulo 2^16, timestamp от непрерывного PTS с частотой 90 кГц modulo 2^32. Сброс PTS кодера компенсируется pipeline, не новой RTP-эпохой. Новый процесс выбирает новую эпоху по существующему контракту.
7. Stop/EOF/expiry/session loss отменяют переход и закрывают RTP ≤500 мс, даже при зависшем init/encode. Safety не ждёт media locks, status writer и cleanup; запрещены `TerminateThread`/конкурентный cleanup зависшего MFT. Сохраняются watchdog 3 с без progress и существующий Job/supervisor-путь, не новый бесконечный retry. Запись `HIGH_LOAD` best effort не задерживает stop; mapping не должен разрешать автоматический цикл restart после terminal HIGH_LOAD.

**D0 и D1:** D0 меняет только raw policy; не сбрасывает корректные AU и не требует IDR. D1 меняет pacing и, при необходимости, поддержанные настройки FPS/GOP кодера. Если D1 можно применить без переинициализации, не требуй сброса/IDR только ради ступени; если backend требует reinit — все правила транзакции выше обязательны. Любая потеря уже закодированного опорного AU требует восстановления SPS/PPS+IDR по существующему RTP-контракту.

### 4.3. Взаимодействие с политикой ввода (§7.2, §9)

1. Внутри `l4capture` **нет обработчика удалённого ввода** (§1–2 архитектуры). Полное решение остаётся в `tools/l4desk`; чистый helper пары профилей, если нужен, возвращает true **только** для (`low`, `base_480p`) и не является авторизацией.
2. Факт деградации `default → … → 480p` **не** выставляет input-разрешение: requested остаётся `default`.
3. При `video_profile_actual` в неизвестном/некорректном состоянии или неподтверждённой геометрии — ввод **запрещён** (fail-closed).
4. Адаптер (`tools/l4desk`, L4C-05) продолжает проверять requested/actual, desktop, разрешение/lease, epoch и geometry. Этот шаг передаёт только достоверные параметры через принятый IPC mapping. Проверка helper не доказывает работу внешнего gate; нужна интеграционная попытка ввода в обход UI на согласованном стенде. Несовместимость статусов, HIGH_LOAD stop/restart mapping или input-gate — `BLOCKED_SCOPE`, не разрешение менять адаптер.
5. Любая попытка включить ввод при `requested == default` (даже если actual == 480p) — **REJECTED** по safety, фиксируется в тестах.

### 4.4. Диагностика и телеметрия (§8)

В локальную диагностику вывести ключи ниже; в IPC — **только** поддержанную контрактом часть через существующие extension-поля / `EVENT_METRICS`. До реализации составить таблицу «ключ / producer / serializer / consumer / разрешённый тип / IPC или local-only». Не предполагать наличие extension-полей и поддержку строкового enum; новые байты фиксированного payload и переинтерпретация reserved-полей запрещены. Непомещающаяся необязательная телеметрия остаётся local-only (§8 архитектуры); отсутствие обязательного safety mapping блокирует интеграцию.

| Ключ | Значения |
|---|---|
| `video_profile_requested` | `480p` / `720p` (маппинг `low`/`default`) |
| `video_profile_actual` | `480p` / `540p` / `720p` |
| `video_degradation_state` | `NOMINAL`, `FPS_THROTTLED`, `DEGRADED_540P`, `DEGRADED_480P` |
| `video_stream_fps`, `video_stream_bitrate` | FPS — полностью отправленные AU за 1 с; H.264 bitrate — окно 10 с (§4.2.2), до накопления полного окна помечать локально как неполное |
| `video_fallback_reason` | Внутренняя причина `HIGH_LOAD`; прежние `NONE`, `DXGI_ACCESS_LOST`, `MFT_UNAVAILABLE`, `WIN7_LEGACY` не теряются. Wire-код выбирается только по принятому mapping |

Период статуса — 1 с, **не** размер окна детектора. Дополнительно локально фиксировать timestamp/поколение, действие/причину, actual и FPS до/после, raw/encoder/transport числители и знаменатели, processing p95, encode p95, queue depth, возраст AU, окна/hold-off и floor-streak. Логи переходов bounded (5 МБ × 2), без кадров, PIN, ключей и покадрового спама; status writer не блокирует safety/media. Не выдавать inventory за оперативный input-gate.

## 5. Интеграция в конвейер `l4capture`

1. **Разрешение профиля при `CMD_START` (`src/main.c` / `pipeline.c`):**
   - Из payload `CMD_START` берётся `requested profile` (`low`/`default`); fps/gop **выводятся из профиля**, не задаются произвольно (§9.1).
   - Разрешение профиля (например, `l4c_profile_resolve`) выбирает стартовую конфигурацию по §4.1; 540p на старте не выбирается.
   - Encoder/scaler используют параметры профиля и отдельно действующий FPS; actual подтверждается первым валидным AU (§4.2.3). Новые CLI-параметры FPS/GOP/profile и bypass-режим lease не добавляются.
2. **Pacing:**
   - Действующий `target_fps` управляет интервалом (`1000/fps`) с компенсацией дробной части для 15 FPS; integer pacing не должен ускорять поток до `1000/66` FPS.
   - D1 переиспользует существующий pacing-механизм (монотонное время, latest-frame), не вводит второй таймер.
3. **Контроллер деградации** встраивается в media-worker цикл **вне** safety locks; его действия не должны задерживать stop/expiry ≤500 мс.
4. **Input safety:** сохранить requested и достоверность actual/geometry в существующем mapping; внешний input-gate не переносить в media-worker (§4.3).
5. **Телеметрия:** разрешённая часть §4.4 идёт в `EVENT_METRICS`, остальное — local-only.
6. Обнови `build.cmd` / `test.cmd` (новые `video_profile.c`, `degrade_controller.c`, тесты).

### 6.1. Обязательные реальные прогоны и evidence

- Собрать и прогнать **весь** существующий набор `l4capture` для x86/x64, включая IPC/safety, capture/scaler, OpenH264/MFT, RTP и telemetry; не ограничиваться новым файлом. Зафиксировать фактически выполненные команды, архитектуру, counts и exit codes.
- На согласованном изолированном стенде Win8+ выполнить controlled encode delay/forced overload для OpenH264 и хотя бы одного реально работающего hardware MFT; software fallback не засчитывать как hardware-pass. Каждый fault/переход повторить ≥3 раз. Режим инъекции ограничен тестовым harness, не production CLI и не обходом lease.
- Через существующий медиатракт проверить браузер на 720→540→480: свежий движущийся тестовый счётчик, рост `framesDecoded`, видимые размеры после переходов, отсутствие старого backlog/рассинхрона. Синтетическая картинка без платёжных данных; запись рабочего экрана не нужна. Парсинг SPS и успешный `sendto` не заменяют browser decode.
- На том же стенде проверить внешний input-gate в обход UI: default на каждой ступени запрещён; low разрешён только при всех условиях §4.3; неверная lease/epoch/geometry запрещает ввод. Если для этого нужен corrective вне scope — остановиться, не править соседний компонент.
- Win7 SP1 x86/x64: smoke базового GDI + OpenH264 без VC Redistributable с **новыми** бинарниками; default остаётся 480p без ввода. `/imports` не является заменой запуска; расширенная матрица и двухчасовой soak остаются L4C-10.
- Для 100 циклов зафиксировать baseline после прогрева, возврат handle/GDI count, Private Bytes/Working Set/GPU allocations. Память не растёт монотонно; рост Private Bytes >5 МиБ требует расследования и блокирует приёмку (§13.2). На каждом переходе сохранить длительность, метрики, queue depth и stop latency, включая stalled-worker сценарий.

Если обязательный стенд, decoder или fault harness отсутствует, перечислить непроверенные пункты и вернуть `BLOCKED_TESTS`; не объявлять весь шаг завершённым только по unit-тестам. Этот промпт не даёт разрешения на production-деплой или воздействие на общий маршрут.

## 7. Порядок выполнения задачи агентом (Workflow)

### Шаг 1. Contract Gate
1. Выполни **весь §3**; сохрани входные хеши и baseline до пересборки.
2. Подготовь карту точек интеграции и IPC mapping, матрицу доступных стендов/неизвестных контрактов. Неизвестное не считать подтверждённым.

### Шаг 2. Разработка и реализация
1. Сначала подготовь тесты §6 для pure controller/профилей и необходимые fault hooks. Для обнаруженных дефектов существующего поведения — воспроизводящий падающий тест до исправления.
2. Добавь модули `video_profile` и `degrade_controller` внутри назначенного scope, без дублирования принятых типов.
3. Интегрируй матрицу старта, pacing, одношаговый controller и транзакцию reconfigure; сохрани внешний input-gate и safety mapping. Реальные точки интеграции устанавливаются по коду, не по предполагаемому имени `pipeline.c`.
4. Подключи новые модули/тесты к `build.cmd`, `test.cmd` и `tests/test_runner.c`.

### Шаг 3. Локальная компиляция и верификация
1. Из `tools\l4capture` в PowerShell выполни `cmd /c "build.cmd all"`; тесты — через поддержанный синтаксис `test.cmd` **для обеих архитектур** (сверить со скриптом). Все обязательные проверки §6 — PASS, 0 failures, без отключения тестов.
2. Для x86/x64 проверь `dumpbin /dependents` **и** `/imports`, map-файл, отсутствие сторонних runtime DLL и неожиданных Win8+ статических imports. Запусти Win7 smoke §6.1.
3. Выполни все стендовые проверки §6.1; зафиксируй OS/build, CPU/GPU/driver, RAM, source RECT/DPI, backend, browser/version, конфигурацию маршрута без секретов, SHA-256 exe. Отдели fake-clock/unit, локальный real codec и сквозной runtime evidence.
4. Сравни итоговые изменения с исходным Git baseline: затронут только scope шага, чужие правки сохранены. Не запускай проверки Python/frontend для этой tools-задачи.

### Шаг 4. Оформление отчёта и Candidate (DETACHED_V1)
1. Создай отчёт §8 с фактическим статусом и матрицей A1–A13. При блокере — причины, владелец, непройденные проверки, без успешного candidate.
2. Убедись, что `producer_commit` действительно содержит предъявляемые изменения. Существующий HEAD с незакоммиченным кодом нельзя выдавать за commit реализации; запроси отдельное разрешение на фиксацию, если его нет. Не коммить чужие изменения.
3. После окончательной фиксации отчёта вычисли SHA-256 его реальных байтов и всех выходных артефактов. Затем сформируй отдельный candidate, повторно проверь YAML, маркеры, соответствие пар путь/хеш и отсутствие placeholders. После хеширования отчёт не редактировать без пересчёта.
4. Передай report/candidate контроллеру и остановись. Не записывай журнал, не объявляй handoff принятым и не запускай L4C-10 самостоятельно.

## 9. Критерии приёмки и Definition of Done

Шаг считается готовым **только** при выполнении **всех** пунктов:

| № | Критерий | Условие прохода |
|---|---|---|
| A1 | Профили §7.1 | Точная таблица и матрица старта §4.1, fail-closed неизвестных значений; 540p только внутренняя ступень; `low` не повышается |
| A2 | Forced overload | D0→D3 в правильном порядке, D0 однократен; старт 10 FPS/480p корректно пропускает неприменимые действия; детектор/границы/знаменатели доказаны |
| A3 | Монотонность | FPS/растр только снижаются в сессии; при падении растра FPS не растёт |
| A4 | Один шаг + hold-off | Ровно одно действие; ≥6 с и два свежих post-action bad-окна; нет очереди накопленных действий |
| A5 | Анти-осцилляция | Отсутствие upgrade после «успокоения» нагрузки в текущей сессии |
| A6 | Первый IDR | При смене растра/кодера и D1 с reinit: очистка pending, отсечение stale AU, SPS/PPS+IDR; actual не публикуется преждевременно; RTP непрерывен, IDR ≤2 с и browser decode подтверждены |
| A7 | Input gate | Внешняя проверка default (в т.ч. 480p) запрещает ввод; low+480p недостаточно без desktop/lease/epoch/geometry; обработчик ввода не перенесён в l4capture |
| A8 | Stop на 480p | Пять полных последовательных bad-окон после D0/D3 → terminal HIGH_LOAD; good/no-data сбрасывает streak; нет restart-петли |
| A9 | Битрейт | Срез к min только при валидном delivery feedback или превышении max в полном 10-с окне H.264; CPU overload/IDR burst/loopback success не подменяют критерий |
| A10 | Safety/ресурсы | RTP-stop ≤500 мс во время reinit/hang; no grace/drain; Job/lease сохранены, bounded queues/128 МиБ/2 МиБ AU, 100 циклов без утечки |
| A11 | Сборка/тесты/стенды | x86/x64 build и все тесты: 0 errors/failures, `/W4 /WX /MT`; dependents/imports/map, новый Win7 smoke, реальный MFT/OpenH264 и browser evidence; skip не PASS |
| A12 | Scope | Изменены только файлы `tools/l4capture/` + отчёт/candidate в `docs/l4capture/handoffs/` |
| A13 | DETACHED_V1 | Report + candidate с маркерами, реальным commit и SHA-256 всех артефактов; нет placeholders/самохеширования; IPC mapping доказан, wire/UI неизменны |
