## 1. Роль, цель и конечный результат

Ты — **L4Capture-ReleasePackager-Agent**. Выпусти **полный tools suite версии 1.8.0**, включающий готовый `l4capture`, через существующий Zero-Touch pipeline. Недостаточно собрать два `l4capture.exe`, создать отдельный ZIP, обновить строку версии или выполнить dry-run.

Результат:
1. Все собственные поставляемые компоненты suite заново собраны для x86/x64 из зафиксированного релизного исходного состояния; сторонние бинарники взяты из проверенных зафиксированных источников.
2. Единый `tools\dist\l4setup.exe` содержит **оба** ресурса `PAYLOAD_X86` и `PAYLOAD_X64`, выбирает правильную архитектуру и устанавливает полный комплект, включая отдельную папку `l4capture`.
3. Рядом находятся `l4tools-release.json` и `SHA256SUMS`; внутри поставки — лицензии/уведомления, SBOM, руководство, release notes и инструкция отката.
4. Проверены чистая установка, обновление, повторная установка и откат на согласованных стендах; подтверждена техническая матрица архитектуры §13 на финальных артефактах.
5. Три штатных файла реально опубликованы в Generic Artifact Registry под **`l4tools/1.8.0/`**, скачаны обратно и проверены по размерам и SHA-256; скачанный установщик испытан.
6. Подготовлен `DETACHED_V1` для `H-L4C-11-v1`. Приёмку и завершение каскада фиксирует контроллер, не исполнитель.

Публикация в реестр **не означает** production-деплой серверов, массовое обновление терминалов или переключение канала автообновления. Эти действия не входят в задание.

## 3. Pre-flight и Contract Gate

1. Сохрани исходные `git status`, ветку и HEAD. Не переключай ветку поверх чужих изменений. Имя ветки в шапке — целевая ветка после согласования безопасного рабочего состояния.
2. Проверь ровно один завершённый `H-L4C-10-v1: ACCEPTED`, готовность `READY_FOR_L4C_11`, отсутствие уже принятого `H-L4C-11-v1`, принятую M-1 и вердикт владельца «НОРМ». Сверь SHA-256 **реальных байтов всех входных артефактов из актуального блока H-L4C-10-v1**, без нормализации LF/CRLF. Не копируй в новый промпт устаревающие хеши.
3. При отсутствующем/повреждённом входе — `BLOCKED_CONTRACT`. Не переписывай прошлые отчёты/хеши, чтобы пройти gate. Исторические пересобранные бинарники не обязаны совпадать с ранними шагами: происхождение проверяется по принятым снимкам и цепочке контрактов, а вход L4C-10 — до любых пересборок.
4. Составь таблицу открытых технических вопросов по фактическому evidence, не по названиям `contract_kinds`. На момент подготовки промпта `H-L4C-10-v1` принят, **но прямо содержит** незакрытую Win7/Embedded-матрицу, `GAP_FULL_2H` и известный дефект consumer (`plen >= 32` при `EVENT_METRICS` длиной 30 байт). Ранние записи также имеют ограничения hardware/browser-проверок. Сверь актуальность и закрой обязательные проверки перед выпуском; `ACCEPTED` не превращает пропущенный тест в PASS.
5. Проверь MSVC/SDK, assembler и статический OpenH264, Win7 x86/x64 образы без VC Redistributable, стенды GPU/Embedded, место на диске, тестовый маршрут, предыдущий проверенный релиз для отката. Опиши точные версии, CPU/RAM/GPU/драйвер/ОС/DPI/браузер и метод измерений. Отсутствующий обязательный стенд не заменяется проверкой импортов.
6. До финальной сборки согласуй **чистый зафиксированный release source** с владельцем. Нельзя выдавать dirty-код за HEAD, вручную ставить `dirty=false`, коммитить чужие изменения или использовать `--allow-dirty`. Если для фиксации собственных релизных изменений нужен коммит — запроси отдельное разрешение. Генерируемые ресурсы версий также не должны незаметно загрязнять финальный source snapshot.
7. Проверь настройки publisher и доступность версии 1.8.0 без загрузки. Ключи `AR_GENERIC_KEY_ID` / `AR_GENERIC_KEY_SECRET` — только environment или штатный локальный `.env`; не печатать значения и не читать raw secret-файлы в отчёт. Другой реестр или версия требуют решения владельца.

Этот шаг не требует MCP Ops для локальной сборки и публикации в Artifact Registry. Если согласованная диагностика стенда требует MCP Ops, сначала выполнить readiness-протокол проекта; `DEGRADED/UNAVAILABLE` не подменяет технический блокер релиза и допускает разрешённый read-only SSH по штатному runbook. Production-изменения этим не разрешаются.

### 4.1. Не отдельный модуль, а весь suite

Базовый состав обоих payload по текущему staging:

| Каталог установки (обычно `C:\l4tools`) | Содержимое |
|---|---|
| `leo4proxy\` | Соответствующий архитектуре proxy, штатные скрипты и документация. |
| `mosquitto\` | Зафиксированный брокер и необходимые файлы; текущая общая x86-сборка в обоих payload допустима только с явной записью в inventory. |
| `l4con\`, `l4superv\`, `l4pin\`, `l4desk\`, `l4sql\` | Полный существующий набор собственных утилит, не выборочная сборка одного компонента. |
| **`l4capture\`** | Соответствующий архитектуре `l4capture.exe`, `OPENH264_LICENSE.txt`, notices/SBOM и документация; не рядом с чужими exe. |
| `ffmpeg\` | Проверенная поставка FFmpeg для камер и контролируемого ручного отката desktop; лицензии/сведения о происхождении сохраняются. |
| `crt\`, корень установки | Только предусмотренный публичный CA, безопасные шаблоны конфигурации и руководство. Не экспорт ключей/сертификатов конкретного терминала и не рабочее локальное состояние. |

Сверь состав с текущим pipeline: не удаляй существующие обязательные файлы. Не включай в релиз весь произвольный каталог `tools` или незавершённые функции из backlog. В x64 payload не подставляй x86 `l4capture.exe`; в `tools\l4capture\bin\l4capture.exe` остаётся копия x86 по правилам tools.

В поставке не должно быть `.env`, PIN, токенов, приватных ключей/PFX, клиентских сертификатов стенда, логов, записей экрана, тестовых команд, cache/obj или исходного рабочего состояния Mosquitto. Публичный CA не считать секретом; его происхождение и хеш фиксируются отдельно.

### 4.2. Версионирование и происхождение

- `1.8.0` — **версия suite/дистрибутива**. Согласуй `tools\version.txt`, генерируемые заголовки l4setup, PE FileVersion/ProductVersion (`1.8.0.0`/`1.8.0`), CLI-версию, manifest, release notes, registry path и запись аудита.
- Компоненты и зависимости сохраняют собственные достоверные версии; не присваивай всем, включая OpenH264/FFmpeg/Mosquitto, `1.8.0`. В `components` добавь l4capture с реальной версией и происхождением. Не используй старые fallback-значения как доказательство версии.
- Для каждого файла payload зафиксируй относительный путь, архитектуру PE (если применимо), размер и SHA-256. Самоссылочные хеши SBOM/inventory не создавать: их байты фиксируются внешним manifest/evidence после генерации. Для собственных компонентов — source commit и build flags; для зависимостей — версия/tag/commit, источник, digest, локальные патчи. SBOM всего suite должен включать статически встроенный OpenH264 и сторонние поставляемые бинарники, а не только новый exe.
- Проверь актуальные security advisories; не обновляй зависимость молча. Смена OpenH264 требует новой проверки C API, `/MT`, encoder-only map/символов, SPS/IDR/декодирования и Win7. Юридическое исключение не отменяет supply-chain проверок.
- Authenticode фиксируй по факту: не заявляй подпись, если её нет. Используй действующую политику suite; не вводи новое юридическое условие подписания. Если подпись применяется, окончательные хеши и проверки выполняются **после** подписания.

## 5. Реализация сборки и установки

### 5.1. Сборочный pipeline

1. Воспроизведи пробел текущего packager тестом комплектности: до исправления l4capture не собирается общим `build_dist.cmd`, отсутствует в staging и `components` manifest. Для любого другого исправления — отдельный падающий тест до правки.
2. Добавь `l4capture` к общей последовательности сборки обеих архитектур, затем staging, упаковку payload, сборку единого l4setup и генерацию manifest. Любая ошибка прерывает выпуск; старый exe не используется как fallback успешной сборки.
3. Собственный native-код — C в принятом MSVC-подмножестве, Release `/MT`; для l4capture `/W4 /WX`, статический OpenH264 через C API. Запиши версии compiler/SDK и минимальную ISA. Не добавляй динамические CRT/OpenH264 DLL.
4. Обнови staging и manifest минимально, без нового параллельного упаковщика. Документация, notices и SBOM попадают **в оба payload** до сборки установщика. Сверь реально существующий путь руководства: текущий staging ищет старое имя `docs\terminal-tools-user-guide.md`, авторитетный документ — `docs\term_tool-user-guide.md`; не теряй руководство из-за устаревшего пути.
5. Проверь содержимое **извлечённых ресурсов финального exe**, а не только каталог `.stage`: совпадение хешей payload с manifest, inventory, версии/архитектуры всех компонентов, наличие l4capture/FFmpeg/документации. Проверка одного размера ZIP или существования ресурса недостаточна.
6. Не создавать циклические digest: manifest описывает готовый setup/payload; `SHA256SUMS` — setup и manifest; собственный digest `SHA256SUMS` — в audit/report. Payload SBOM не содержит самоссылочный хеш финального exe.

### 5.2. Установка, обновление, выбор backend и откат

- Добавь изолированный `l4capture\l4capture.exe` в существующую установку и legacy-совместимость, не создавая новый сервис. `l4desk` остаётся единственным владельцем child/Job/IPC; запуск l4capture только в разрешённой интерактивной сессии и по действующей lease.
- Проверь реальное разрешение пути к child из установленного корня, из другого CWD и из разрешённого пользовательского install path; отсутствие зависимости от dev checkout/PATH. Запуск desktop-захвата не требует admin; elevation существующего установщика служб — отдельный неизменённый процесс.
- Финальный пакет должен позволять штатно использовать нативный desktop backend без копирования файлов вручную. Зафиксируй фактическую релизную настройку/feature flag, значения для новой установки и upgrade, правила сохранения явных настроек оператора. Не снимай пилотное ограничение до технических gate, не оставляй единственным результатом неактивный exe без документированного штатного включения.
- Перед заменой бинарников останови активный stream через штатный lifecycle, подтверди завершение child и освобождение ввода. Не отправляй остаточные кадры. Обновление/откат не создаёт lease и не возобновляет захват автоматически.
- Сохраняй identity/SN, сертификаты и private key store, пользовательские конфиги, действующие ACL и существующие службы. Не перезаписывай рабочую конфигурацию шаблоном; не вводи лишние записи PATH/службы/процессы при повторной установке.
- Проверь известную 30-байтную телеметрию на актуальном adapter: offsets/length checks должны читать принятый wire без изменения схем. Исправление только узкого consumer-дефекта с тестами разрешено §2; неизвестная геометрия/профиль по-прежнему запрещают ввод.
- Протестируй чистую установку, upgrade с **фактически выбранной предыдущей опубликованной версии**, повторную установку 1.8.0, занятый/отсутствующий/повреждённый файл, отказ доступа, прерванную установку и неверную архитектуру. Ошибки не должны оставлять частично работоспособную смесь версий или обнулять identity.
- Откат — проверенный возврат прежнего комплекта/конфигурации с подтверждением хешей и работоспособности. Для ручного desktop-отката на FFmpeg сначала остановка старого процесса, затем **новый авторизованный start**; при expiry/lock fallback запрещён. Камеры используют FFmpeg до и после upgrade/rollback.

## 6. Тесты и release gate

Запусти все релевантные native/unit/integration-тесты l4capture, затронутого adapter, packager, installer/legacy installer и publisher, включая downstream проверки поставки всего suite. Новые тесты покрывают положительный состав, отсутствие обязательного файла, неправильную архитектуру/версию, stale binary, несовпадение digest и повторный запуск. Для дефекта сначала доказать падение, затем PASS после исправления. Проверки backend/frontend не запускать, если они не изменялись; их изменение запрещено этим scope.

Каждая строка ниже: `PASS/FAIL/BLOCKED`, точный стенд, команда/сценарий, время UTC, версии/хеши, фактические числа и ссылка на evidence. Пустые поля, отсутствие стенда и `NOT_RUN` не являются PASS. Подтверждённые прежние результаты можно использовать лишь при доказанной применимости к **тем же финальным бинарникам/конфигурации**; пересборка или изменение затронутого пути требует повторной проверки.

## 7. Публикация версии 1.8.0

### 7.1. Штатный формат реестра

Используй существующий publisher, не Docker registry и не копирование на production-хост. По текущей конфигурации:

```text
https://l4tools-generic.ar.cloud.ru/l4tools/1.8.0/l4setup.exe
https://l4tools-generic.ar.cloud.ru/l4tools/1.8.0/SHA256SUMS
https://l4tools-generic.ar.cloud.ru/l4tools/1.8.0/l4tools-release.json
```

URL выше — **целевые адреса**, не доказательство уже существующего релиза. SBOM/notices/руководство должны быть доступны из опубликованного установщика в обоих payload; наличие только локальной копии недостаточно. Не расширяй формат реестра дополнительными файлами без согласования.

### 7.2. Порядок выпуска

Команды выполняются из корня репозитория в PowerShell, **по одной**, с обязательной проверкой exit code перед продолжением. Это опорные команды для исполнителя, не указание выполнить их при подготовке промпта:

```powershell
cmd /c "tools\build_dist.cmd 1.8.0"
uv run python deploy\publish_l4tools.py verify tools\dist
uv run python deploy\publish_l4tools.py check 1.8.0
uv run python deploy\publish_l4tools.py --version 1.8.0 publish tools\dist --dry-run
uv run python deploy\publish_l4tools.py --version 1.8.0 publish tools\dist
```

1. Сборка запускается после исправления pipeline; финальные install/runtime gate выполняются **до** последней команды. Verify/check/dry-run не являются публикацией.
2. Используй явную подкоманду `publish`. **Не используй сокращение `--dist` без подкоманды:** текущий `main()` publisher автоматически включает `allow_dirty` в этом режиме. Запрещены также `--allow-dirty`, `--skip-check`, `-SkipVerifications`, ручная правка manifest/digest и загрузка в обход publisher.
3. `check`: отсутствие версии разрешает дальнейший preflight; существующая версия требует сравнения **всех** файлов. Сетевой сбой, 401/403/5xx или неизвестный результат не равны «версии нет». Сохрани фактические коды и ответы без credentials.
4. Уже опубликованная полностью идентичная 1.8.0 допускает идемпотентное подтверждение без upload. Частичная публикация либо любое отличие — остановка; не удалять/перезаписывать 1.8.0, не менять версию на 1.8.1 самостоятельно. При сбое посреди загрузки фиксировать частичный результат, не выдавать успех.
5. Штатный порядок загрузки: `l4setup.exe`, `SHA256SUMS`, **manifest последним**. Проверь remote digest, затем выполни независимое полное скачивание трёх файлов в новый каталог evidence под `tools\l4capture\`; вычисли SHA-256 реальных скачанных байтов и размеры. HEAD/HTTP 200 без проверки тела не доказывает комплектность. Сам `SHA256SUMS` также сверяется с локальным frozen-файлом.
6. Проверка содержимого и installation smoke скачанного setup — на согласованном тестовом стенде. Нельзя пересобрать/доподписать файл после проверки и опубликовать уже другие байты без повтора hash/runtime gate.
7. Проверь `artifacts\l4tools\1.8.0.json` и append-only запись в `releases.jsonl`: версия, UTC, source commit, точные URLs, размеры/хеши. Предупреждение publisher об ошибке записи аудита нельзя проигнорировать даже при успешном upload. Локальная команда `record` сама по себе не доказательство публикации.
8. Не менять `latest`, каналы обновлений и production-установки. Если сбой обнаружен после upload, зафиксируй `PUBLISHED_BUT_VERIFICATION_FAILED` в отчёте и запроси решение владельца; не маскируй его статусом успешного релиза и не переписывай immutable-артефакты.

- Полную ведомость компонентов/архитектур/версий/размеров/хешей, финальные setup/payload/manifest/SHA256SUMS, SBOM/notices и release notes; путь каждого установленного компонента.
- Матрицу G1–G11 и применимые требования §13 с реальными числами/логами/стендами, без фиктивных PASS; закрытие прежних технических gaps и consumer-телеметрии.
- Проверенную инструкцию установки, upgrade и rollback с выбранной предыдущей версией, сохранением identity/config и явными release settings desktop backend.
- URLs публикации, upload/GET результаты, сравнение downloaded hashes/размеров, протокол установки скачанного exe и запись release audit. Не сохранять credentials или содержимое экрана терминала.
- Явную пометку `legal_review: OUT_OF_SCOPE_BY_OWNER_DECISION` без утверждения «юридически одобрено»; оставшиеся неприёмочные ограничения и отдельный факт отсутствия production-деплоя.

После фиксации отчёта вычисли SHA-256 его **реальных байтов** и всех передаваемых артефактов, затем создай отдельный candidate. Не включай собственный digest отчёта в отчёт и не включай candidate в собственный список хешей.

Candidate использует поля действующего принятого формата, без выдуманных значений и готового шаблона с фиктивным `all_verified`:
- Маркеры вне YAML-блока: `<!-- HANDOFF:H-L4C-11-v1:BEGIN -->` и `<!-- HANDOFF:H-L4C-11-v1:END -->`.
- `handoff_id`, `status`, `contract_kinds`, `producer_prompt_id`, `producer_scope_project`, `producer_report_path`, `producer_branch`, `producer_commit`, `accepted_at_utc`, `contract_version`, `schema_revision`, `artifact_version`.
- `artifact_paths` и соответствующие им `artifact_sha256` (одинаковый порядок и число элементов), `compatibility`, `deployment_status`, `deployed_environment`, `feature_flags`, `contract_payload`, `supersedes`, `known_risks`, `consumers`, `next_prompt_id`.
- `artifact_version: 1.8.0`; версия контракта/схемы не повышается автоматически вслед за продуктом. `next_prompt_id: null`: это последний шаг, не автоматическое начало нового каскада.
- Минимальные артефакты для hashing: отчёт, `tools\dist\l4setup.exe`, `tools\dist\l4tools-release.json`, `tools\dist\SHA256SUMS`, оба payload, x86/x64 l4capture, SBOM/inventory, руководство/откат, результаты проверок и `artifacts\l4tools\1.8.0.json`. Не хешируй весь изменяемый `releases.jsonl` как immutable-артефакт: зафиксируй конкретную запись аудита в отчёте.
- `contract_payload` описывает release version/состав, установочные пути и backend settings, SBOM/notices, проверенные платформы, install/rollback, gate-evidence, registry URLs и downloaded hashes; юридическое исключение и `production_deployed: false` записываются явно.
- Для успешного результата `deployment_status: PUBLISHED_TO_REGISTRY`, среда — фактический Generic Artifact Registry и согласованные тестовые стенды. `LOCAL_TESTS_PASSED` не заменяет успешную публикацию. `accepted_at_utc` в candidate — время заявки исполнителя; окончательную приёмку подтверждает только контроллер.

`ACCEPTED` — только заявка при полностью выполненном DoD. Для остановки используй статус стандарта (`BLOCKED_CONTRACT`, `BLOCKED_TESTS`, `BLOCKED_SCOPE`, `REJECTED`) с точной причиной; недоступность реестра/проверки публикации отражай как `BLOCKED_TESTS` с отдельной причиной `PUBLICATION_UNVERIFIED`. Не формируй заведомо успешный кандидат при частичном выпуске.

Передай report/candidate контроллеру и остановись. **Не редактируй `contract-handoff.md`, не принимай собственный результат, не запускай следующий шаг.**
