# Архитектурный релиз: нативный модуль видеозахвата `tools\l4capture`

**Статус:** Целевая архитектура; рабочая ревизия перед реализацией. Допуск к релизу — только по проверкам ниже.

**Версия документа:** `1.0.0` (ревизия без выпуска новой версии продукта)

**Дата ревизии:** 2026-09-19

**Область действия:** `tools/l4capture`, адаптер `tools/l4desk`; совместимость с `leo4proxy`, `l4media` и MenuBuilder.

**Размещение артефактов проекта:**
- **Целевая папка для промптов проекта `l4capture`, контроллера каскада и документации:** `docs\l4capture` (`docs/l4capture/prompts`, `docs/l4capture/handoffs`, `docs/l4capture/contracts`).
- **Строгий запрет:** Запрещено использовать `l4desk-service` для размещения файлов проекта `l4capture`. Регламенты контроллера каскада, стандарты и журнал передачи контрактов ведутся изолированно внутри `docs\l4capture`.
- **Целевая папка для кода, скриптов, сборок, тестов и других результатов:** `tools\l4capture`.

**Заменяемый компонент:** `ffmpeg.exe` только для desktop-трансляции; камеры остаются на существующем пути.

## 1. Решение и результат ревизии

`l4capture.exe` — дочерний Windows-процесс: захват экрана и курсора → масштабирование → H.264 → локальный RTP/RTCP. Внутри нет MQTT, TLS, WebRTC, авторизации, ввода или самостоятельного восстановления серверной сессии. Агент остаётся владельцем запуска, lease, событий и перезапусков.

Сохраняются: собственный код на C, статический OpenH264, `/MT`, отдельные x86/x64 exe, GDI для Windows 7, DXGI/MFT для новых ОС, три профиля, 11 шагов каскада и обязательное решение владельца на Milestone M-1. Новые сервисы, очереди, сетевые команды и обязательный обратный медиаканал не вводятся.

### Что исправлено в ревизии

| Нестыковка исходной редакции | Решение |
|---|---|
| Loopback назван входом удалённого `l4media`; порт объявлен динамическим | Локальный получатель — `leo4proxy`, затем существующий TLS-туннель; порты берутся из согласованной конфигурации (§2, §10). |
| OpenH264 получает NV12; «чистый C» распространён на чужую библиотеку | OpenH264 получает I420 через публичный C API; его реализация C++/assembler статически связывается (§3, §5). |
| Fallback после UAC противоречит fail-closed | Недоступный desktop/lease всегда останавливает поток; fallback допустим только при доступной сессии (§9). |
| RTCP PLI, телеметрия и Win7 объявлены готовыми без проверки всей цепочки | Разделены подтверждённый локальный код, целевые требования и условия допуска; обязательное восстановление не зависит от PLI. |
| Живая M-1 проверяет главным образом картинку | Введены четыре риска, ранние владельцы мер и воспроизводимые fault-тесты (§12, §14). |
| Гарантии CPU/RAM и патентного освобождения не обоснованы | Производительность измеряется на описанном стенде; лицензирование — отдельный допуск к распространению, не следствие бесплатности. |

Это спецификация будущей реализации, **не отчёт о пройденных тестах или деплое**. Ревизия меняет только этот документ; MQTT-клиент, серверы, предыдущая альфа-редакция и принятые handoff не изменяются.

## 2. Границы компонентов и существующие контракты

```text
MenuBuilder / app1 → существующее управление lease → l4desk (супервизор)
                                                     │ IPC + Job Object
                                                     ▼
 l4capture: GDI/DXGI → курсор → scale → I420/NV12 → OpenH264/MFT → RTP/RTCP
                                                     │ UDP loopback
                                                     ▼
 leo4proxy: локальные RTP 5004 / RTCP 5005 → L4RTP/1 поверх mTLS/TCP
                                                     │
                                                     ▼
                           l4media ingress → Janus → WebRTC → MenuBuilder
```

| Владелец | Ответственность | Не принадлежит ему |
|---|---|---|
| app1 / MenuBuilder | Серверная аренда и доступ, route/mountpoint, просмотр и разрешение ввода | Выбор графического API терминала |
| `l4desk` | Проверка команд/эпохи, локальный deadline, Job, IPC, recovery, блокировка ввода | Кодирование видео и TLS-медиатуннель |
| `l4capture` | Только разрешённый desktop, кодирование, ограниченные буферы, локальная отправка и диагностика | Продление lease по своей инициативе, MQTT, проверка PIN |
| `leo4proxy` / `l4media` | Существующая доставка и маршрутизация медиаданных | Подтверждение, что браузер показывает свежий кадр |

**Инварианты:** один активный desktop-медиапроцесс; неограниченных очередей нет; stop/expiry/session loss сильнее recovery; старый кадр не считается успешным восстановлением; никакой новый fallback не обходит запрет захвата или ввода.

Изменение внешних схем требует отдельного согласования, а не скрытого расширения «инвентаря».

## 3. Платформа, сборка и поставка

| Параметр | Требование и способ доказательства |
|---|---|
| Собственный код | C99/C11 в поддерживаемом MSVC подмножестве, компиляция `.c` как C; Win32/COM через C-интерфейсы. |
| OpenH264 | Статическая сторонняя библиотека C++/assembler, адаптер использует C-ветку `wels/codec_api.h`. Отдельная собственная C++-обёртка не нужна. |
| CRT | `/MT` для всех Release-объектов, включая библиотеку. `/MTd` только для отладки, не для поставки. |
| Артефакты | `bin/x86/l4capture.exe`, `bin/x64/l4capture.exe`, `bin/l4capture.exe` — копия x86 по правилам tools. Один exe на архитектуру плюс лицензии/SBOM в пакете. |
| Win7 | Windows 7 SP1 x86/x64 — обязательная целевая платформа GDI + OpenH264. Версии MSVC, SDK, минимальная ISA и системные обновления фиксируются; `/MT` сам по себе не доказывает совместимость. |
| Новые ОС | Windows 8/8.1/10/11 — DXGI при успешном probe, иначе GDI. Embedded/Server принимаются только по перечисленным протестированным редакциям, не «всем версиям» автоматически. |
| Системные API | Опциональные MF/D3D11/DXGI/DWM загружаются из системного каталога, не из текущей директории. Базовые Win7 API, COM, session notification и криптографический RNG разрешены; список из четырёх DLL не является полным. |
| Проверка бинарника | `dumpbin /dependents` **и** `/imports`, map-файл, запуск на чистой Win7 без VC Redistributable. Отсутствие сторонних runtime DLL проверяется повторно после OpenH264 и MFT. |

Привязка к Job, дескрипторы, безопасные таймеры и ограничения памяти закладываются в L4C-01, а не после появления картинки. Совместимость OpenH264 с выбранным toolchain проверяется в L4C-03 до M-1; при отсутствии Win7-стенда допуск блокируется, а не заменяется предположением по таблице импортов.

## 4. Scope v1

**Включено:** выбранный монитор либо виртуальный desktop; GDI и DXGI; курсор; отрицательные координаты; масштабирование в фиксированный растр; BGRA → I420/NV12; OpenH264 и hardware MFT; RTP Single NAL/FU-A, исходящий RTCP; три профиля и понижение качества; внутренний IPC; безопасный адаптер существующего агента.

**Исключено:** звук, запись, декодер, камеры в `l4capture`, RTSP/RTMP/WebRTC/TLS/MQTT внутри него, другие видеокодеки, обход Secure Desktop, новые серверные API и композитинг нескольких DXGI outputs. Виртуальный desktop захватывается GDI единым прямоугольником; DXGI применяется к одному output. Так поддержка виртуального desktop не требует отдельного GPU-композитора.

FFmpeg сохраняется для камер и контролируемого отката пилота. Автоматическое переключение между FFmpeg и `l4capture` в текущей сессии по умолчанию **выключено**: старый путь ещё не доказывает новые размеры/тайминги безопасности. Ручной откат — только после остановки старого процесса и нового авторизованного старта. Ни один откат не разрешён при невалидной lease или недоступной сессии.

## 5. Подсистемы и внутренние контракты

### 5.1. Захват, буферы и ошибки

Абстракции `ICaptureBackend` и `IEncoderBackend` сохраняются как небольшие C-таблицы функций. Точные заголовки фиксирует L4C-01; неоднозначные `bool` и указатель без длины не служат контрактом.

| Граница | Обязательные данные и владение |
|---|---|
| Захват → pipeline | `FrameView`: BGRA top-down, width/height, положительный stride, длина буфера, исходный физический `RECT`, монотонный PTS, поколение геометрии. Память захвата действительна до `release_frame`; постановка в очередь требует собственного слота. |
| Pipeline → encoder | Формат I420 либо NV12, плоскости/stride/размеры, видимые чётные width/height, PTS и запрос IDR. Только поддержанный `init` формат; скрытая конвертация NV12→I420 в каждом encode запрещена. |
| Encoder → RTP | Полный access unit (AU), PTS, признак IDR и список NAL с длинами; срок жизни до возврата callback либо явное копирование в ограниченный слот. Граница AU нужна для RTP marker. |
| Результаты | Раздельно: готово, кадр ещё не готов, восстановимая ошибка устройства, недоступная сессия, фатальная ошибка. `NO_FRAME`/DXGI timeout не являются падением или разрешением повторять старое изображение после lock. |

GDI переиспользует `CreateDIBSection`/DC; на каждом кадре нет перевыделений. DXGI staging/readback в CPU-память учитывается в бюджете: наличие Desktop Duplication **не означает zero-copy**. Полученный DXGI frame обязательно освобождается, включая ветки ошибки; rotation output учитывается до масштабирования.

При `DXGI_ERROR_ACCESS_LOST` сначала проверяется доступность пользовательской сессии. Если она недоступна — terminal stop. Если доступна — не более трёх попыток reinit с паузами 100/300/1000 мс, затем GDI; stop/expiry отменяет ожидания. Исчезнувший выбранный монитор не подменяется основным: `source_unavailable` и новый выбор пользователя.

### 5.2. Курсор и геометрия

- GDI: `GetCursorInfo`, hotspot из `GetIconInfo`, `DrawIconEx`; временные bitmap-дескрипторы освобождаются. DXGI: shape/position и флаг, уже включён ли указатель в изображение; рисовать ровно один раз.
- Геометрия задаётся физическими пикселями с DPI-awareness процесса. Учитываются `RECT.left/top`, в том числе отрицательные, DPI 100/150/200%, hotspot и границы кадра.
- Для v1 полный исходный `RECT` масштабируется в растр профиля **без обрезки и полей**. На не-16:9 экране возможно изменение пропорций; это сознательный простой режим, сохраняющий существующий нормализованный маппинг ввода. Letterbox потребовал бы согласования content-rect с UI и в v1 не добавляется.
- Агент ввода использует тот же исходный `RECT`, не размер кодированного кадра. Смена монитора/геометрии инвалидирует разрешение ввода до повторного согласования источника и свежего кадра; одна автодеградация разрешения геометрию не меняет.

### 5.3. Масштабирование, цвет и pacing

Билинейное масштабирование на C; SIMD — оптимизация с проверкой ISA, не обязательное условие запуска. На один захваченный кадр выполняется одна конверсия: **I420 для OpenH264**, **NV12 для принявшего его MFT**. Выбор MFT может требовать собственного alignment/stride, это проверяет адаптер.

Матрица — BT.601 limited range для всех профилей; chroma усредняется на блоке 2×2, значения насыщаются в разрешённый диапазон. Цветовые параметры SPS/VUI должны соответствовать конверсии, не зависеть от default драйвера. Тесты: цветовые полосы, градиент, мелкий текст и границы плоскостей. При `854×480` внутренний macroblock padding кодера не меняет видимые 854 пикселя: cropping проверяется по SPS и декодированному кадру.

Pacing использует монотонное время, не wall clock. Очередь — один кадр в обработке и не более одного ожидающего; ожидающий заменяется более свежим. Опоздание не запускает цикл «догнать все тики». Raw-кадр можно сбросить до encode; произвольный P-кадр/фрагмент кодированного AU нельзя отбросить и продолжить зависимую цепочку без восстановления через IDR.

При init проверяются размеры, stride, все умножения и бюджет. В v1 предел исходного прямоугольника — 8 294 400 пикселей (4K по площади); превышение или нехватка памяти даёт контролируемый отказ, не огромный malloc. Бюджет включает source BGRA, рабочие поверхности DXGI, до двух YUV-слотов, контекст кодера и ограниченный AU. Лимиты проверяются **до** выделения, повторно после смены режима.

### 5.4. Кодеры

**Общий контракт:** AVC single layer, совместимый с текущим SDP Constrained Baseline/Level 3.1, без B-кадров и reorder/lookahead. Проверять фактические SPS и декодирование, а не только успешность установки опций. Annex B start codes или AVCC length prefixes нормализуются в NAL без префикса перед RTP.

**OpenH264:** `PRO_BASELINE`, `LEVEL_3_1`, I420 через C API, bitrate mode, без SVC-слоёв. Контекст переиспользуется. Пропуск кадра кодером допустим и считается отдельно от ошибки. Rate control не гарантирует жёсткий максимум в каждую миллисекунду; правила измерения и bursts заданы §13.

**Hardware MFT:** `MFTEnumEx` с hardware-флагом, COM/MF startup/shutdown, корректные synchronous/asynchronous MFT state/event handling. Проверяются media types, stream changes, SPS/PPS, настоящий IDR, запрет B-кадров и время выдачи AU. Имена GPU QSV/NVENC/AMF не доказывают наличие подходящего MFT; прямые vendor SDK не добавляются.

Probe ограничен 2 секундами и входит в общий startup-бюджет; media-worker не блокирует safety/watchdog. Несовместимый либо ошибочный MFT → один переход на OpenH264 при действующей lease. Зависший вызов не «лечится» конкурентным `cleanup`/`TerminateThread`: супервизор завершает процесс и делает ограниченный restart с программным бэкендом. Контроль безопасности действует и во время probe.

**Ключевые кадры:** первый AU — SPS/PPS + IDR; далее IDR не реже чем раз в 2 секунды монотонного времени, даже при снижении FPS/frame skip. Повторяются актуальные SPS/PPS. Force-IDR запросы объединяются (не более одного внепланового IDR в 500 мс); старт и смена конфигурации не откладываются этим лимитом.

## 6. OpenH264, supply chain и патентный допуск

- Базовый кандидат — OpenH264 `v2.6.0`: содержит исправление `CVE-2025-27091`. Перед фиксацией версии проверяются новые advisories; tag/commit, SHA-256 исходников, toolchain, параметры сборки и локальные патчи входят в SBOM уже с L4C-03.
- Encoder-only компоновка проверяется map-файлом/символами. Исключение декодера уменьшает поверхность атаки, но не доказывает отсутствие уязвимостей энкодера, IPC, RTCP или native-кода.
- BSD-2-Clause требует сохранения уведомлений; `OPENH264_LICENSE.txt` поставляется с пакетом. Исходники/зависимости берутся из зафиксированного источника, не скачиваются на терминале при старте.
- Покрытие Cisco для распространяемого ими бинарника **не переносится автоматически** на собственную статическую сборку. Бесплатность tools, закрытый корпоративный контур и платность только серверного сервиса не являются доказательством патентного освобождения. Утверждение «до 100 000 установок обязательств нет» здесь не применяется.
- До внешнего распространения владелец получает письменное подтверждение применимых AVC/H.264 условий для рынков и модели поставки. Изоляция `IEncoderBackend` облегчает замену реализации H.264, но переход на иной кодек потребует изменения SDP/медиатракта и находится вне v1. Отсутствие юридического допуска блокирует распространение, а не маскируется низким уровнем риска.

Первичные источники: [C API OpenH264](https://github.com/cisco/openh264/blob/v2.6.0/codec/api/wels/codec_api.h), [Cisco FAQ](https://www.openh264.org/faq.html), [security advisory](https://github.com/cisco/openh264/security/advisories/GHSA-m99q-5j7x-7m9x). Это технические основания, не юридическое заключение.

## 7. Профили и деградация

### 7.1. Целевые параметры

| Профиль | Видимый растр | FPS | Нижний / целевой / максимум, кбит/с H.264 | Назначение |
|---|---|---:|---:|---|
| `base_480p` | `854×480` | 10 | 500 / 500 / 700 | `low`, Win7, единственный профиль для ввода |
| `premium_540p` | `960×540` | 10–15 | 600 / 700 / 900 | Только внутренняя ступень |
| `premium_720p` | `1280×720` | 10–15 | 600 / 800 / 1000 | `default`, наблюдение |

`low` никогда не повышается автоматически. `default` задаёт верхнюю границу качества, не обещание аппаратного ускорения. На Win7 фактический профиль — 480p. M-1 реализует только 480p; запрос `default` в пилоте может деградировать до него, но **не даёт права ввода**.

### 7.2. Ввод

Необходимы одновременно: явный запрос пользователя `low`, фактический `base_480p`, desktop-источник, действующее разрешение/lease, совпадающая эпоха и подтверждённая геометрия. Агент проверяет это независимо от UI. Автодеградация `default → 480p` не включает ввод. При неизвестном фактическом профиле или геометрии ввод запрещён.

Используется текущий UI с двумя опциями, 540p не выводится. Если существующие consumer-поля не позволяют подтвердить safety-инварианты, это блокер интеграции с отдельным согласованным corrective, а не разрешение изменить MenuBuilder внутри scope `tools`.

### 7.3. Простой алгоритм

Перегрузка: доля drops >20% либо p95 времени обработки > интервала кадра в двух последовательных окнах по 3 секунды. После действия — минимум 6 секунд наблюдения; один шаг за раз:

```text
сброс опоздавших raw-кадров → FPS 15→10 → снижение растра 720→540→480
```

При уменьшении растра FPS **не увеличивается**. Битрейт уменьшается до нижней границы только при подтверждённом ограничении доставки либо превышении измеренного битрейта; это не универсальное лекарство от CPU overload. Успешный `sendto` в loopback ничего не говорит о внешней полосе. Без достоверного feedback причина сетевой деградации не угадывается.

На 480p устойчивая перегрузка ещё 15 секунд → диагностированный stop; бесконечная работа с неприемлемой задержкой запрещена. Повышение в текущей сессии запрещено. Смена кодера/разрешения очищает pending raw/AU, публикует фактический профиль и начинает новую конфигурацию с SPS/PPS + IDR. SSRC/sequence/timestamp сохраняются внутри процесса; после его restart — новая RTP-эпоха (§10).

## 8. Диагностика без нового сетевого протокола

IPC и локальный отчёт содержат: requested/actual profile, capture/encoder backend, fallback reason, fps, H.264 bitrate, raw/encoder/transport drops, encode p95, queue depth, возраст последнего AU, Private Bytes/handles. Метрики агрегируются за окно, а не отправляются на каждый кадр; период статуса — 1 секунда.

| Предлагаемый внутренний ключ | Значения / смысл |
|---|---|
| `video_capture_backend`, `video_encoder_backend` | `GDI`/`DXGI`, `OPENH264_SOFTWARE`/`MF_HARDWARE` |
| `video_profile_requested`, `video_profile_actual` | `480p`/`720p`; фактически также `540p` |
| `video_hw_accel` | Производное от активного кодера, не от названия GPU |
| `video_degradation_state` | `NOMINAL`, `FPS_THROTTLED`, `DEGRADED_540P`, `DEGRADED_480P` |
| `video_stream_fps`, `video_stream_bitrate` | Фактические значения за окно, кбит/с для битрейта |
| `video_fallback_reason` | `NONE`, `DXGI_ACCESS_LOST`, `MFT_UNAVAILABLE`, `WIN7_LEGACY`, `HIGH_LOAD` |

Это словарь **внутренней диагностики**, не утверждение, что все ключи уже принимают серверные модели. L4C-01 фиксирует путь producer → сериализатор → consumer и разрешённые extension-поля; L4C-05 подтверждает минимальные статусы по существующему каналу. Что не помещается без изменения схем — остаётся в локальном отчёте до отдельного согласования. Инвентарь не используется как оперативный safety-сигнал.

`EVENT_READY` означает первый локально отправленный SPS/PPS+IDR, не «пользователь видит видео». Для M-1 отдельно подтверждаются свежие ingress-пакеты и рост browser `framesDecoded` на движущемся тестовом изображении. Логи ограничены по размеру (5 МБ × 2), не содержат кадров, PIN, ключей и полного содержимого команд.

## 9. IPC, lease и безопасное завершение

### 9.1. Канал и framing (внутренний контракт v1)

Две анонимные наследуемые pipes; CLI содержит только `--pipe-in=<HANDLE_IN> --pipe-out=<HANDLE_OUT>`. Передаются исключительно нужные child-концы через handle allowlist; родитель сразу закрывает свои копии этих концов. Job handle ребёнку не наследуется. Формат HANDLE проверяется на размер указателя x86/x64.

Фрейм: `version:u16`, `type:u16`, `payload_length:u32`, `request_seq:u64`, затем payload, little-endian; максимум payload 4096 байт. Числа сериализуются явно, не `memcpy` нативной структуры. Частичное чтение/запись обязательно поддерживается; неизвестная версия/type, слишком большая длина, неполное сообщение при EOF — ошибка протокола и fail-closed. Парсер ограничивает строки/массивы и не исполняет произвольные пути или адреса.

| Команда/событие | Содержание и правило |
|---|---|
| `CMD_START` | Идентичность lease/stream, физический source RECT/ID и его поколение, requested profile, согласованные локальные RTP/RTCP порты, начальный `deadline_tick_ms`. Один старт на процесс; fps/gop выводятся из профиля, не задаются произвольно. |
| `CMD_RENEW_LEASE` | Та же идентичность, возрастающий request_seq, абсолютный `deadline_tick_ms`; устаревшее, истёкшее или уменьшающее срок продление не оживляет поток. |
| `CMD_STOP`, `CMD_FORCE_IDR` | Идентичность текущего потока; stop идемпотентен и приоритетен, IDR coalesced по §5. |
| `EVENT_READY`, `EVENT_METRICS` | Идентичность/sequence, фактические параметры и метрики §8. |
| `EVENT_DEGRADED`, `EVENT_ERROR` | Причина и фактическое состояние; ошибки не создают новые сетевые enum без проверенного mapping. |

Отдельный control/watchdog-путь не ждёт захват/encode/send и не захватывает их долгие mutex. Запись статуса не блокирует safety или media: один ограниченный writer, максимум 16 сообщений, metrics заменяются последними. Если критический статус не удаётся передать за 500 мс — local stop; завершение не ждёт читателя. Успех сетевого ACK на renew нельзя публиковать до подтверждения применения внутреннего deadline.

### 9.2. Один срок аренды, два исполнителя защиты

Агент валидирует внешние lease/epoch/expiry и переводит оставшийся допустимый TTL в абсолютный `GetTickCount64` deadline общего для процессов системного uptime. Доставка IPC не добавляет времени к аренде; renew передаёт deadline, не «ещё N секунд с момента чтения». Дубликаты не продлевают срок. Изменение wall clock не увеличивает действующий монотонный deadline; после resume он проверяется **до** первого RTP.

Внутренний таймер ребёнка — страховка того же deadline, не вторая аренда. Для `l4capture` существующие 5 секунд grace не добавляются. Потеря MQTT сама по себе не создаёт новую lease: разрешено только оставшееся действующее время, без renew происходит expiry. Stop/release/expiry/session loss отменяют pending recovery и освобождают ввод в агенте.

### 9.3. Запуск, остановка, зависания

1. Запуск только в интерактивной пользовательской сессии, не Session 0. Агент создаёт ребёнка suspended, назначает `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, затем resume. Если Job не назначается (в том числе ограничения вложенных Jobs Win7) — отказ до захвата, не запуск без защиты.
2. Доступность desktop проверяется до захвата и перед отправкой, с опросом/уведомлениями не реже 100 мс. Lock/UAC/session switch/disconnect либо невозможность проверить доступ → `session_unavailable`, сброс очередей и stop. Старые кадры/чёрная заглушка не продолжают поток. Unlock не запускает его сам: нужен новый разрешённый start.
3. `CMD_STOP`, EOF, expiry и session loss сразу закрывают допуск отправки, очищают очереди; RTP прекращается не позднее 500 мс от события/deadline. **Drain с отправкой остаточных кадров запрещён.** Штатное освобождение и exit — до 2 секунд; затем супервизор завершает процесс. Graceful stop возвращает 0, ошибка — диагностический ненулевой код.
4. Отсутствие media-progress 3 секунды при ожидаемой работе либо зависание probe вызывает stop/recovery; heartbeat control-потока не считается media-progress. При safety-событии и зависшем worker родитель не ждёт 2 секунды ради RTP: при необходимости завершает процесс в пределах 500 мс. Таймер защиты не зависит от mutex кодера.
5. Только unexpected exit/device error при действующей lease и доступном desktop допускает bounded recovery супервизора. Используется существующий предел 5 попыток за 600 секунд с backoff; дополнительный независимый цикл перезапуска не добавляется. Stop/expiry во время backoff отменяет попытку. Новый процесс не стартует до подтверждённого завершения старого.

Пределы измеряются на работающей ОС; suspend не обещает выполнения таймера, но после resume отправка без повторной проверки запрещена. Ошибки доступа не переводятся в fallback. Гарантия касается новых локальных RTP; уже доставленные в сеть/браузер кадры отозвать нельзя — их свежесть проверяется отдельно (§12).

## 10. RTP/H.264 и RTCP: точный минимальный контракт

- Назначение — только `127.0.0.1`, текущие согласованные порты RTP `5004` и RTCP `5005` локального `leo4proxy`. Другие порты допустимы только при совпадении конфигураций обоих концов. Это не динамические порты Janus/ingress. Route/mountpoint должен быть подготовлен штатной orchestration до старта.
- RTP v2, **динамический PT 96**, clock rate 90 000 Гц; `packetization-mode=1`. SPS должен быть совместим с SDP `42e01f` (§5). Шифрование и framing L4RTP/1 принадлежат proxy, а не кодеру.
- SSRC, начальные sequence и timestamp выбираются системным RNG. Sequence увеличивается на каждый RTP-пакет modulo 2^16; timestamp = base + elapsed_pts_ms × 90 modulo 2^32. Все NAL одного AU имеют один timestamp; marker=1 только у последнего пакета AU, не каждого NAL/FU.
- Бюджет **RTP payload ≤1200 байт**, включая два байта FU-A. Для FU-A фрагмент исходного NAL несёт максимум 1198 байт; исходный NAL-header заменяется FU indicator/header. Start/end, NRI/type и непустые фрагменты проверяются тестами. RTP-header и UDP/IP не входят в эти 1200 байт.
- Перед каждым IDR отправляются актуальные SPS/PPS; первый AU, late join и восстановление после потерь не требуют PLI. Annex B/AVCC служат форматом выхода кодера, не уходят в RTP payload.
- Отправка UDP неблокирующая с ограниченным socket buffer. Ошибка/срыв отправки AU учитывается, остаток AU отбрасывается и зависимая цепочка возобновляется с SPS/PPS+IDR; нельзя бесконечно копить пакеты или продолжать декодер с потерянной опорой. Уже отправленные фрагменты не «откатываются».
- Исходящий RTCP: SR + SDES CNAME раз в 1 секунду с корректным NTP/RTP соответствием и счётчиками; BYE при штатном завершении только best effort, без задержки stop. RTP pacing не зависит от wall clock, используемого для NTP.
- **Обратные RR/PLI не являются зависимостью M-1 или v1.** Их обработка включается только после подтверждения адреса/порта и всего обратного пути отдельным согласованием. Поддерживаемый локальный `CMD_FORCE_IDR` не доказывает доставку браузерного PLI. Любой добавляемый RTCP parser проверяет длины, source/SSRC и ограничивает частоту запросов.

Loopback `sendto`/счётчик RTP не обнаруживает TCP head-of-line blocking, backlog proxy, потерянный route или зависший браузер. Внешняя доставка испытывается на M-1; дефект proxy/ingress оформляется владельцу компонента и блокирует приёмку, но не расширяет scope исполнителя `tools`.

## 11. Контроллер каскада и передача результатов

Нормативная основа — регламент контроллера каскада [HANDOFF-CONTROLLER-PROMPT](prompts/HANDOFF-CONTROLLER-PROMPT.md) и стандарт промптов [PROMPT-STANDARD](prompts/PROMPT-STANDARD.md) в целевой папке `docs/l4capture/prompts/`. Единственный журнал передачи контрактов проекта `l4capture` — `docs/l4capture/prompts/contract-handoff.md`.

**Строгое правило изоляции:** Запрещено использовать `l4desk-service` для размещения файлов проекта `l4capture`. Проект `l4desk-service` обслуживает отдельный каскад сервиса L4Desk. Все промпты, стандарты, handoff-отчёты, кандидаты и журнал каскада `l4capture` размещаются исключительно внутри `docs/l4capture`.

До запуска L4C пользователь утверждает регистрацию этого реестра/sequence gate в процессе контроллера `l4capture`. Эта архитектурная ревизия **не регистрирует** шаги автоматически и не меняет принятые блоки. Контроллер работает в своём scope `docs/l4capture`, исполнители — в scope §12 (`tools/l4capture` и адаптер `tools/l4desk`); чтение точных контрактов соседних проектов не даёт разрешения на их несанкционированное редактирование.

Приёмка одного шага:

1. Исполнитель передаёт report и candidate с точными файлами, commit, контрактами и evidence. Отчёты размещаются в `docs/l4capture/handoffs/<PROMPT_ID>-report.md`, кандидаты — в `docs/l4capture/handoffs/<PROMPT_ID>-candidate.md`. `ACCEPTED` в отчёте — заявка, не самостоятельное разрешение следующего шага.
2. Контроллер проверяет scope, обязательные тесты, предыдущий принятый handoff, отсутствие дубликата ID и SHA-256 **реальных байтов** всех артефактов. LF/CRLF не нормализуется молча; отчёт не включает собственный самоссылочный digest. Отдельный candidate — только по согласованному `DETACHED_V1` стандарта.
3. Для M-1 дополнительно нужны fault-матрица §12 и явный вердикт владельца «НОРМ». Без них acceptance запрещён.
4. При `BLOCKED_*`/`REJECTED`, пропущенном обязательном тесте или несовпадении хеша — отказ без принятого блока. Исправление возвращается владельцу дефектного компонента, не всегда агенту L4C-05.
5. Запись append-only выполняется единственным writer: проверка длины/хеша исходного префикса, полное добавление BEGIN/END-блока, повторная проверка префикса/целостности. Параллельные append запрещены; незавершённая запись не считается handoff.
6. Контроллер выдаёт готовность и останавливается. Следующего исполнителя запускает только пользователь. Local build, публикация и production deploy не подменяют друг друга в статусах.

Формат YAML повторно не копируется: обязательные поля и правила версионирования берутся из стандарта `docs/l4capture/prompts/PROMPT-STANDARD.md`. В `contract_payload` достаточно точных интерфейсов, ограничений, ошибок, доказанных проверок и потребителя; полные исходники/история обсуждения в handoff не переносятся.

## 12. Каскад реализации и обязательная M-1

Последовательность остаётся из **11 шагов / 4 фаз**. Каждый следующий шаг требует принятого предыдущего `H-L4C-XX-v1`; повторная приёмка/исправление оформляется по стандарту, старый ID не перезаписывается. Отчёты: `docs/l4capture/handoffs/<PROMPT_ID>-report.md` по зарегистрированному заданию.

```text
Фаза 1: L4C-01 → 02 → 03 → 04 → 05 → 06 (M-1: СТОП до «НОРМ»)
Фаза 2: L4C-07 → 08 → 09       Фаза 3: L4C-10       Фаза 4: L4C-11
```

### 12.1. Шаги 1–5: защита входит в минимальный тракт

### 12.2. L4C-06-MILESTONE-LIVE-VERIFY — M-1

**Агент:** `L4Capture-MilestoneVerifier-Agent`. **Scope:** подготовка evidence в `tools/l4capture` и `tools/l4desk`, чтение штатных статусов и согласованная живая проверка в MenuBuilder/l4media. Никакого скрытого исправления серверов. Вход `H-L4C-05-v1`.

Стенд владельца: Windows 10 x64, Core i7 (точная модель обязательна), GDI + OpenH264, `base_480p`, исходный экран 1920×1080; фиксируются OS build, RAM, DPI, версия драйвера/браузера, сеть, хеши exe и конфигурация. В отчёте отдельно перечисляются результаты раннего Win7 x86/x64 smoke. Всё ниже — критерии, а не уже полученные результаты.

| Проверка | Как воспроизвести | Условие прохода |
|---|---|---|
| Базовый просмотр | 10 стартов/остановок из MenuBuilder; затем 30 минут мелкого текста, скролла и движения курсора | Ни одного crash/зависания/второго процесса; правильные цвета/размер, один курсор; first-frame, fps/CPU/RAM по §13. Владелец подтверждает читаемость и отклик. |
| **R1: lease/session safety** | Прекратить renew; отдельно stop, убить родителя, закрыть pipe, lock, UAC, сменить session; stop/expiry во время backoff; sleep до истечения deadline и resume | Новые RTP прекращаются ≤500 мс; нет orphan/restart после terminal stop, ввода и отправки после resume. Старый/дублированный renew не оживляет поток. После unlock нужен новый start. |
| **R2: внешняя доставка** | Late join; отключить медиатранспорт на 10 секунд при живой lease, затем вернуть; удалить/восстановить тестовый route штатным способом; потери RTP 1% и 5% в тестовом стенде | После подтверждённого восстановления транспорта/route свежий кадр ≤3 с без PLI; нет проигрывания старого backlog. Растут `framesDecoded`, экранный счётчик времени актуален. Невосстановившийся tunnel — отдельный fail, время его reconnect не скрывается. |
| **R3: внутренняя устойчивость** | Задержка encode 200 мс на кадр, затем зависший worker; заблокировать чтение status; отказ allocation/send; 100 start/stop циклов | Очереди не растут, перегрузка даёт drop/ограниченный stop; safety не ждёт worker/writer, recovery ограничен. После прогрева нет роста GDI/handle count, память соответствует §13. |
| **R4: совместимость/геометрия** | Использовать ранние Win7 x86/x64 артефакты; отключённые optional API; DPI 100/150/200%, монитор слева с отрицательным origin, смена разрешения/отключение выбранного дисплея | Базовый путь не зависит от MF/DXGI/VC runtime. Нет двойного курсора, неверных плоскостей или кликов по старому RECT; неизвестный/слишком большой источник даёт контролируемый отказ. |
| Ограничение ввода | Явный `low`; отдельно `default`, фактически пониженный до 480p; отправка ввода в обход UI | Только первый сценарий с валидной lease/геометрией разрешён; недостаточно одного размера видеокадра. |

Сетевые сбои воспроизводятся только на согласованном тестовом маршруте/стенде, не отключением общей production-инфраструктуры. Подготовка такого стенда не является автоматическим разрешением на деплой. Каждый fault повторяется минимум 3 раза; время воздействия, ожидаемый исход и фактические метрики входят в один компактный отчёт с PCAP/логами по необходимости, без секретов и записи рабочего экрана.

**Шлюз:** технические проверки пройдены **и** владелец лично дал «НОРМ» → контроллер может принять `H-L4C-06-v1`. «НЕУДАЧА», отсутствие стенда/evidence или пропущенная обязательная строка → остановка, адресный corrective владельцу дефекта и повтор M-1. Хорошая картинка не компенсирует провал safety. L4C-07 не запускается до принятия вехи.

## 13. Измеримые критерии приёмки

### 13.1. Функциональность и безопасность — обязательные пределы

- Один desktop-процесс, штатные команды без изменения wire-схем; камера продолжает работать по прежнему пути. `low`/`default` согласованы с фактическим профилем и политикой ввода.
- Win7 x86/x64 запускает базовый тракт без VC Redistributable; новые ОС используют только успешно проверенный backend. Неизвестная платформа помечается непроверенной, не поддержанной по умолчанию.
- Изображение проходит через существующие proxy/ingress/Janus и декодируется браузером; отсутствие server changes подтверждается diff, а не обещанием совместимости.
- RTP-stop ≤500 мс по §9, штатный exit ≤2 с, Job cleanup, никаких автоматических restart после expiry/lock. Нет MessageBox, консольных окон, требования admin и обхода Secure Desktop.
- Каждая ветка init/ошибки освобождает sockets/handles/GDI/COM/DXGI; тесты включают partial init и allocation failure. Защиты §9 обязательны независимо от результатов визуальной оценки.

### 13.2. Измерения и стендовые бюджеты

| Метрика | Метод и порог |
|---|---|
| First frame | После успешного штатного `stream_start` при уже готовых route/mountpoint — первый **свежий декодированный** кадр ≤1,5 с для базового тракта, минимум 10 запусков. Время от клика UI, включая сеть/подготовку route, измеряется отдельно. Hardware probe имеет отдельный предел 2 с, полный hardware-start ≤3,5 с. |
| Latency | На стенде M-1 p95 capture→browser ≤200 мс, цель 150 мс. Съёмка/сопоставление меняющегося счётчика на источнике и клиенте, не разность несинхронизированных часов и не только encode time. Сеть и метод указываются в отчёте. |
| FPS/encode | 480p: ≥9 отправленных кадров/с в среднем на движущемся сценарии без искусственной перегрузки; p95 encode ≤100 мс. Под fault нагрузкой обязательны safety и bounded queues, не номинальные FPS. |
| CPU | Среднее за 60 с, нормировано на все логические CPU; указать их число. Стендовые бюджеты: GDI/OpenH264 480p ≤25% на указанном 2-ядерном терминале; DXGI/MFT ≤5% на указанном i5/i7. Проценты и «<5 мс encode» не универсальны для всех устройств. |
| RAM | Отдельно Private Bytes, Working Set и GPU allocations. Цель Private Bytes ≤45 МиБ для 1080p→480p GDI; общий admission-предел управляемых буферов/контекста 128 МиБ, включая проверенный максимум AU 2 МиБ. 4K/DXGI требуют расчёта §5, не обещания тех же 45 МиБ. Превышение лимита — отказ/stop, не расширение очереди. |
| Утечки | После 5 минут прогрева: 30 минут M-1, 2 часа финальный soak. При повторении одинакового цикла GDI/handle count возвращается к baseline, Private Bytes не растёт монотонно; рост >5 МиБ требует расследования и блокирует приёмку. |
| Битрейт | H.264 payload, включая SPS/PPS, среднее по скользящему окну 10 с ≤700/900/1000 кбит/с. IDR bursts фиксируются отдельно; это не мгновенный wire cap. RTP/RTCP/IP/TLS overhead и пик за 1 с измеряются отдельно; формулировка «строго ≤700 кбит/с в сети всегда» не используется. |

Бюджеты проверяются на описанных стендах, не выдаются за уже достигнутые значения. Невыполнение согласованного порога блокирует шаг; менять порог для сокрытия провала нельзя. Несопоставимое железо/сеть требуют явно согласованной матрицы, а не молчаливого снятия проверки.

## 14. Четыре приоритетных риска устойчивости

Вероятности — инженерная оценка для неоднородного парка, не статистика эксплуатации. Юридический допуск учтён отдельно в §6 и не подменяет технические риски.

| Риск и ранний сигнал | Вероятность / ущерб | Мера с первых шагов и владелец | Доказательство M-1 / остаточное ограничение |
|---|---|---|---|
| **R1. Потеря разрешённого состояния:** lock/UAC, lease expiry, поздний renew, смерть агента | Высокая / критический: лишний кадр, ввод в другую сессию, orphan | L4C-01: deadline/epoch и независимый safety-gate; L4C-02: desktop availability; L4C-05: агент владеет Job, input release и отменой recovery | Fault-строка R1, отсутствие RTP ≤500 мс и автопуска после unlock. Уже ушедшие в сеть кадры не отзываются. |
| **R2. Нарушение внешней доставки:** TLS reconnect, потери/route loss, накопление задержки при живом процессе | Высокая / высокий: чёрный или замерший экран, ложное «работает» | L4C-03/04: SPS/PPS+IDR ≤2 с, bounded send, без зависимости от PLI; L4C-05/06: отдельные проверки local RTP, ingress и browser. | **R3. Внутренняя перегрузка/зависание/утечка:** encode p95, drops, отсутствие AU, растущие handles | Высокая / высокий: торможение платёжного UI, память, невозможность stop | L4C-01: лимиты/контракты владения; L4C-02/03: reuse/latest-frame; L4C-05: watchdog вне media locks, bounded restart. Полная GPU/Embedded матрица остаётся финальным допуском, не заявляется закрытой ноутбуком владельца. |

## 15. Условия начала реализации и итог

Перед L4C-01 должны быть доступны: зарегистрированный sequence gate/границы задач, согласованные локальные порты и consumer-mapping диагностики, Win7 x86/x64 тестовые образы, стенд M-1 и способ безопасной имитации сетевых сбоев. Неясный внешний контракт фиксируется как адресный блокер; новый сервис или поле не создаётся «для удобства».

Ревизия сохраняет узкую замену FFmpeg и существующую orchestration. Минимальный релизный фундамент — не только **GDI + I420/OpenH264 + RTP 480p**, но и **deadline, session gate, ограниченные буферы, контролируемое завершение и доказанное восстановление декодирования без обратного PLI**. Эти свойства проверяются до DXGI/MFT, а M-1 остаётся одновременно техническим шлюзом и личным решением владельца.
