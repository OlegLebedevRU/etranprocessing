# Ролевая модель, роль «Наблюдатель» (Viewer) и управление пользователями тенанта

## 1. Концепция и ролевая матрица

В платформе `etranprocessing` (в частности, в административно-пользовательском портале `MenuBuilder` и общей модели БД `etranprocessing_db`) зафиксирована четырехуровневая модель ролей:

| `role_id` | Системное имя (`role`) | Описание и область ответственности | Доступ к тенантам |
|---|---|---|---|
| **1** | `superuser` | Глобальный администратор платформы. Доступ ко всем разделам и тенантам, переключение контекста организаций (`can_switch_org = True`), управление глобальными пользователями и системными настройками. | Все организации (0 и любой `org_id`) |
| **2** | `admin` | Системный администратор / технический персонал платформы. | Все организации |
| **3** | `user` | **Главный пользователь (Администратор тенанта)**. Обладает полными правами в рамках закрепленной организации (`org_id`): управление меню, каталогом, терминалами, заказами лицензий, просмотр и пересчет отчетов, настройка профиля. Наделен правом управления пользователями роли 4 своей организации в «Настройки → Пользователи». | Строго свой `org_id` |
| **4** | `viewer` | **Пользователь-наблюдатель организации**. Пользователь с ограниченными правами просмотра: жесткая изоляция 1:1, полный запрет любых мутирующих операций (`POST`/`PUT`/`PATCH`/`DELETE`), гранулярный доступ к разделам по белому списку `permissions`. | Строго свой `org_id` (`can_switch_org = False`) |

## 2. Реестр кодов разрешений (Permissions)

Для роли 4 (`viewer`) действует нормализованный реестр строковых прав доступа:

| Код разрешения | Назначение | Эндпоинты API бекенда | Маршруты UI фронтенда |
|---|---|---|---|
| `monitoring:view` | Просмотр состояния и связи терминалов | `GET /api/monitoring` | `/monitoring` |
| `reports:inkass:view` | Просмотр отчета «Инкассация» | `GET /api/reports/inkass` | `/reports?tab=inkass` |
| `reports:payments:view` | Просмотр отчета «Платежи» | `GET /api/reports/payments` | `/reports?tab=payments` |
| `reports:balance_terminal:view` | Просмотр отчета «По терминалам» | `GET /api/reports/balance-by-terminal` | `/reports?tab=balance-terminal` |
| `reports:balance_tsp:view` | Просмотр отчета «По ТСП» | `GET /api/reports/balance-by-tsp` | `/reports?tab=balance-tsp` |
| `reports:export` | Экспорт табличных данных отчетов в CSV | Доступно для всех разрешенных отчетов | Кнопка «Экспорт в CSV» в тулбарах отчетов |
| `billing:view` | Информационное табло сроков лицензий терминалов | `GET /api/billing/summary`, `GET /api/billing/terminals` | `/billing` (кнопки оплаты и отключения скрыты) |
| `settings:terminals:view` | Просмотр параметров и адресов терминалов (Readonly) | `GET /api/settings/terminals` | `/settings/terminals` (форма disabled, сохранения нет) |

### Безусловно закрытые разделы для роли 4 (HTTP 403 / скрыты в UI)
- «Управление меню» (`/menu/*`): терминалы, варианты, каталог товаров.
- «Интеграции» (`/integrations`): API, вебхуки, шлюзы.
- «Настройки → Профиль» (`/settings/profile`): реквизиты организации и смена мастер-пароля.
- «Настройки → Пользователи» (`/settings/users`): доступно только ролям 1 и 3.
- «Администрирование» (`/admin/*`): доступно только глобальным суперадминистраторам.

## 3. Архитектурная реализация

### 3.1. Слой данных и схема БД (Alembic & shared `etranprocessing_db`)
- В модели `User` (`shared/etranprocessing_db/models/auth.py`) добавлена колонка:
  ```python
  permissions: Mapped[list[str]] = mapped_column(
      JSONB,
      nullable=False,
      server_default=text("'[]'::jsonb"),
      comment="Список строковых разрешений пользователя (актуально для role_id=4)"
  )
  ```
- Миграция `025_add_user_permissions_and_role4.py`:
  - Добавление `JSONB`-колонки `permissions` с дефолтным `'[]'::jsonb`.
  - GIN-индекс `idx_users_permissions` для ускорения поиска по элементам массива permissions.
  - Ограничение целостности `chk_users_role4_tenant`:
    ```sql
    CHECK (role_id != 4 OR (org_id IS NOT NULL AND org_id > 0))
    ```

### 3.2. Бекенд (`MenuBuilder/backend`)
- **Контроль безопасности (`app/security/permissions.py`)**:
  - `require_readonly_guard`: блокирует любые HTTP-методы мутации (`POST`, `PUT`, `PATCH`, `DELETE`) для роли 4 с ответом 403 Forbidden.
  - `require_permission(permission_code)`: проверяет наличие требуемого права в `user["permissions"]`. Для ролей 1, 2, 3 доступ предоставляется автоматически.
  - `require_tenant_admin`: ограничивает доступ к управлению пользователями тенанта только для `role_id in (1, 3)`.
- **Эндпоинт `GET /api/auth/me` (`app/routers/auth.py`)**:
  - Возвращает поле `permissions`. Для роли 4 возвращается реальный список из БД, для ролей 1, 2, 3 возвращается полный перечень всех прав.
- **Управление пользователями (`app/routers/settings_users.py`)**:
  - `GET /api/settings/users` — список пользователей тенанта (роли 3 и 4).
  - `POST /api/settings/users` — создание наблюдателя (роль принудительно фиксируется в 4, организация берется из токена создателя, валидируются разрешения).
  - `PUT /api/settings/users/{user_id}` — редактирование ФИО, разрешений и активности (редактирование роли 3 через этот эндпоинт запрещено).
  - `POST /api/settings/users/{user_id}/change-password` — смена пароля с автоматическим отзывом всех сессий в `user_sessions`.
  - `POST /api/settings/users/{user_id}/toggle-active` — блокировка/активация с отзывом сессий при блокировке.

### 3.3. Фронтенд (`MenuBuilder/frontend`)
- **Маршрутизация и резолвер по умолчанию (`src/App.tsx`)**:
  - При входе роли 4 вычисляется первый доступный маршрут (`monitoring` → `reports` → `billing` → `settings/terminals`).
  - При отсутствии каких-либо разрешений выводится блокирующее модальное окно: «Доступ ограничен. Вам необходимо обратиться к Главному пользователю...» с кнопкой «Выйти».
- **Гарды (`ViewerGuard`)**: предотвращают переход по прямым ссылкам на запрещенные разделы.
- **Интерфейс раздела «Настройки → Пользователи» (`src/routes/settings/UserSettingsPage.tsx`)**:
  - Таблица пользователей тенанта с отображением бейджей ролей, статуса, назначенных тегов прав.
  - Модальные окна создания, редактирования прав с удобной группировкой чекбоксов, смены пароля и подтверждения блокировки.
- **Адаптация разделов**:
  - `ReportsPage`: динамическое скрытие вкладок, скрытие кнопок пересчета кассеты, поддержка экспорта в CSV.
  - `BillingPage`: сокрытие карточки оплаты, переключателей авансовых периодов и кнопок отключения/включения терминалов.
  - `TerminalsSettingsPage`: режим просмотра без кнопки сохранения.

## 4. Предложения по архитектурному развитию и рефакторингу

1. **Нормализованный RBAC (Role-Based Access Control) в БД**:
   - В текущей реализации права хранятся как `JSONB`-массив в таблице `users`, а роли определяются числовым `role_id`.
   - *Рекомендация*: В долгосрочной перспективе перейти на классическую схему таблиц: `roles`, `permissions`, `role_permissions`, `user_roles`. Это позволит тенантам создавать кастомные профили ролей (например, «Бухгалтер», «Инкассатор», «Сервисный инженер») без изменения кода приложения.
2. **Включение permissions в JWT-токены**:
   - Передавать массив прав непосредственно в JWT claims при выпуске access-токена (с коротким TTL, например, 15 минут), чтобы снизить количество обращений к БД на каждый запрос через `get_user_store().get_by_id(...)`.
3. **Журналирование действий и аудит (Audit Log)**:
   - Внедрить отдельную таблицу `audit_logs` для фиксации экспорта отчетов (кто, когда и какой отчет выгрузил в файл), а также истории создания и изменения прав пользователей тенанта.
4. **Кэширование прав в Redis/памяти**:
   - Для высоконагруженных шлюзов и API кэшировать активные права пользователей и инвалидировать кэш по событиям смены пароля или прав через pub/sub брокер.
