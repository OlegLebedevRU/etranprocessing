# Управление MQTT и RTP соединениями leo4proxy через ProcessingBackend

Отчет первого этапа, 1 октября 2026 года. Серверная часть реализована в ProcessingBackend; состояние выпуска фиксируется ниже по результатам deployment. Изменения leo4proxy пока только запланированы.

ProcessingBackend вычисляет разрешения для конкретного терминала. leo4proxy опрашивает API каждые 10 минут и сразу применяет полученный запрет к MQTT/RTP. При отсутствии ответа для MQTT/RTP действует запас 72 часа. Входящий HTTPS-прокси, локальные служебные API и поллинг сохраняются. Исходящий HTTPS регулируется отдельным флагом: только явный `false` ограничивает маршруты; сейчас backend всегда возвращает `true`.

## Согласованные требования

- Разрешение leo4proxy — синтетический результат, без отдельного поля в БД. Сейчас единственный аргумент вычисления — `Terminal.is_active`.
- «Отключен» запрещает попытки подключения к MQTT-брокеру и медиашлюзу; предложенное ранее закрытие текущих MQTT/RTP-соединений входит в остановку передачи.
- Служба, входящий HTTPS-прокси, локальные служебные API и поллинг не останавливаются. Полученное разрешение возвращает штатные MQTT/RTP-подключения.
- Независимый флаг исходящего HTTPS разрешает запросы при любом отсутствии явного `false`. При явном запрете остаются маршруты policy, certificates и licensebilling. Сейчас этот флаг на backend — константа `true`.
- Внутренние клиенты и остальные tools вне задачи: leo4proxy не останавливает их процессы и службы и сохраняет свой внутренний контракт готовности.
- Запас 72 часа действует при недоступности API, без отсрочки для полученного запрета.
- Первая установка или потеря обеих достоверных локальных копий восстанавливает запас 72 часа в пользу клиента.
- Ужесточения при злоупотреблениях, санкции и удаление сертификата исключены из первого этапа.

## Основания и границы исследования

В [общей модели Terminal](../shared/etranprocessing_db/models/terminal.py) существует `is_active`. В [get_current_terminal](../ProcessingBackend/backend/app/dependencies.py) распознавание по новому сертификату проверяет SN и serial и возвращает терминал без проверки активности. Отключенный терминал поэтому может получать решение. Лицензирующую зависимость для этого API использовать нельзя: она блокирует отключенный терминал вместо выдачи состояния.

[Архитектура утилит](term_tool-architecture-guide.md), [руководство инженера](term_tool-user-guide.md) и [контракт медиатракта](../.agent-context/contracts/video-streaming.md) дают контекст. Направления HTTPS сверены с кодом: [http_proxy.c](../tools/leo4proxy/src/http_proxy.c) пересылает локальные запросы во внешний HTTPS backend; [reverse_proxy.c](../tools/leo4proxy/src/reverse_proxy.c) принимает входящий HTTPS и передает его локальному backend. Входящий прокси сохраняется при обоих запретах.

Исследован только `tools/leo4proxy`: main, service manager, HTTP/reverse HTTPS, MQTT, RTP и конфигурация. MQTT делает внешний TLS-connect после локального подключения; RTP соединяется при поступлении датаграмм и имеет backoff. В service manager отдельно запускаются транспорты, входящий и исходящий HTTPS. Конкретные изменения пока не реализованы. Другие tools, включая l4superv, не исследованы и не участвуют в доработке. Runtime и E2E не проверены.

## Владельцы и поток решения

ProcessingBackend владеет вычислением и терминальным API. Общая модель остается источником `Terminal.is_active`; новый атрибут и миграция не нужны. leo4proxy владеет применением решения и локальным хранением.

Поток: существующее изменение `Terminal.is_active` → вычисление в ProcessingBackend → mTLS HTTPS → состояние leo4proxy → разрешение или запрет MQTT/RTP. Разрешение исходящего HTTPS вычисляется отдельно и сейчас всегда `true`; оно не зависит от `Terminal.is_active`. Отдельный API установки синтетического флага не нужен. Пользовательский JWT-маршрут в ProcessingBackend не добавляется. Статусы организации, лицензии и другие факторы в первый этап не входят.

## Предлагаемый контракт API

Терминальный маршрут: `GET /api/leo4proxy/policy`, реализован в [router](../ProcessingBackend/backend/app/routers/leo4proxy.py), [schema](../ProcessingBackend/backend/app/schemas/leo4proxy.py) и [вычислении политики](../ProcessingBackend/backend/app/services/leo4proxy_policy.py). Терминал определяется существующей mTLS-аутентификацией, без клиентского выбора чужого SN. В конфигурации Nginx добавлен явный маршрут с перезаписью certificate identity headers из TLS-сеанса и отключением proxy cache.

Отключенный, но распознанный терминал получает `200 OK`. Заголовок ответа: `Cache-Control: no-store`.

```json
{
  "v": 1,
  "sn": "<SN>",
  "mqtt_rtp_allowed": false,
  "outgoing_https_allowed": true,
  "stop_facts": ["terminal_inactive"]
}
```

Для активного терминала: `mqtt_rtp_allowed: true`, `outgoing_https_allowed: true`, `stop_facts: []`.

Сейчас `mqtt_rtp_allowed = Terminal.is_active`. Список `stop_facts` содержит машинные коды фактов запрета; первый и единственный код — `terminal_inactive`. Другие аргументы вычисления и коды добавляются отдельными задачами. Это небольшая точка расширения, без системы правил и плагинов.

На границе leo4proxy ответ преобразуется в два независимых разрешения и факты для диагностики. Незнакомый код факта не отменяет корректно полученный запрет MQTT/RTP. Ошибка обязательной схемы означает неуспешное чтение политики MQTT/RTP. Отсутствие или неверный тип дополнительного HTTPS-флага не должны отвергать корректное решение MQTT/RTP.

### Разрешение исходящего HTTPS

`outgoing_https_allowed` предназначен для будущего серверного ограничения исходящего спама от работающего, но брошенного агента. В первом этапе ProcessingBackend явно возвращает константу `true`, без нового поля БД и без логики определения брошенного агента.

Запрет принимается только из валидного аутентифицированного ответа для своего SN с JSON-значением `false`. Отсутствующее поле, `null`, строка `"false"`, ошибочный ответ, недоступность API или отсутствие достоверного локального значения означают разрешение. Последний полученный явный запрет действует между плановыми опросами; следующий неуспешный опрос снимает именно HTTPS-ограничение, не отменяя сохраненный запрет MQTT/RTP. После перезапуска службы HTTPS разрешен до нового валидного явного `false`; сохраненный ответ используется как история, а не основание бессрочного запрета HTTPS. Запас 72 часа к этому флагу не применяется.

При явном `false` leo4proxy не отправляет обычные исходящие запросы во внешний backend и возвращает вызывающему клиенту штатный HTTP-отказ, например `403` с машинным кодом `outgoing_https_disabled`. Слушатель и процесс остаются работающими. Не вводятся очередь отложенных запросов и автоматические повторы запрещенных запросов.

Исключения сохраняются всегда: `/api/leo4proxy/policy`, `/api/certificates` и `/api/licensebilling`. Существующий `/licensebilling` — зарегистрированный backend alias — также относится к исключению. Для certificates/licensebilling допускается конечный `/` и query string, включая `function=setup`; произвольные дочерние пути не разрешаются. Сопоставляется разобранный путь, а не подстрока: `/api/certificates-other` не является исключением. Локальные `/_leo4/*` не являются исходящими маршрутами и этим флагом не блокируются.

Входящий reverse HTTPS этим флагом не фильтруется. Два разрешения независимы: запрет MQTT/RTP не запрещает HTTPS, а запрет исходящего HTTPS не запрещает MQTT/RTP.

| Ответ | Обработка |
| --- | --- |
| Корректный `200`, ожидаемые версия, SN и обязательные типы | Принять MQTT/RTP-решение; HTTPS запретить только по явному `false` |
| `401` или `403` | Ошибка аутентификации или доступа; не подменять состоянием «отключен» |
| `404`, `5xx`, timeout, DNS/TLS error, неверные JSON или SN | Нет достоверного решения; не продлевать запас |

Для MQTT/RTP отсутствие валидного ответа расходует запас, включая ошибки доступа. Причины фиксируются отдельно. HTTP-код или текст ошибки не заменяют серверное решение. Для HTTPS при этих ошибках действует разрешение по умолчанию.

## Поллинг и запас 72 часа

Первый запрос выполняется при старте службы, следующие — раз в 600 секунд. Одновременно выполняется не более одного запроса. Конечный timeout не должен блокировать HTTPS-прокси; конкретное значение выбирается после проверки существующего HTTP-клиента.

После валидного ответа MQTT/RTP «разрешено» сохраняется срок `offline_allowed_until = время получения + 72 часа`. Неуспешный запрос его не сдвигает. Истечение срока проверяется независимо от запросов, поэтому зависший запрос не продлевает доступ. Сетевой отказ не создает дополнительных санкций и не прекращает доступ к исключениям HTTPS.

| Ситуация | MQTT и RTP | Входящий HTTPS и поллинг |
| --- | --- | --- |
| Получено разрешение | Разрешить штатные подключения | Продолжаются |
| Получен запрет | Закрыть текущие соединения; отменить новые и reconnect | Продолжаются |
| API недоступно, последнее решение разрешающее, запас есть | Продолжить работу в пределах оставшегося запаса | Продолжаются |
| API недоступно, запас истек | Закрыть соединения; запретить новые | Продолжаются |
| API недоступно, последнее решение запрещающее | Сохранить запрет при любой длительности недоступности | Продолжаются |
| Нет обеих достоверных копий | Создать и сохранить запас 72 часа; разрешить подключения | Продолжаются |

Истечение запаса — локальный факт `policy_unavailable`, а не изменение серверного состояния. Новый валидный разрешающий ответ снимает его и серверный запрет.

Перезапуск службы или ОС не создает новый запас при наличии хотя бы одной достоверной копии. Первоначальный срок сохраняется один раз, а не при каждом неудачном опросе.

Время сохраняется в UTC. В работающем процессе отсчет дополняется монотонным таймером: перевод часов назад не должен продлевать текущий запас. После перезапуска используется сохраненный абсолютный срок. Защита от намеренной подмены часов и отката диска в первый этап не входит.

## Локальное хранение

Предлагается один небольшой документ состояния в реестре и его копия в JSON. leo4proxy самостоятельно выбирает реально доступное хранилище с учетом версии Windows, разрядности и учетной записи запуска. Предпочтительна машинная ветка реестра для службы; если доступ запрещен, проверяется ветка текущей учетной записи leo4proxy. В служебном режиме это профиль службы, не интерактивного пользователя. Путь выбирается проверкой доступности чтения и записи, а не только номером Windows; результат запоминается и диагностируется. Согласованное представление реестра для x86/x64 должно сохранять состояние при замене сборки.

Если реестр недоступен, используется доступная JSON-копия в каталоге данных leo4proxy. Если недоступен выбранный каталог, проверяется доступный каталог данных учетной записи. Точные имена ключей и файлов определяются в реализации; новые зависимости и требования повышения прав для работы политики не вводятся. Сохранившиеся копии читаются до выбора нового места, чтобы смена пути не сбрасывала известное решение. Отказ одной записи не должен препятствовать попытке записать другую. Если нет доступного постоянного хранилища, состояние остается в памяти и доступность хранения периодически проверяется.

| Поле записи | Назначение |
| --- | --- |
| `storage_version`, `sn` | Формат и принадлежность терминалу |
| `generation` | Номер локальной записи для восстановления после частичной записи |
| `server_policy` | Последний валидный ответ либо его отсутствие при первоначальном запасе |
| `last_success_at` | Время последнего принятого ответа, отсутствует до первого ответа |
| `offline_allowed_until` | Сохраненный предел разрешения при отсутствии ответа |

Эффективное разрешение вычисляется из записи. Отдельный изменяемый флаг для него не нужен.

Предлагаемый порядок: сформировать документ с новой `generation`, записать его одним значением реестра, записать временный JSON, сбросить содержимое на диск и заменить основной файл. Общей транзакции между реестром и файлом нет; восстановление учитывает сбой между записями. Обе копии проверяются на корректность схемы и SN.

Одна корректная копия достаточна. При разных поколениях используется более новая корректная запись, вторая копия восстанавливается при доступности. При одинаковом поколении и противоречии выбирается разрешающее MQTT/RTP-решение; при двух разрешающих — более поздний достоверный срок, в пользу клиента. Само расхождение не создает новый запас и не считается злоупотреблением. Полная потеря достоверных копий создает новые 72 часа. Ошибки доступа и неподдерживаемые способы хранения не становятся самостоятельной причиной запрета.

Запись ограничивается учетной записью службы, SYSTEM и администраторами с учетом фактического способа установки. JSON повышает восстановимость, но не доказывает неподменность. Подписи состояния, санкции и удаление сертификата не вводятся.

Запрет применяется к транспорту до записи на диск: ошибка хранения не должна продолжать передачу. Если обе записи не удались, процесс удерживает решение в памяти, повторяет сохранение и сообщает об ошибке. Без работающего хранилища нельзя гарантировать сохранение запрета после аварийного перезапуска; полная потеря копий включает согласованный запас.

## Изменения на границе leo4proxy

Один модуль политики внутри leo4proxy выполняет опрос, хранит состояние и выдает два независимых разрешения. MQTT и RTP проверяют свое разрешение перед каждой попыткой внешнего подключения. Исходящий HTTP handler проверяет отдельный HTTPS-флаг после обработки локальных API и до внешнего соединения; входящий reverse proxy не получает эту проверку.

Запрет MQTT/RTP отменяет начатое подключение и закрывает действующие внешние соединения. Соединение, завершившее handshake после запрета, не должно начать передачу. RTP не накапливается для отправки после разрешения. Локальные TCP/UDP-слушатели сохраняются: поступление пакетов или подключения внутренних клиентов не запускают запрещенный внешний connect. Политика не должна реализовываться общим вызовом остановки прокси.

Внутренние клиенты и остальные tools не изменяются и не останавливаются. Потеря внешней связи — ожидаемый результат запрета, а не команда перезапустить клиента. Задача сохраняет локальный контракт leo4proxy; доставка накопленных сообщений и поведение клиентских служб находятся за ее границей. Этап не меняет топики, QoS, retain и presence.

### Контракт готовности и отсутствие рестартов

В [http_proxy.c](../tools/leo4proxy/src/http_proxy.c) локальные `/_leo4/info`, `/_leo4/status`, `/_leo4/sn` и существующие alias обслуживаются до внешнего proxying. `status=ready` зависит от наличия сертификата и `cert_ready`, а не от соединения с брокером. В [service_mgr.c](../tools/leo4proxy/src/service_mgr.c) служба объявляется `SERVICE_RUNNING` и имеет SCM failure actions с перезапуском после сбоя. Поэтому запрет не должен менять `cert_ready`, сертификат, SN, существующий смысл `ready`, состояние SCM или завершать процесс. Счетчики внешних соединений могут стать нулевыми, но это не отказ локальной службы.

Обработка политики должна работать и в служебном режиме, и в пути запуска [main.c](../tools/leo4proxy/src/main.c), включая обновление credentials. При необходимости диагностические поля добавляются отдельно, без переопределения существующих полей. Сохранение внутренних ответов, слушателей и состояния процесса можно проверить в leo4proxy; отсутствие рестартов остальных служб не доказано runtime и не заявляется как результат этого чтения.

Для объяснения остановки достаточно кодов фактов в существующем журнале: серверного `terminal_inactive` либо локального `policy_unavailable`. Расширение локального API диагностики оценивается после чтения кода; новый диагностический протокол здесь не вводится.

## План реализации

1. Использовать проверенные точки в tools/leo4proxy: MQTT handler, RTP state machine, HTTP route handler, reverse proxy, service manager и main. Сохранить локальные слушатели, ready/SN/cert_ready и SERVICE_RUNNING. Другие tools не читать и не изменять в этой задаче.
2. В ProcessingBackend добавить вычисление и маршрут с существующей terminal auth. Добавить маршрутизацию Nginx. Сохранить распознавание отключенных терминалов и существующий контракт licensebilling.
3. В leo4proxy добавить поллинг, доступное локальное хранение и независимые проверки MQTT/RTP и исходящего HTTPS, включая исключения. На backend HTTPS-флаг остается константой true.
4. В будущей реализации собрать leo4proxy для x86/x64 и выполнить проверки затронутых подпроектов. Изменения упаковки вне leo4proxy не входят в текущий scope и потребуют отдельного расширения задачи; здесь создается только документация.

## Критерии проверки реализации

- API возвращает разрешение и запрет для своего терминала; чужая идентичность отклоняется. Отключенный терминал получает политику без лицензирующего отказа.
- Запрет останавливает MQTT/RTP, включая гонку подключения; входящий HTTPS, локальные API и поллинг продолжаются. Локальные слушатели остаются доступны; ready, SN, certificate_found/cert_ready, состояние SCM и PID не меняются от политики.
- Отдельный HTTPS false запрещает обычные исходящие маршруты, сохраняя policy, certificates и licensebilling с допустимыми query/trailing slash. Входящий HTTPS не фильтруется. Подстроки и похожие имена путей не обходят исключения.
- Для HTTPS отсутствие поля, null, неверный тип, сетевой отказ, поврежденный ответ и перезапуск дают разрешение; они не отменяют независимый сохраненный запрет MQTT/RTP. Backend пока всегда выдает true.
- Неудачные запросы не продлевают запас. Граница 72 часов проверяется управляемым временем, без ожидания трех суток.
- Перезапуск сохраняет остаток запаса и серверный запрет. Потеря одной копии восстанавливается из другой; потеря обеих создает новые 72 часа.
- Сбой между записями, поврежденный JSON, расхождение поколений, отказ реестра/каталога и смена x86/x64 диагностируются, запускают доступный fallback и не приводят к падению службы или санкциям. Неоднозначное восстановление разрешается в пользу клиента.
- HTTP/TLS-ошибки, неверный SN и схема не становятся разрешающим ответом MQTT/RTP. Для HTTPS они включают разрешение по умолчанию. Продолжающийся поллинг позволяет получить новое серверное решение.

## Ограничения первого этапа

Удаление обеих копий дает новый запас, в том числе после серверного запрета. Это следствие согласованного поведения в пользу клиента. Реестр и JSON не защищают от администратора, отката диска или изменения бинарника. Защита от этих действий требует отдельного исследования злоупотреблений.

При исправном поллинге серверное изменение обнаруживается на следующем опросе, обычно в пределах 10 минут плюс время запроса. «Сразу» означает после получения ответа. При недоступном API работа может продолжаться до конца запаса.

Политика ограничивает внешние MQTT/RTP и, только при отдельном явном false, обычные исходящие HTTPS-маршруты через leo4proxy. Входящий HTTPS, локальные служебные API, три исключения и альтернативные прямые соединения не блокируются. Сертификат сохраняется. HTTPS-разрешение по умолчанию означает, что при отказе policy API будущая защита от исходящего спама ослабляется; это согласованный приоритет доступности клиента.

## Проверки отчета

Прочитаны модель Terminal, terminal auth и маршруты, документы и исходники leo4proxy. Серверный контракт реализован; локально прошли 138 тестов ProcessingBackend, Ruff check/format и Pyright app. Существующий suite выдает 20 предупреждений, в основном о старых AsyncMock fixtures и deprecated TestClient; новых отказов нет. Backend тестируется с mock DB и simulated cert headers, без production credentials. На момент этого коммита deployment еще не проверен; фактический результат будет записан следующим документальным обновлением. Исходники leo4proxy не изменены, его сборка и runtime не проверялись.
