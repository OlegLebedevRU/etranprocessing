# GitHub и выпуск серверных компонентов

Этот регламент определяет выбор источника, способ доставки и проверку результата.
Он не даёт разрешения на деплой: доступ к builder `176.108.247.249` применяется
только по прямому указанию пользователя, как требует `AGENTS.md`.

## Исходники и GitHub

| Компонент | Репозиторий | Базовая ветка | Что проверять перед выпуском |
|---|---|---|---|
| ProcessingBackend, MenuBuilder и общий контур | `etranprocessing` | `main` | полный SHA, чистый checkout, затронутые компоненты |
| app1 | `iot-rpc-rest-app` | `master` | полный SHA отдельно от `etranprocessing` |

Работайте в чистом checkout, созданном от актуального `origin/main` или
`origin/master`. Грязную рабочую ветку пользователя не очищайте и не используйте
как источник релиза. Коммиты и результаты ревью должны быть достижимы из
соответствующей базовой ветки; факт локального commit или публикации образа
этого не подтверждает.

На Windows сначала проверьте `whoami`, `gh auth status`, `git remote -v` и
`git ls-remote origin refs/heads/main` (для app1 — `master`). `gh` и Git Credential
Manager работают в профиле текущей учётной записи Windows. Запуск агента от
другой учётной записи может не видеть вход, хотя интерактивный пользователь
авторизован. В этом случае используйте штатный `gh auth login` и
`gh auth setup-git` в том же профиле либо вернитесь к рабочему профилю;
не копируйте приватные SSH-ключи и токены в checkout. Затем используйте обычный
`git push` и независимо сверьте удалённый SHA через `git ls-remote` или `gh api`.
При системной ошибке `git-remote-https` остановите push, сохраните локальный
commit и устраните ошибку профиля/транспорта. Git Data API не является штатной
заменой `git push`: его разовое применение к merge 1.9.2 было восстановлением
после сбоя транспорта, с проверкой обоих родителей и точного tree SHA.

## Выбор маршрута деплоя

Для управляемых образов `etranprocessing` при **явно согласованном** маршруте
используйте [бета-регламент](ops_run-beta-ci-cd.md): Git `main` → builder
`176.108.247.249` → registry с immutable digest → pull на production
`87.242.100.34`. Builder собирает и публикует; production только подтягивает
проверенный digest. До отчёта об успехе сверяйте SHA исходников, digest/ID
работающего образа, health и поведение затронутого сервиса. Не пересоздавайте
соседние контейнеры. Для общих моделей и миграций порядок задаёт
`ProcessingBackend`.

При отсутствии прямого указания использовать builder действуют правила
`AGENTS.md` и [основной runbook](ops_run-devops-runbook.md): production host
`87.242.100.34`, ключ оператора `d:\.ssh\id_ed25519`. Для builder используется
отдельный `d:\.ssh\free-tier-cloud_ru`; на production из builder — отдельный
deploy key и проверенный `known_hosts`. Не отключайте проверку host key.
Если SSH ищет `known_hosts` под `C:\Windows`, проверьте учётную запись и её
профиль; это не доказательство смены ключа хоста.

Для `app1` сначала читайте его собственные `AGENTS.md` и
`docs/manual-app1-deploy-runbook.md`. На принятом master8c2be80 штатный маршрут
теперь builder → private registry → production pull по immutable digest;
`deploy/registry_app1.py` запускается из корня чистого checkout. Исторические
инструкции ручной сборки на production не задают текущий default. Это изменение
владельца app1 не отменяет обязательного прямого разрешения на builder в данном
репозитории. Для RPC7011 такое разрешение получено от пользователя; проверенные
ревизии и digests находятся в [handoff](../.agent-context/tasks/active/2026-10-04-rpc7011-implementation.md).
Пересоздаётся только app1 (`--no-deps`); сохраняйте `.env`, применяйте его собственные
миграции и проверяйте health.

## Локальные копии и следы проверок

Перед удалением worktree проверьте: он не текущий, чистый, его HEAD достижим
из свежего `origin/main`, а ветка не содержит уникального результата. Локальные
ветки удаляются отдельно после worktree; удалённые ветки этим не затрагиваются.
Не запускайте `git clean -fdx` в общей рабочей копии. В `D:\.codex` удаляйте
только явно перечисленные и проверенные временные файлы; файлы с доступами,
резервными конфигами и незавершённым evidence сохраняйте.

Для проверенного списка используйте `deploy/Clear-ReviewedLocalResidue.ps1`:
сначала запуск без `-Execute` показывает цели, затем пользователь запускает
его с `-Execute`. Manifest фиксирует точные пути, SHA веток, размеры и SHA-256
файлов. При изменении хотя бы одной цели скрипт останавливается до удаления.
