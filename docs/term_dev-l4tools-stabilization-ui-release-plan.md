# L4 Tools: финальные изменения, стабилизация, UI и подписанный выпуск

Дата: 2026-10-02. Статус: исследование и план; новые исправления и выпуск ещё не выполнены.

## Цель и границы

Поднять финальные результаты всего tools, сохранить принятый UI l4pin,
устранить подтверждённые проблемы надёжности и сделать l4setup понятным
установщиком для первой установки и обновления. Закрепить единственный
повторяемый выпуск через существующие скрипты подписи EXE с timestamp.
Владельцы: инструменты — свои native-компоненты; упаковка и подпись —
tools/release и l4setup. Серверные API и MQTT-контракты этим планом не меняются.

Пользователь разрешил пошаговую реализацию. Единый [отчёт каскада](term_dev-l4tools-cascade-report.md) фиксирует каждый этап. На момент подготовки плана сборки, установка, потребление
PIN, изменения служб и публикация в рамках этого документа не выполнялись.
Незакоммиченные результаты основной рабочей папки нельзя заменять содержимым
базовой ветки. Сверку вести по файлам и контрактам, а не сливать старые ветки целиком.

## Исследование Windows 10: учитывать, но проверять

Внешний источник: `D:\.codex\check_one_fail_case_l4tools_windows-10-pro.md`.
Прочитан 2026-10-02. Его выводы — вопросы для стабилизации, не подтверждение
всех причин на текущем терминале или доказательство исправлений.

Подтверждено чтением актуального кода:

- l4pin HTTP enrollment использует DEFAULT_PROXY без вызова WinHttpSetTimeouts
  на этом пути. Discovery имеет отдельные таймауты.
- l4superv svc_stop_and_kill запрашивает stop и затем пытается TerminateProcess
  по ранее прочитанному PID, без ожидания SERVICE_STOPPED.
- DEFAULT_PROXY встречается в discovery l4con/l4desk, probes l4setup и
  proxy_client l4superv. policy leo4proxy использует NO_PROXY и таймауты 5 с.
- l4setup создаёт шрифты с фиксированной высотой в пикселях; manifest объявляет
  DPI awareness. Сам manifest не обеспечивает корректную перекладку UI.

Остаётся проверить: связь WPAD с конкретными зависаниями; все времена ожидания;
владение TLS credentials и завершение работников при ротации сертификата;
контекст crash handler и абсолютный путь crash log; причины watchdog restart;
binPath, параметры, recovery и DisplayName служб во всех способах установки.
Event7034 сам по себе не отличает crash от принудительного завершения.
Не менять системные DACL/WinHttpAutoProxySvc и не отключать защитное ПО
автоматически ради исправления приложения.

Для loopback использовать прямой HTTP без WPAD; для внешних адресов сначала
определить поддерживаемую proxy-политику: явный host не исключает необходимость
корпоративного прокси. Требуются ограниченное время операции, явная ошибка и
отсутствие каскадных рестартов. TCP connect не заменяет проверку HTTP ready.

## Порядок реализации по инструментам

### 0. Сверка состава

Зафиксировать таблицу финальных исходников/веток/версий всего tools и diff с
main. Отдельно установить регрессию l4pin и связанных переходов идентичности.
Сопоставить пакет, source, staged EXE и установленные версии. Не менять номер
нового пакета до определения его итогового состава. 1.9.3 не перезаписывать.

### 1. l4pin

Восстановить принятый GUI вместе с сертификатным исправлением, ресурсами и
штатной сборкой. Затем ограничить enrollment/discovery по времени, устранить
зависимость loopback от WPAD, сверить парсинг info и выбор endpoint.
Сохранить CLI, видимый PIN и понятное принудительное перевыпускание;
объяснить последствия Force, не терять действующий сертификат при отказе.
PIN не попадает в журналы. GUI должен показывать занятую операцию и итог ошибки.

Проверка: x86/x64/default, certificate tests, запуск GUI без PIN; контролируемые
отказ/timeout с сохранением старого сертификата. Реальную выдачу проводить
отдельно с согласованным тестовым PIN, не расходовать действующий ради UI.

### 2. l4superv

Ожидать завершение службы с конечным сроком и проверкой актуального состояния.
Принудительное завершение — после исчерпания ожидания, с повторной проверкой
принадлежности процесса; не убивать чужой процесс по устаревшему PID.
Проверить NO_PROXY для локального probe, причины restart и ограничение повторов.
Отличать недоступность внешней сети/запрет policy от неисправности локальной службы.
Сохранить переход сертификата/SN и правильную перестройку Mosquitto/l4con.

Проверка: обычный stop/start, зависшая остановка, потеря probe, смена идентичности,
повторяющиеся отказы. Штатный stop не должен выглядеть как crash7034.

### 3. leo4proxy

Сверить выбор сертификата с терминальным контрактом и l4pin/l4superv: не выдавать
ready с неподходящей идентичностью. Аудит 1.9.3 уже выявил выбор старого certsrv
по email/NotBefore без отдельной проверки issuer; поддержку legacy согласовать
до изменения поведения. Проверить lifetime TLS credentials, stop/join,
ротацию, диагностику crash без интерактивного ожидания в службе.
Сохранить клиентскую стратегию policy и локальный ready независимо от MQTT/RTP.

Проверка: x86/x64, policy tests, ротация при активных соединениях, отсутствие
внешних маршрутов без рестарта внутренних клиентов, доступность HTTPS.

### 4. l4con

Включить финальную 1.9.4 в будущий пакет; исправить только подтверждённые
проблемы локального discovery/proxy/timeouts. Сохранить тип extra_service,
presence, MQTT5, event75 и разрешение пользовательских событий только текущему Job.
Проверка: существующие тесты MQTT/IPC/Job/Unicode, ограничение потока и tenant E2E
при наличии выделенных временных ключей. Изменение MQTT-клиента требует
соблюдения обязательного опроса AGENTS; ранее для l4con согласован extra_service.

### 5. Mosquitto

Сверить генераторы конфигурации и источник SN с фактически выбранной допустимой
идентичностью. Не принимать stale info за основание переписать конфигурацию.
Проверить reconnect/log growth при серверном запрете MQTT, сохранив локальный
брокер для внутренних клиентов. Не менять протокол и routing без подтверждённой
необходимости. Проверить переход SN и отсутствие старого SN в новом мосте.

### 6. l4setup: процесс и новый интерфейс

Процесс: сохранить безопасную установку/upgrade, порядок остановки/запуска,
сертификат и результаты проверки. Сверить drainage и принудительные kill,
таймауты probe, определения installed/package/component versions и итог ошибок.

Предлагаемый интерфейс:

- Основное окно ориентировочно 1000×700 при 100% DPI, с изменением размера и
  ограничением рабочей областью экрана. Размер — отправная точка для проверки,
  на 1366×768 окно должно полностью помещаться.
- Две панели: слева операция, установленная и новая версии, путь, этапы,
  состояния служб и заметная сводка проблем; справа постоянный подробный журнал.
  На небольшом экране панели перекладываются, элементы не обрезаются.
- Перед стартом ясно «Установить L4 Tools» либо «Обновить L4 Tools с … до …»;
  для совпадающей/более новой версии описать реальную доступную операцию,
  не маскировать её как обычный upgrade. Не менять молча CLI-семантику.
- Нижняя панель: справа основная акцентная кнопка «Установить»/«Обновить» и
  вторичная «Отмена». На успехе — «Готово». На ошибке — «Повторить» только
  если текущий pipeline допускает безопасный повтор, и «Закрыть».
- «Копировать журнал», «Открыть файл» и версии компонентов находятся у журнала
  или в подробностях, не конкурируют с основным действием. Отдельная постоянная
  кнопка Retry и Hide Details в главной панели не нужны.
- Синий акцент основного действия, зелёный успех, янтарное предупреждение,
  красная ошибка. Каждое состояние также имеет текст/значок: цвет не единственный
  способ распознать результат. Не перерисовывать весь Win32 UI без необходимости.
- Segoe UI с читаемым базовым размером около 10–11pt, более крупный заголовок;
  журнал — моноширинный читаемый шрифт. DPI-aware layout/шрифты, обработка смены
  DPI, fallback для Windows7; проверка 100/125/150/200%, клавиатуры и high contrast.
- Журнал с временем/этапом/уровнем и выделением warning/error; выбор и копирование,
  автопрокрутка только пока пользователь не читает старые строки. Ограничение
  памяти UI не должно уничтожать полный файловый журнал.
- Ошибка показывается отдельной сводкой: что не получилось, на каком этапе,
  что сохранено и какое следующее действие доступно. Не заставлять искать её
  среди строк лога; не показывать успех, если обязательный этап не завершён.
- Во время работы исключить повторный старт. Отмена/закрытие отражают фактическую
  возможность безопасно остановить этап; нельзя просто оборвать worker.

Сначала подготовить видимые состояния до старта, upgrade, выполнение, warning,
failure и success; затем реализовать Win32 UI поверх существующего engine.
Проверять отдельно внешний вид и реальную установку/обновление/отказ.
Красивый native UI достижим: сейчас мешают плотная фиксированная форма,
одинаковый вес действий и слабая иерархия статусов, а не ограничение платформы.

### 7. Другие инструменты в scope всего tools

## Отдельный обязательный шаг: сборка → подпись → timestamp → пакет

Постоянный первичный runbook: [tools/release/README.md](../tools/release/README.md).
Использовать существующие скрипты, не создавать новый рецепт при каждом выпуске:

1. Штатная проверка/сборка `tools/build_dist.cmd <version>` и staging обоих payload.
   Сверить источник, версии, архитектуры и обязательные результаты тестов.
2. Передать оператору одну команду существующего Complete-SignedRelease.ps1;
   дождаться результата подписи. PFX и пароль только вне Git/через environment.
3. Скрипт подписывает staged EXE x86/x64 через Sign-Executables.ps1 с
   `/fd SHA256 /tr <RFC3161 endpoint> /td SHA256`, упаковывает подписанные payload,
   пересобирает встроивший их l4setup, подписывает финальный установщик,
   пересоздаёт manifest и SHA256SUMS. Не менять файлы после подписи.
4. Независимо проверить Authenticode, timestamp, архитектуры/версии и хеши
   именно извлечённых payload финального установщика. Сверить все входящие EXE,
   не закреплять число «18» как вечную истину при изменении состава пакета.
5. Публиковать только после успешных gates. Отказ timestamp/подписи/тестов
   останавливает выпуск. Timestamp сохраняет проверяемость после истечения
   сертификата подписанта при выполнении правил доверия; не отменяет отзыв
   сертификата или повреждение файла.

Команда оператора из выбранного checkout (шаблон, версия ещё не назначена):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File '.\tools\release\Complete-SignedRelease.ps1' -PfxPath '<PFX вне репозитория>' -Version '<версия выпуска>'
```

Обновить ссылки на этот runbook из общего контекста tools и release handoff.
При реализации проверить полноту manifest, проверку доверия всех подписей,
поведение timestamp failure и недопустимость публикации unsigned payload.

## Критерий завершения и evidence

Финальные наработки сведены без потерь; каждый изменённый native инструмент
прошёл x86/x64/default и необходимые тесты. Windows10 с недоступным WPAD,
обычная остановка, ротация и server-disabled проверены контролируемыми сценариями.
UI принят на разных DPI/разрешениях, включая понятный upgrade и заметную ошибку.
Установщик содержит согласованные подписанные EXE с timestamp; проверены
извлечённые payload. Runtime, неподтверждённые случаи и остаточные риски
отдельно отражены в handoff. До этих проверок не заявлять выпуск готовым.
