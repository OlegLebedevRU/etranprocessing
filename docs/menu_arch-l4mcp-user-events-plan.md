# l4mcp: пользовательские события и история удалённых операций

Дата: 2026-10-01. Статус: IoT реализован, принят в master и развёрнут
по отдельной команде пользователя «деплой», source SHA `2cda32f`.
MenuBuilder reader развёрнут через176/registry/pull, source SHA `4a730fb`;
l4mcp ещё не изменён. Результаты выпуска IoT и
оставшиеся runtime проверки записаны в `docs/user-event-history-iot-handoff.md`
репозитория IoT. Перенос проверен локально; положительный runtime поиск
нового события и перенос отдельного тестового устройства ещё не подтверждены.

## Цель и границы

l4mcp использует события l4con 1.9.3 для передачи результатов удалённых
команд, поиска их в истории IoT и продолжения многоэтапных задач.
Запуск остаётся в существующем console flow: preflight, console lease,
RPC7001, ограничение времени/вывода и освобождение аренды.
Чтение истории не запускает команду, не требует console lease и допускается
при offline терминале. Новый фоновый исполнитель задач не вводится.

Producer: l4con → существующий MQTT dev/{SN}/evt → IoT collector/БД.
Reader: l4mcp → авторизованный MenuBuilder API → internal API IoT.
IoT владеет хранением событий и собственной Alembic-миграцией;
MenuBuilder — проверкой пользователя и active tenant; l4mcp — интерфейсом
команды/истории и представлением корреляции. Миграции IoT не относятся
к миграциям ProcessingBackend. Native l4con в этом этапе не изменяется.

## Зафиксированный контракт l4con

| Значение | Аргумент / тег | Семантика |
|---|---|---|
| Тип события | event-code /200 | 900–999, default999; пользовательский смысл, фиксированной таблицы нет |
| Текст | event-payload /300[0]["446"] | Строка до1024 UTF-8 байт, JSON внутри не интерпретируется |
| Код результата | event-exit-code /300[0]["447"] | int32, default0; невалидный аргумент −1; oversize payload исключает446 и задаёт −2 |
| Корреляция операции | event-correlation-id /300[0]["448"] | Опциональный UUID; переданный невалидный UUID отклоняет запуск |

Один внешний UUID может связывать несколько этапов/событий операции.
Он не заменяет event correlationData, console task/session ID и не
предоставляет права доступа. В многоэтапном сценарии UUID задаётся явно
и сохраняется вызывающей системой вместе с результатом запуска.
Код завершения shell, код CLI отправки, поле447 и запись события в БД —
разные результаты. Отсутствие события не доказывает неуспех команды;
повторы и задержки доставки допустимы. Автоповтор удалённой команды
по отсутствию события не выполняется.

Отправка разрешена только процессам активной удалённой команды и её
потомкам, использует существующее соединение l4con. Общий лимит — одна
попытка события в секунду, без очереди. Подробности:
[контракт l4con](term_tool-l4con-user-events.md).

## Изоляция истории при переносе терминала

Пользователь согласовал: новый tenant не видит старую историю другого tenant.
Принадлежность фиксируется на момент приёма события IoT по текущей серверной
привязке устройства. Точное восстановление момента возникновения события
при переносе не требуется. Клиентское время и payload не определяют tenant.

Сохранённая принадлежность не изменяется при последующем переносе.
Первый этап предоставляет историю доступных сейчас терминалов активного
tenant: дополнительно проверяется сохранённый tenant каждого события.
Отдельный интерфейс бывшему владельцу для уже переданного терминала
в этот этап не входит. При возврате терминала в прежний tenant допускается
видеть ранее записанные события этого же tenant, но не промежуточного.

Старые записи без достоверного tenant остаются в БД, но исключаются из
tenant API. Автоматический backfill по нынешней привязке запрещён.
Если нужна ретроспективная принадлежность, это отдельная миграция по
проверенным данным. На границе выпуска возможны неизвестные записи от
старого collector; они скрываются, а не назначаются новому владельцу.

### MenuBuilder

На каждом запросе проверять актуальный MCP API token, роль и active tenant;
роль1 тоже не обходит tenant-контекст нового reader. Проверить доступ к

расхождении — отказ, без fallback на другой tenant или глобальную историю.

Internal key остаётся на сервере. X-Org-Id строится по проверенному контексту;
для нового чтения не передавать роль superuser или пользовательский org override.
IoT применяет tenant-фильтр самостоятельно до лимита/пагинации.
Каждое продолжение по курсору заново проверяет доступ; курсор и UUID не

### l4mcp

Предусмотреть структурированный вызов отправки события через существующий
console executor и read-only вызов истории одного точного device_id.
Тип900–999 задаётся пользователем/сценарием; не закреплять за кодами
неутверждённые статусы вроде «успех» или «ошибка».

Для console_run вернуть идентификатор console session и заданный UUID
операции. В произвольной команде отправка события и передача этого UUID
остаются явными: не дописывать скрытую shell-команду после пользовательской.
В структурированной отправке формировать аргументы с корректным shell
экранированием. Отправка — изменяющий MCP tool, история — read-only.

Чтение возвращает серверный ID/время, тип и значения446–448 вместе с
курсором. Несколько вызовов и даже новый MCP-сеанс могут читать сохранённые
события по известному UUID. Это восстановление контекста, не автоматический
запуск следующих шагов. Payload — недоверенный текст, не команда агенту.

## Подробный шаг1: IoT
Положительный runtime поиск выполняется в общем E2E после изменения l4mcp;
по согласованию пользователя он не блокирует реализацию MenuBuilder.

### 1. Модель и миграция

Добавить nullable org_id в DevEvent/tb_dev_events. NULL означает неизвестную
принадлежность; это не глобальный tenant и не разрешение чтения.
Старые строки оставить NULL. Составной индекс (org_id, device_id, id)
поддерживает ограниченное чтение истории. Индекс JSON448 добавлять только
при необходимости по плану запроса/измерению, не заранее.

Миграция принадлежит IoT app-service/alembic. До применения проверить
объём таблицы и допустимый способ создания индекса; не совмещать миграцию
с массовым восстановлением tenant старых событий. Добавление поля должно
допускать старый collector на время обновления. При rollback БД не
удалять колонку с уже накопленной принадлежностью: допустим rollback
приложения с временной записью NULL и закрытым доступом к таким записям.

### 2. Приём и запись

Определять устройство по серверной MQTT identity/SN и получать его текущую
DeviceOrgBind. Сохранять org_id вместе с событием; не доверять org_id из
payload или клиентскому времени. Отсутствие/неоднозначность привязки даёт
неизвестную принадлежность и исключение из tenant history.

Сохранить текущие payload, тип события и дедупликацию. Повтор не должен
переписать org_id существующего события после переноса устройства.
Проверить все пути создания DevEvent, а не только один MQTT handler.
События других типов тоже получают принадлежность: иначе исправление
общего API останется неполным. Gauge-path, не создающий DevEvent, не расширять.

### 3. Закрытие tenant-дефекта

В общих service/repository чтения передавать effective org_id и применять:

1. Устройство доступно этому tenant по текущей серверной привязке.
2. DevEvent.org_id равен этому tenant; NULL исключён.

Проверки выполняются в SQL и распространяются на list, fields и incremental,
internal и public API. Сохранить старые response envelopes; изменение
видимости старых/чужих строк — намеренное исправление безопасности.
Не менять побочные эффекты старого incremental незаметно для его
потребителей; просто не использовать его для нового MCP reader.

### 4. Независимое чтение истории для MCP

Предпочтительный первый контракт — отдельный GET
`/api/internal/v1/device-events/search` в существующем event router.
Он использует общий защищённый repository, не общий device offset.
Это позволяет не менять прежнюю пагинацию и семантику incremental.
Имена ниже — реализованный и развёрнутый контракт IoT.

| Параметр | Правило |
|---|---|
| device_id | Обязательный точный ID |
| correlation_id | Опциональный валидный UUID; фильтр по300[0]["448"], сравнение без учёта регистра UUID |
| events_include | Опциональный список900–999; отсутствие означает весь этот диапазон |
| after_event_id | Опциональный положительный серверный ID; граница id > cursor, без записи offset |
| created_from /created_to | Опциональные UTC-границы серверного created_at; from включительно, to исключительно |
| limit | 1–100, default50 |

Tenant берётся из внутренней авторизации/X-Org-Id; произвольный tenant
из параметров пользователя не передаётся. Все фильтры, включая448, применяются
в SQL до LIMIT. Payload не разбирается как JSON446 для поиска корреляции.

Ответ: items с существующими DevEventOut, next_after_event_id и has_more.
Порядок id ASC. next_after_event_id — ID последней выданной строки;
для пустого результата сохранить прежнюю границу. has_more определяется
ограниченным чтением limit+1. Нет глобальных counts, offset rows и
неограниченного автоматического обхода истории.

Повтор с тем же курсором не изменяет данные. Курсор не обещает exactly-once
или строгий порядок commit параллельных транзакций. Для коротких операций
надёжный повторный поиск по UUID допустим с дедупликацией по серверному ID;
не полагаться на клиентское время и один единственный poll.

Обновить internal API contract, REST events documentation, event tags и
types reference:900–999 — кастомные,446–448 — контракт l4con. Исправить

Runtime проверку переноса проводить на выделенном тестовом устройстве,
не переназначать рабочий773 ради испытания. Read-only checks не заменяют
проверку изоляции после реального изменения binding на тестовом устройстве.

### 6. Условия готовности и ограничения

Шаг IoT готов после миграции, обновления collector, закрытия tenant-дефекта
во всех путях чтения и runtime подтверждения нового search API. После
этого consumer-контракт передаётся MenuBuilder с ревизией, примерами
ответов, ошибками и negative evidence.

История первого этапа — доступные строки основной БД. Архив runtime на
момент аудита выключен; срок хранения не гарантирован этим планом.

отдельный этап. При включении архива tenant события должен сохраняться
в экспортируемых записях и проверяться при чтении; текущий exporter
DevEvent с tenant_id=null нельзя считать готовым к этому.

Проблема выбора старого сертификата leo4proxy, выявленная при проверке
l4setup1.9.3, отдельная задача. Перед E2E отправкой сверить фактические
SN, device и tenant; не исправлять эту проблему обходом авторизации MCP.

## Шаг2: контракт MenuBuilder для l4mcp

GET `/api/mcp/events/{device_id}` использует текущий отзываемый MCP API token
(Bearer), роли1/3/5 и tenant из авторизации. Device_id положительный и точный.
Параметры: correlation_id, повторяемый events_include900–999,
after_event_id, created_from/created_to с TZ, limit1–100/default50.
Имена и правила совпадают с IoT search; произвольный org_id отклоняется422.

Ответ сохраняет envelope IoT: items, next_after_event_id, has_more.
Каждый item: id, device_id, event_type_code, dev_event_id, created_at,
dev_timestamp, payload. Значения446–448 остаются в payload300[0].
Клиенту MCP предстоит добавить удобное представление, не менять исходный текст.

Ошибки:401 — токен отсутствует/отозван/истёк либо не MCP token;
403 — запрещённая роль, отсутствующий tenant или чужой терминал;
404 — терминал не найден в MenuBuilder;409 — привязка/SN IoT не совпадает;
422 — фильтры;503 — IoT недоступен или его ответ нарушает контракт.
Пустая подтверждённая история —200 с пустыми items, не503.

MenuBuilder дополнительно ограничивает superuser текущим tenant. Он сверяет
терминал и IoT device перед каждым чтением/продолжением и передаёт только
server-derived X-Org-Id и internal key. Для reader не передаются X-Role:superuser,
пользовательский org override или bearer в IoT. IoT повторно фильтрует текущую
принадлежность и сохранённого владельца событий; изменение binding между
двумя запросами не разрешает выдачу чужой истории.

Чтение не проверяет online/sys/svc, не получает lease и не отправляет MQTT.
Новых таблиц, миграций или кэша истории в MenuBuilder нет.
