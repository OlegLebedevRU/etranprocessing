# Аппаратный HEVC: сквозной план и оркестрация
Версия плана 1.0 · 22 октября 2026 · статус: исходный план; P0 фиксирует contract 2.0.0, реализация следующих этапов отдельно.

## 1. Решение
Добавить H.265/HEVC для рабочего стола через аппаратный Media Foundation MFT. Существующие H.264 агенты, API-клиенты и источники продолжают работать без обновления. На сервере нет перекодирования. Браузерная поддержка кодеков принята как исходное условие пользователя.

Кодек выбирается до создания медиатракта и фиксируется для одного stream_instance_id. Auto выбирает HEVC только при свежем положительном результате проверки агента и готовности всей серверной цепочки; иначе H.264. Запрос старого клиента без выбора кодека означает H.264 при создании нового потока. Присоединение наблюдателя к уже работающему потоку не создаёт новый поток и не выбирает кодек заново.

Первая версия при отказе HEVC завершает поток и передаёт структурированную причину. Никакого автоматического переключения HEVC → H.264, массового переподключения зрителей или нового цикла автозапуска. Уже существующее поведение восстановления H.264 сохраняется, кроме отдельно проверенных исправлений ошибок.

## 2. Почему не менять кодек при аппаратном отказе
В текущей модели один закодированный поток обслуживает множество наблюдателей. Замена H.265 на H.264 изменяет описание медиа и может потребовать нового SDP/пересоздания подписок у всех зрителей. Даже успешный запуск H.264 на агенте не означает, что уже подключённые клиенты начали его декодировать.

Будущий повтор с тем же кодеком перспективнее: сохраняются mountpoint, клиентские PeerConnection и согласованные параметры. Но этого недостаточно для обещания бесшовного восстановления. Нужно проверить RTP sequence/timestamp/SSRC, очистку старой очереди, параметрические наборы, IDR, RTCP и поведение Janus при новом encoder instance. Перезапуск процесса обычно меняет часть этих условий.

Этап 1 фиксирует только контракт:
- current_stream_terminated=true: эта попытка окончательно остановлена;
- recovery_class=reprobe_required: возможна новая попытка после проверки;
- suggested_action=retry_same_codec: подсказка будущей политике, не команда;
- auto_restart_allowed=false: автоматизация выключена;
- scope=stream: отказ относится к видеопотоку, а не к жизни агента.

«Восстановимый» не означает, что текущая сессия остаётся running, lease продлевается или рестарт точно удастся. Следующий ручной запуск создаёт новый stream_instance_id и проходит обычную авторизацию. После runtime-ошибки HEVC capability становится temporarily_unavailable, пока повторная проверка не вернёт ready.

### G-SERVER-READY: что обязано быть сделано до агента
1. В целевом окружении развёрнуты совместимые IoT, l4media и MenuBuilder, зафиксированы полные SHA и digest.
2. Новый UI показывает Auto/H.264/H.265 и причины недоступности; HEVC ещё не объявляется доступным реальному старому агенту.
3. Авторизованный тестовый источник передаёт заранее подготовленный HEVC RTP через тот же L4RTP/1 ingress и Janus, а не напрямую в браузер.
4. В целевом MenuBuilder действительно растут decoded frames. Есть тестовый текст/таблица, читаемые после доставки.
5. Проверены 1 и 3 авторизованных Janus-подписки, позднее подключение, уход одной подписки без остановки остальных, общий отказ источника. Использовать разрешённую текущую модель доступа. Если независимые viewer leases сейчас не поддержаны, не обходить запрет; расширение многопользовательского допуска вынести отдельно и явно указать границу теста.
6. Старый H.264 агент и старый API запрос прошли регрессию на обновлённом сервере.
7. Нет программного HEVC в продукте. Для серверного теста используется готовый образец/поток камеры и RTP replay; источник явно тестовый.
8. Все тестовые аренды/маршруты освобождены; сохранены сценарий повторного запуска и комплект отката.

До прохождения этого барьера сервер считается «реализован локально», но не «готов к отладке агента».

## 6. Выбор и фиксация параметров
Новый BFF выступает единым инициатором prepare/start:
- получить и проверить актуальные capability агента;
- выбрать конкретные codec/profile/size/fps и привязать их к новым stream_instance_id + media descriptor revision;
- создать route/mountpoint с тем же descriptor до первого RTP;
- послать START с теми же параметрами;
- дождаться подтверждённого старта; READY содержит фактические параметры;
- различать «процесс стартовал», «RTP пришёл», «первый кадр декодирован».

В l4media и IoT одинаковый stream_instance_id с другим codec/profile/источником возвращает conflict, не already_running. Резервирование и истечение незавершённого prepare ограничены сроком lease. Компенсация частичного запуска адресует только собственные идентификаторы.

Любой новый наблюдатель получает фактический descriptor существующего потока. Он не может сменить кодек, остановить producer при своём disconnect или продлить publisher lease от своего имени. При завершении producer всем наблюдателям приходит один и тот же terminal outcome; освобождение ресурсов идемпотентно.

## 7. Совместимость и выпуск
Сначала разворачиваются серверные dual readers, затем UI, затем новые агенты. Новые возможности скрыты feature gate до сквозной проверки. H.264 не мигрируется массово.

Новый агент по умолчанию говорит старым CTL v1. Расширение включается только после явного согласования с новым сервером. Старые строгие схемы не должны получать ни новых top-level полей, ни нового v без предварительного согласования. Откат на старый сервер требует сначала запретить новые v2 сессии, завершить существующие HEVC сессии и сбросить negotiated state; просто откатить контейнер при живых v2 publisher нельзя.

Использовать совместимые добавления в хранение данных. До отката старого reader остановить и очистить/сохранить отдельно новые HEVC записи, чтобы они не были прочитаны как H.264. Старый двоичный протокол IPC остаётся байтово неизменным.

## 8. Доставка результата исполнителями
Каждое задание завершается handoff: полные SHA, изменённые файлы, контракт/fixtures revision, выполненные проверки, не выполненные проверки, остаточные ограничения, инструкции запуска и отката. Слово «готов» сопровождается уровнем доказательства: static / unit / integration / deployed / real-hardware.

Проектные требования к сборке, подписи и релизам применяются на этапе реализации. Этот комплект содержит план; изменения репозиториев, сборки, серверный деплой и аппаратные тесты в текущей задаче не выполнялись.
