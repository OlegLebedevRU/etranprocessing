# Стандарт именования технической документации etranprocessing

Настоящий стандарт определяет обязательные правила формирования имен файлов активной технической, архитектурной и эксплуатационной документации платформы `etranprocessing`.

---

## 1. Базовый формат и формула префикса

Имя каждого активного документа в каталоге `docs/` формируется по единому шаблону:

```text
{СФЕРА}_{ФЛОУ}-{дескриптивное-имя}.md
```

### Составляющие формулы:
1. **`СФЕРА` (Мнемокод 1)** — фиксированный код из 3–5 латинских букв в нижнем регистре, определяющий уровень охвата системы или конкретный подпроект.
2. **`_` (Разделитель кодов)** — символ нижнего подчеркивания, объединяющий два мнемокода в компактный префиксный тег.
3. **`ФЛОУ` (Мнемокод 2)** — фиксированный код из 3–4 латинских букв в нижнем регистре, определяющий конкретный функциональный поток, крупный участок или домен документа.
4. **`-` (Разделитель префикса)** — дефис, отделяющий стандартизированный префикс от содержательного имени.
5. **`дескриптивное-имя`** — понятное название файла в формате `kebab-case` (строчные латинские буквы, слова разделены дефисами), отражающее конкретную тему документа.

## 2. Словарь мнемокодов 1-го уровня (`СФЕРА`)

| Мнемокод | Область / Подпроект | Область применения и критерии выбора |
|---|---|---|
| **`etran`** | Общесистемный контур | Сквозные архитектурные документы, охватывающие всю платформу и несколько подпроектов, стандарты проектирования, соглашения для разработчиков и ИИ-агентов. |
| **`proc`** | `ProcessingBackend` | Сервис обработки платежей терминалов, mTLS-аутентификация, tech gate, license billing check, транзакционные таблицы PostgreSQL. |
| **`menu`** | `MenuBuilder` | Подсистема управления меню и портал администратора: React SPA фронтенд, backend меню, API биллинга и организаций, мультитенантность. |
| **`term`** | Терминалы и оборудование | Терминальный контур (киоски): нативные утилиты L4 Suite (`l4superv`, `l4pin`, `l4con`), протоколы обмена, телеметрия, клиентские приложения. |
| **`ops`** | DevOps и инфраструктура | Инфраструктура серверов, обратные прокси Nginx, SSL-терминация, регламенты деплоя, ранбуки эксплуатации, мониторинг и диагностика. |

## 3. Словарь мнемокодов 2-го уровня (`ФЛОУ`)

| Мнемокод | Функциональный поток / Участок | Описание и тематика |
|---|---|---|
| **`arch`** | Архитектура и анализ | Общие архитектурные концепции, системный анализ, доменные модели, сквозные диаграммы потоков. |
| **`data`** | Данные и схема БД | Модели данных, разграничение владения таблицами БД (`shared/etranprocessing_db`), правила миграций Alembic. |
| **`auth`** | Аутентификация и безопасность | Аутентификация пользователей, мультитенантность, JWT-токены (RS256), сессии в cookie/БД, разграничение прав. |
| **`bill`** | Лицензирование и биллинг | Математика и правила биллинга лицензий, расчет периодов с якорем, статусы терминалов, корзина и чекаут. |
| **`cert`** | Инфраструктура сертификатов | mTLS терминалов, выпуск клиентских сертификатов через двухфакторный PIN, криптопровайдеры (CNG / CryptoAPI), PKI. |
| **`pay`** | Платежный процессинг | Обработка финансовых транзакций от киосков, шлюзы TSP, параметры платежей, агрегация балансов терминалов. |
| **`ui`** | Фронтенд и интерфейс | Архитектура SPA, дизайн-система Ant Design 6, токены оформления, таблицы, формы, клиентские состояния. |
| **`tool`** | Нативные терминальные утилиты | Разработка и эксплуатация вспомогательного ПО для киосков (`l4superv`, `l4pin`, `l4mon`, `l4route`, `l4sql`, `l4con`). |
| **`conn`** | Связь и аудит устройств | Состояние связи терминалов (REST API `connection`), аудит клонов и коллизий серийных номеров, MQTT/SChannel-прокси. |
| **`net`** | Сеть и проксирование | Сетевая топология, конфигурация Nginx, проксирование заголовков сертификатов, порты (:443, :4443). |
| **`run`** | Эксплуатация и DevOps-ранбуки | Инструкции по развертыванию контейнеров, регламенты обновлений, диагностические процедуры через SSH/консоль, откат. |
| **`dev`** | Руководства разработчика | Быстрый старт (Quickstart), регламенты для AI-агентов, стандарты кодирования и правила именования файлов. |

## 5. Исключения и особые каталоги

1. **Корневой навигатор `docs/README.md`**:
   Главный оглавительный индекс документации сохраняет имя `README.md` для корректного отображения на GitHub/GitLab и в IDE.
2. **Архив активной разработки `docs/history/`**:
   Исторические материалы (отчеты ревью `docs/history/reviews/`, пошаговые логи `docs/history/implementation-logs/`, планы `docs/history/planning-and-research/`, черновики промптов `docs/history/prompts-and-drafts/`) **НЕ переименовываются** по данному стандарту. Они сохраняют свои исходные имена для сохранения контекста исторических коммитов и изолированы от активного контекста разработки.

## 6. Обязанности ИИ-агентов (AI Agent Directives)

- При создании любого нового файла технической документации в `docs/` ИИ-агент **ОБЯЗАН**:
  1. Выбрать соответствующую `СФЕРУ` из таблицы раздела 2.
  2. Выбрать соответствующий `ФЛОУ` из таблицы раздела 3.
  3. Сформировать имя по формуле `{СФЕРА}_{ФЛОУ}-{дескриптивное-имя}.md`.
  4. Зарегистрировать новый документ в реестре `docs/README.md`.
- Запрещено создавать документы с произвольными именами без префикса (например, `new-guide.md`, `draft.md`) в активном каталоге `docs/`.
