## 1. Executive summary — итоговая оценка и рекомендация

### 1.1. Общая оценка

Реализация представляет собой **качественно спроектированный, но незавершённый и небезопасный к развёртыванию** срез биллинга.

Сильная сторона — чистый слой расчётов (`app/services/billing.py`): чистые функции, явный параметр `as_of`, все денежные величины в целочисленных минимальных единицах (копейках), отсутствие `float` в денежной арифметике. Требования по неиспользованию `Terminal.is_active` для пользовательской деактивации, по неблокирующему `renewal_enabled=false` до конца оплаченного периода, по нулевому долгу для деактивированных терминалов — выполнены и подтверждены трассировкой кода и тестами.

Слабая сторона — **система не является работающим биллингом**: платёж физически невозможен ни через API, ни через UI; ни одна строка кода никогда не изменяет `License.expires_at`; схема БД не может быть развёрнута, так как миграции отсутствуют полностью. Дополнительно найден архитектурный дефект доверительной границы аутентификации, допускающий межарендный доступ (cross-tenant), и утечка производственных учётных данных в отслеживаемых файлах.

### 1.2. Итоговая рекомендация

**НЕ ДОПУСКАТЬ К ПРОДАКШЕНУ.** Требуется устранение 2 BLOCKER и 2 CRITICAL замечаний до любого развёртывания, а также 8 HIGH — до объявления функциональности готовой к эксплуатации.

### 1.3. Топ-5 рисков

1. **B1** — миграций нет вообще (`alembic/versions/` отсутствует), `alembic` даже не в зависимостях. Развёртывание на существующей БД невозможно; сообщение коммита о «alembic migration» не соответствует действительности.
2. **B2** — платёжный тракт мёртв: провайдер всегда `None` → оба checkout-эндпоинта всегда `501`; вебхука/подтверждения нет; `expires_at` не обновляется нигде → долг невозможно погасить, терминал остаётся заблокированным навсегда.
3. **C1** — бэкенд доверяет заголовкам `jwt-sub`/`jwt-org`, которые nginx-модуль **добавляет**, а не перезаписывает; Starlette читает первое вхождение → владелец любого валидного JWT может читать и деактивировать терминалы чужой организации.
4. **C2** — производственные строки подключения к БД с логином/паролем и внутренним хостом лежат в отслеживаемых файлах (нарушение `AGENTS.md`).
5. **H1/H2/H3** — нарушение XML-контракта для админ-заблокированного терминала (JSON 403 вместо `state=error`), календарный дрейф дат (переплата на целый период) и рассогласование «оплачено N периодов ⇄ выдано N периодов».

### 2.2. Методика

1. **Статический анализ**: последовательное чтение исходников, трассировка потоков управления от входной точки HTTP до записи в БД. Требование считалось выполненным только после прослеживания реальной формулы/ветвления, а не по совпадению имени поля.
2. **Эмпирическая проверка формул**: изолированный запуск функций `app/services/billing.py` на Python 3.14 с подбором контрпримеров (граничные даты, високосный год, конец месяца, просрочка на годы, нулевой период).
3. **Запуск тестов и линтеров** в изолированном venv Python 3.14.7, созданном **вне репозитория** (`~/audit314`), чтобы не изменять рабочее дерево.
4. **Анализ доверительной границы**: изучение исходного кода стороннего nginx-модуля `ngx-http-auth-jwt-module` (TeslaGov) и семантики чтения заголовков Starlette.
5. **Сканирование секретов** по правилам `AGENTS.md`.
6. **Сверка со спецификацией** `docs/billing-implementation-plan.md` (гэп-анализ решений Decision 1–5 и разделов 1.1/1.2).

### 2.3. Ограничения окружения

- Нет доступной СУБД PostgreSQL → интеграционные проверки БД не выполнялись.
- Нет nginx с JWT-модулем → эксплуатация C1 не воспроизведена end-to-end (вывод сделан из исходников модуля + семантики Starlette).
- Нет браузера/сборки фронтенда → UX оценивался по исходному коду.
- В репозитории отсутствуют `uv` и Python 3.14 «из коробки»; они установлены во внешний каталог пользователя, репозиторий не изменялся.

## 5. Проверка бизнес-логики

### 5.1. Ценообразование

Трассировка `compute_terminal_billing` (`billing.py:238–332`):

```
monthly_minor = license.monthly_price_override_minor
                if override is not None else settings.base_monthly_price_minor   # 246–252
period_minor  = monthly_minor * license.billing_period_months                    # 254–256
```

Всё в целых копейках, `float` отсутствует. Приоритет индивидуальной цены над базовой корректен. Значение `0` в override обрабатывается как валидная бесплатная цена (проверка `is not None`, а не truthiness) — это правильно, но приводит к состоянию «статус `overdue`, долг 0» (см. M2-смежный эффект).

**Вывод: PASS.**

### 5.2. Календарная арифметика — дефект дрейфа (H2)

`add_billing_months` (`billing.py:90–92`) корректно ограничивает день числом дней в целевом месяце. Однако вызывающий код применяет её **итеративно, от уже усечённого результата**:

```python
# calculate_periods_due, billing.py:118–123
while cursor <= as_of:
    cursor = add_billing_months(cursor, months)
    periods += 1
```

Эмпирический прогон (Python 3.14, реальный модуль):

| Шаг | Дата |
|---|---|
| исходная | 2026-01-31 |
| +1 мес | 2026-02-28 |
| +1 мес | **2026-03-28** (ожидается 2026-03-31) |
| +1 мес | 2026-04-28 |
| +1 мес | 2026-05-28 |

Якорный день теряется безвозвратно. Финансовое следствие:

```
calculate_periods_due(expires_at=2025-12-31, as_of=2026-03-30, months=1) → 4
Корректный ответ: 3
```

То есть при периоде 1 месяц и цене 3 000 ₽ пользователю выставляется **на 3 000 ₽ больше**, чем положено. Ошибка усиливается для 29/30/31 числа и для февраля високосного года.

**Вывод: FAIL. Требование 1.6 не выполнено.**

### 5.3. Долг просроченного терминала (H3)

Долг считается как `periods_due × period_minor`, где `periods_due` отсчитывается **от `expires_at`**. Но выдаваемый после оплаты период считается иначе — `project_expiration_after_payment` (`billing.py:144–156`):

```python
base = max(as_of, expires_at)          # 148–150
for _ in range(periods):
    base = add_billing_months(base, months)
```

Из-за `max(as_of, expires_at)` для просроченного терминала база = `as_of`, а не `expires_at`. Эмпирический прогон:

| Сценарий | Значение |
|---|---|
| `expires_at` | 2024-08-10 |
| `as_of` | 2026-08-18 |
| период | 1 месяц, 3 000 ₽ |
| `periods_due` | 25 |
| долг | 7 500 000 коп. (75 000 ₽) |
| проекция после оплаты | **2028-09-18** |
| ожидаемая проекция | 2026-09-10 |

Пользователь платит за 25 периодов «в прошлое», а получает 25 периодов **в будущее от сегодняшнего дня** — то есть услугу до сентября 2028 года. Либо долг завышен, либо выдача завышена: две формулы в одном модуле реализуют взаимоисключающие модели («долг за простой» и «предоплата вперёд»).

Второй пример (период 3 месяца):

| Сценарий | Значение |
|---|---|
| `expires_at` | 2026-08-10, `as_of` 2026-08-18 |
| `periods_due` | 1, долг 900 000 коп. |
| проекция | **2026-11-18** вместо 2026-11-10 |

Даже при отсутствии длительной просрочки дата «съезжает» на 8 дней вперёд при каждом платеже.

**Вывод: FAIL. Требование 1.7 выполнено частично, требование 2.10 нарушено для обычного продления.**

### 5.4. Прогноз на три месяца (M1)

`build_org_forecast` (`billing.py:335–376`) формирует ровно три записи по календарным месяцам — структурно требование 1.9 выполнено. Однако флаг `included_in_forecast` (`billing.py:289–308`) выставляется в `False` для терминалов со статусом `overdue`. Это корректно решает задачу «не дублировать текущий долг в прогнозе» (требование 1.10 — PASS), но приводит к тому, что после погашения долга терминал будет продлеваться, а прогноз этого не показывает — **прогноз занижает будущие обязательства**.

Эмпирический прогон для активного терминала с ежемесячным периодом (`expires_at=2026-08-20`, `as_of=2026-08-18`, 3 000 ₽):

```
[('2026-08', 300000), ('2026-09', 300000), ('2026-10', 300000)]
```

— корректно. Для просроченного терминала все три месяца дают `0`.

**Вывод: PARTIAL.**

### 5.5. Статус терминала без лицензии (M2)

`resolve_billing_status` (`billing.py:224–225`): при `license is None` возвращается статус `active`, `included_in_forecast=True`, долг 0. При этом терминальный API (`dependencies.py:165–190`) для терминала без лицензии возвращает `state=error`. Пользователь видит в UI «активен, оплачен», а терминал не работает.

**Вывод: FAIL по консистентности состояния.**

### 5.6. Бесконечный цикл (H4)

`calculate_periods_due` (`billing.py:110–123`) при `billing_period_months <= 0` вызывает `add_billing_months(cursor, 0)`, что не изменяет `cursor` → условие `cursor <= as_of` никогда не станет ложным. Проверка выполнена эмпирически: процесс завершён по таймауту (код выхода 124), CPU 100 %.

Защиты нет ни на уровне БД (в `models.py:103–110` есть CHECK только на цену), ни в валидации Pydantic, ни в самой функции. Любая административная запись `billing_period_months = 0` подвешивает воркер uvicorn при первом же запросе сводки.

**Вывод: FAIL, доступен как DoS.**

### 5.7. Граница календарного месяца (M4)

Ключи прогнозных месяцев формируются из UTC-даты `as_of` (`billing.py:340–344`, `195–203`). Проверка: `as_of = 2026-08-31T22:00:00Z` (что соответствует 1 сентября 01:00 по Москве) даёт первый прогнозный месяц `2026-08`. Для бизнес-календаря МСК это неверно на 3 часа в конце каждого месяца.

**Вывод: PARTIAL.**

|---|---|---|

## 6. Проверка XML-контракта `/api/licensebilling`

### 6.1. Фактический вывод

`app/routers/licensebilling.py:16–20`:

```python
def xml_response(state: str, balance: int) -> Response:
```

Структура тегов и их порядок соответствуют эталону. `Result` всегда `OK`, `balance` берётся из лицензии независимо от `state`.

|---|---|---|

| `state=ok` разрешает работу | PASS | |
| `state=error` блокирует | PASS | |
| `balance` сохраняется при штатной блокировке | PASS | `licensebilling.py:23–48` |
| Положительный `balance` ≠ разрешение | PASS | |
| Истечение лицензии не даёт `Result=ERROR` | PASS | |
| `renewal_enabled=false` не блокирует до `expires_at` | PASS | `dependencies.py:192–196` |
| Инфраструктурные ошибки отличимы и не раскрывают исключения | FAIL | Нет XML-обработчика исключений; `Result=ERROR` не выдаётся никогда |
| Админ-блокировка → `state=error` | FAIL | JSON 403 вместо XML (H1) |

### 6.2. Разрыв контракта при админ-блокировке

`app/dependencies.py:89–90` (внутри `get_current_terminal`, строки 32–104):

```python
if not terminal.is_active:
    raise HTTPException(status_code=403, detail="Terminal is disabled")
```

Эта проверка срабатывает **до** вызова `get_terminal_license_state` (`dependencies.py:146–196`), в котором есть специальная ветка для админ-блокировки (`:155–163`), возвращающая `state=error`. Следовательно, ветка `:155–163` — недостижимый код, а терминал получает JSON-ответ `{"detail":"Terminal is disabled"}` с кодом 403 вместо ожидаемого XML `Result=OK / state=error`.

Легаси-шлюз (см. формат запросов в `migrate/log-examples/licensebilling.log:14–24`) ожидает XML; JSON с кодом 403 приведёт к ошибке парсинга на стороне терминала и, вероятно, к состоянию, отличному от штатной блокировки.

### 6.3. Отличия от эталона (не блокирующие)

- XML-пролог использует одинарные кавычки (`<?xml version='1.0' ...?>`), эталон — двойные. Семантически эквивалентно, но при строковом сравнении на стороне легаси-клиента может иметь значение (LOW, **L6**).
- `media_type="application/xml"`; легаси мог ожидать `text/xml` — не проверяемо без доступа к терминалу (NOT VERIFIED).
- Легаси-параметры POST (`function`, `Signature`) игнорируются — совместимость сохраняется, но потеря диагностической информации.

## 8. Проверка безопасности и tenant isolation

### 8.1. C1 — подделка `org_id` через заголовок

Цепочка доверия:

1. `MenuBuilder/backend/app/routers/auth.py:38` выпускает JWT с claim `org` (строкой — модуль nginx поддерживает только строковые claim'ы).
2. `MenuBuilder/nginx.conf:56–66` проксирует `/api/billing/` и объявляет `auth_jwt_extract_request_claims sub org`.
3. Модуль `ngx-http-auth-jwt-module` (TeslaGov) в функции `set_request_header` добавляет заголовок через `ngx_list_push(&r->headers_in.headers)` — это **append**, а не replace. Пришедший от клиента заголовок `jwt-org` не удаляется.
4. `ProcessingBackend/backend/app/dependencies.py:205–225` (`get_current_user_jwt`) читает `request.headers.get("jwt-org")`.
5. Starlette `Headers.get()` возвращает **первое** вхождение (проверено эмпирически на локальном Starlette).

Итог: клиент, обладающий валидным JWT своей организации, может отправить собственный заголовок `jwt-org: <чужой_id>`; он окажется первым в списке и будет использован бэкендом. Это даёт чтение сводки и списка терминалов чужой организации, а также вызов деактивации и checkout по чужим терминалам (все мутации проверяют принадлежность терминала именно этому подделанному `org_id`).

Спецификация (Decision 2/5) требовала проверки подписи JWT на стороне бэкенда (`python-jose`); зависимость была удалена, проверка не реализована.

**Статус эксплуатации:** воспроизведение end-to-end невозможно (нет nginx с модулем в окружении). Вывод сделан из исходного кода модуля и семантики Starlette — уверенность высокая.

Нарушены явные правила `AGENTS.md` («NEVER hardcode secrets... Database URLs must never contain credentials in code»). Требуется удаление из истории и ротация учётных данных.

### C1 — Подделка `org_id`: обход изоляции арендаторов

- **Severity:** CRITICAL
- **Proof:**
  - `app/dependencies.py:205–225` — `get_current_user_jwt` берёт `org_id` из `request.headers.get("jwt-org")` без какой-либо криптографической проверки.

- **Proof:** `app/services/billing.py:118–123` (`calculate_periods_due`), `:150–156` (`project_expiration_after_payment`), `:360–367` (`build_org_forecast`) вызывают `add_billing_months` в цикле от уже усечённого результата. Эмпирически: цепочка от `2026-01-31` → `2026-02-28` → `2026-03-28` → `2026-04-28` → `2026-05-28`. `calculate_periods_due(2025-12-31, as_of=2026-03-30, months=1)` возвращает **4** вместо 3.
- **Файлы:** `app/services/billing.py:90–92, 110–123, 144–156, 335–376`
- **Фактическое поведение:** якорный день месяца теряется после первого прохода через короткий месяц; для терминалов с датой 29–31 числа начисляется лишний период.
- **Ожидаемое поведение:** дата вычисляется как `anchor_day` + N месяцев от **исходной** даты (`add_months(original, k*months)`), с clamp только на этапе финального вычисления.
- **Бизнес-риск:** систематическая переплата клиентов (для месячного периода — до одного полного периода), споры и возвраты; для годового периода — сдвиг даты продления на дни/недели.
- **Архитектурная причина:** отсутствует понятие «якорного дня» подписки; период моделируется рекуррентно, а не как функция от исходной даты.
- **Рекомендация:** ввести `add_billing_months(anchor: date, months_total: int)` и во всех циклах считать `add_billing_months(base, months * k)`; хранить `anchor_day` при создании лицензии; добавить property-тесты на все дни месяца и високосные годы.

### H3 — Долг и выдаваемый период считаются по разным моделям

- **Severity:** HIGH
- **Proof:** `calculate_periods_due` (`billing.py:110–123`) отсчитывает периоды **от `expires_at`**, а `project_expiration_after_payment` (`billing.py:144–156`) стартует с `base = max(as_of, expires_at)`. Эмпирически: `expires_at=2024-08-10`, `as_of=2026-08-18`, период 1 месяц/3 000 ₽ → `periods_due=25`, долг 7 500 000 коп., проекция **2028-09-18** (ожидалось 2026-09-10). Даже без просрочки: `expires_at=2026-08-10`, `as_of=2026-08-18`, период 3 мес → проекция `2026-11-18` вместо `2026-11-10`.
- **Файлы:** `app/services/billing.py:110–123, 144–156`
- **Фактическое поведение:** пользователь платит за период «в прошлое», а получает эквивалентный период вперёд от даты платежа — двойной учёт времени.
- **Ожидаемое поведение:** одна согласованная модель. Для «долг за простой»: новая дата = `expires_at + periods_due × months`. Для «предоплата вперёд»: долг = стоимость одного периода, дата = `as_of + months`. Требование 2.10 явно указывает: новый период после истечения **не** должен считаться от старой даты — значит для реактивации верна вторая модель, а для непрерывной подписки — первая.
- **Бизнес-риск:** предоставление услуги на годы вперёд без оплаты либо, при обратной трактовке, завышенный счёт; расхождение выручки и обязательств в отчётности.
- **Архитектурная причина:** две формулы написаны независимо и нигде не связаны инвариантом; отсутствует тест «после оплаты долга долг равен нулю и дата равна ожидаемой».
- **Рекомендация:** зафиксировать инвариант `debt(after_payment) == 0 and expires_at_new == f(expires_at_old, periods_due)`; реализовать `project_expiration_after_payment(expires_at, periods, months, mode)` с явным режимом (`renewal` / `reactivation`); покрыть property-тестом.

## 14. Положительные стороны реализации

1. **Чистый расчётный слой.** `app/services/billing.py` — детерминированные функции с явным параметром `as_of`, без обращений к БД и времени. Это лучший по качеству модуль в задаче и хорошая основа для исправлений.
2. **Корректная денежная модель.** Все суммы — целые числа в копейках (`*_minor`), `float` в денежных путях отсутствует. Требование выполнено строго.
3. **Правильная семантика пользовательской деактивации.** `Terminal.is_active` не используется как немедленная блокировка; терминал работает до `expires_at` (`dependencies.py:192–196`), но сразу исключается из прогнозов (`billing.py:289–308`).
4. **`renewal_enabled=false` не блокирует терминал** до конца оплаченного периода — сложное требование выполнено точно.
5. **Долг = 0 для отключённых и для просроченных отключённых** терминалов (`billing.py:262`, `:134–135`) — требования 2.5/2.6 выполнены.
6. **Отмена деактивации после истечения запрещена** (409, `routers/billing.py:287–291`) и запрещена для админ-заблокированных (403, `:293–297`).
7. **Реактивация считает новый период от даты платежа**, а не от старой истёкшей даты (`routers/billing.py:475–593`) — соответствует требованию 2.10.
8. **Ценообразование только на сервере**; клиент не может влиять на суммы.
9. **Последовательное применение org-скоупа** внутри контура: `_get_terminal_for_org` (`routers/billing.py:55–68`) вызывается во всех мутациях.
10. **UX-требование по долгу выполнено буквально**: красный цвет и знак минус в UI при неотрицательном хранении величины.
11. **Разделение состояний в UI** отдельными вкладками — деактивированные и ожидающие деактивации не смешиваются.
12. **31 сфокусированный юнит-тест** на расчёты и 12 контрактных тестов XML; вся сюита (62 теста) проходит.
13. **Pyright — 0 ошибок**, `ruff check app/` — чисто.
14. **Конфигурация соответствует `AGENTS.md`**: значения из окружения, `extra="ignore"` для общего `.env`.
15. **Терминальный контур не сломан по формату** для основных сценариев: структура XML, порядок тегов и сохранение `balance` при блокировке соответствуют эталону.
