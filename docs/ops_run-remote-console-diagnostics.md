# Remote Diagnostics & Console Flow Specification (Удалённая консоль и диагностика)

Данный документ является **единым источником правды (Single Source of Truth)** для архитектуры, протокола взаимодействия, маршрутизации топиков MQTT и реализации всех компонентов подсистемы удаленной диагностики и веб-консоли терминалов:
1. **Frontend**: Панель веб-консоли и пресетов в `MenuBuilder/frontend` (`DeviceConsoleTab.tsx`).
2. **Backend**: Сервис диагностики и управления сессиями консоли (`MenuBuilder/backend` / `ProcessingBackend` / `iot-rpc-rest-app`).
3. **MQTT Broker**: Локальный или центральный брокер сообщений (Mosquitto / RabbitMQ MQTT).
4. **Agent (Устройство)**: Автономный легковесный C/Win32 агент `l4con` (`tools/l4con`), выполняющий команды в ОС Windows и передающий потоковый вывод.

---

## 1. Архитектура и сквозной поток данных (End-to-End Flow)

```
+----------------------------------------------------------------------------------------------------+
|                                    1. Web UI Console (Browser)                                     |
|  - Вход в консоль: ручное подключение по кнопке «Подключить» (нет автоконнекта)                    |
|  - Переключатель «Сохранять сессию» (default: false): сброс/7002 при смене вкладки если выкл       |
|  - Строгое завершение (7002 + close WS) при закрытии Drawer или уходе со страницы                 |
|  - Адаптация под тег sys: sys=windows (CLI + пресеты), sys=esp32 (только логи), без тега (Alert) |
|  - Автоматический возврат фокуса в строку ввода после завершения команды (InputRef)                |
|  - Дедупликация чанков вывода по seq и исключение повторных идентичных статусов                   |
+----------------------------------------------------------------------------------------------------+
                                             │ ▲ WebSocket
                                             ▼ │ (JSON: exec, output, cancel, status, ping)
+----------------------------------------------------------------------------------------------------+
|                                  2. Diagnostics Backend (FastAPI)                                  |
|  - Аутентификация JWT и валидация роли, tenant, владельца console lease и доступа к терминалу     |
|  - Управление жизненным циклом сессии (session_id, task_id, таймауты)                             |
|  - Мост WebSocket <-> MQTT RPC (публикация задач, подписка на dev/{SN}/out и dev/{SN}/res)         |
|  - Реактивное глушение (Active Silencing): отправка 7002 при чанках с неизвестным session_id        |
+----------------------------------------------------------------------------------------------------+
                                             │ ▲ MQTT 3.1.1 (TCP / mTLS)
                                             ▼ │ (JSON RPC: tsk, req, rsp, res, out, svc)
+----------------------------------------------------------------------------------------------------+
|                                 3. Central / Local MQTT Broker                                     |
|  - Изоляция по Serial Number (SN) устройства                                                       |
|  - Поддержка LWT (Last Will & Testament) и Retain для отслеживания онлайн-статуса                  |
+----------------------------------------------------------------------------------------------------+
                                             │ ▲ MQTT TCP (127.0.0.1:1883 или remote broker)
                                             ▼ │
+----------------------------------------------------------------------------------------------------+
|                           4. Diagnostic Agent l4con (Windows Terminal)                             |
|  - Роль MQTT-клиента: extra_service (LWT: dev/{SN}/svc)                                            |
|  - Single-Instance Mutex (Global\L4Con_SingleInstance_Mutex) — запрет двойного запуска             |
|  - Автоматическое определение SN через локальный Leo4Proxy (GET http://127.0.0.1:18443/_leo4/sn)   |
|  - Исполнение процессов через CreateProcess (stdin=NUL, неинтерактивный режим)                     |
|  - Перекодирование вывода из OEM CP866 / CP1251 в UTF-8                                            |
|  - Потоковая отправка чанков вывода в dev/{SN}/out с монотонным seq и флагом eof                   |
|  - Обработка RPC-методов: 7001 (Exec), 7002 (Cancel), 7003 (Ping/Pong), 7004 (Keepalive Lease)     |
|  - Прерывание дерева процессов (taskkill /F /T) при отмене (7002) или таймауте (ttl_sec)           |
+----------------------------------------------------------------------------------------------------+
```

## 2. Стандартизация топиков MQTT (`iot-rpc-rest-app`)

В соответствии с базовой спецификацией `iot-rpc-rest-app` и правилами именования `mqtt_topic_rules.md`, в подсистеме диагностики и консоли **строго запрещено создание нестандартных ad-hoc топиков** (таких как `srv/<SN>/cmd`, `dev/<SN>/ctrl`, `dev/<SN>/cmd/...`).

Разрешена работа **исключительно** со следующей матрицей топиков:

### 2.1. Матрица топиков

| Направление | Топик | QoS | Retain | Назначение / Описание |
|---|---|---|---|---|
| **Server ➔ Device** | `srv/<SN>/tsk` | 1 | 0 | **Триггер/Анонс новой задачи**: оповещение агента о наличии задачи на исполнение или отмену. |
| **Server ➔ Device** | `srv/<SN>/rsp` | 1 | 0 | **Тело задачи (RPC Payload)**: полные параметры исполнения команды (`7001`), отмены (`7002`), эхо (`7003`) или продления аренды (`7004`). |
| **Server ➔ Device** | `srv/<SN>/cmt` | 1 | 0 | **Подтверждение фиксации (Commit)**: опциональный ack завершения. |
| **Device ➔ Server** | `dev/<SN>/req` | 0 / 1 | 0 | **Запрос параметров задачи**: отправляется агентом в ответ на `srv/<SN>/tsk` по `correlationData`. |
| **Device ➔ Server** | `dev/<SN>/res` | 1 | 0 | **Финальный отчет о задаче**: результат выполнения, `status_code`, `exit_code`, `duration_ms`. |
| **Device ➔ Server** | `dev/<SN>/out` | 0 / 1 | 0 | **Потоковый вывод (Volatile Stream)**: фрагменты вывода stdout/stderr с порядковым номером `seq` и `eof`. |
| **Device ➔ Server** | `dev/<SN>/svc` | 1 | **1 (True)** | **Presence / LWT вспомогательного сервиса**: статус агента диагностики (`svc_online` / `svc_offline`). |
| **Device ➔ Server** | `dev/<SN>/app` | 1 | **1 (True)** | **Presence / LWT основного приложения**: статус ПО терминала (`app_online` / `app_offline`). |

## 3. Регламент RPC-методов линейки диагностики (`7000..7009`)

| Метод RPC | Константа | Назначение |
|---|---|---|
| **7000** | `CMD_DIAG_STREAM_CONTROL` | Управление непрерывными потоками (старт/стоп передачи логов ESP32/служб с параметрами `rate_limit`, `level`). |
| **7001** | `CMD_DIAG_EXEC` | Запуск неинтерактивной команды / пресета с `ttl_sec` и `max_output_bytes`. |
| **7002** | `CMD_DIAG_CANCEL` | Принудительное прерывание выполнения / завершение активной сессии и остановка потока. |
| **7003** | `CMD_DIAG_PING` | Прикладной эхо-запрос (RPC Ping/Pong) для замера сквозного RTT и подтверждения живости цикла агента. |
| **7004** | `CMD_DIAG_SESSION_KEEPALIVE` | Продление аренды сессии (Session Lease). Если в течение N секунд keepalive от сервера не поступил, агент самостоятельно гасит фоновый процесс. |
| **7005** | `CMD_DIAG_AGENT_STATUS` | Мгновенный опрос внутреннего состояния агента (список запущенных дочерних PID, память, время непрерывной работы). |

## 4. Сценарии взаимодействия и форматы сообщений

### 4.1. Presence & LWT (Статус агента диагностики `extra_service`)

1. **CONNECT**:
   - `will_topic = dev/<SN>/svc`
   - `will_payload = svc_offline`
   - `will_retain = true`, `will_qos = 1`
2. **После CONNACK (rc=0)**:
   - `PUBLISH dev/<SN>/svc = svc_online (retain=true, qos=1)`
   - `SUBSCRIBE srv/<SN>/tsk (qos=1)`, `SUBSCRIBE srv/<SN>/rsp (qos=1)`
3. **Штатная остановка (Normal Shutdown / Service Stop)**:
   - `PUBLISH dev/<SN>/svc = svc_offline (retain=true, qos=1)`
   - `DISCONNECT`
4. **Аварийный сбой (Crash / Drop connection)**:
   - Брокер автоматически рассылает `dev/<SN>/svc = svc_offline (retain=true)`.

---

### 4.2. Выполнение команды (`CMD_DIAG_EXEC` / Method `7001`)

#### Шаг 1. Анонс задачи (Server ➔ `srv/<SN>/tsk`)
```json
{
  "id": "b3b7e7e8-3482-446a-8b1e-61e8bf2803b9",
  "method_code": 7001,
  "correlationData": "b3b7e7e8-3482-446a-8b1e-61e8bf2803b9"
}
```

#### Шаг 2. Запрос параметров (Device ➔ `dev/<SN>/req`)
```json
{
  "correlationData": "b3b7e7e8-3482-446a-8b1e-61e8bf2803b9"
}
```

#### Шаг 3. Доставка параметров задачи (Server ➔ `srv/<SN>/rsp`)
```json
{
  "id": "b3b7e7e8-3482-446a-8b1e-61e8bf2803b9",
  "method_code": 7001,
  "session_id": "sess_91823791283",
  "command_line": "ipconfig /all",
  "shell": "cmd",
  "ttl_sec": 30,
  "max_output_bytes": 1048576,
  "topic": "dev/a4b0000773c82116d210826/out"
}
```

#### Шаг 4. Потоковый вывод (Device ➔ `dev/<SN>/out`)
```json
{
  "session_id": "sess_91823791283",
  "seq": 1,
  "data": "Windows IP Configuration\r\n\r\n   Host Name . . . . . . . . . . . . : POS-TERMINAL-01\r\n",
  "eof": false
}
```
Финальный чанк по завершении процесса:
```json
{
  "session_id": "sess_91823791283",
  "seq": 2,
  "data": "",
  "eof": true,
  "exit_code": 0
}
```

#### Шаг 5. Финальный отчет о задаче (Device ➔ `dev/<SN>/res`)
```json
{
  "correlationData": "b3b7e7e8-3482-446a-8b1e-61e8bf2803b9",
  "task_id": "b3b7e7e8-3482-446a-8b1e-61e8bf2803b9",
  "status_code": "200",
  "status": "completed",
  "exit_code": 0,
  "duration_ms": 145
}
```

### 4.3. Отмена активной команды и закрытие сессии (`CMD_DIAG_CANCEL` / Method `7002`)

1. **Триггеры отправки 7002**:
   - Нажатие пользователем кнопки «Прервать» в UI.
   - Нажатие кнопки «Отключить» в UI во время активной сессии.
   - Переключение между внутренними вкладками (Задачи/События/Консоль), если выключен переключатель «Сохранять сессию».
   - Закрытие формы управления (Drawer) или уход со страницы.
   - Реактивное подавление фантомного потока на бэкенде: если на бэкенд поступает чанк `dev/<SN>/out`, а сессия не найдена в реестре.
2. **Формат задачи отмены** (`srv/<SN>/rsp`):
```json
{
  "id": "cancel_b3b7e7e8",
  "method_code": 7002,
  "session_id": "sess_91823791283",
  "task_id": "b3b7e7e8-3482-446a-8b1e-61e8bf2803b9",
  "reason": "User cancelled or session closed"
}
```
3. **Действия агента `l4con`**:
   - Прерывание дерева дочерних процессов: `taskkill /F /T /PID <pid>` и `TerminateProcess`.
   - Отправка финального чанка с `eof: true`, `exit_code: 130` в `dev/<SN>/out`.
   - Ответ в `dev/<SN>/res`:
```json
{
  "correlationData": "b3b7e7e8-3482-446a-8b1e-61e8bf2803b9",
  "status_code": "200",
  "status": "cancelled",
  "exit_code": 130
}
```

---

### 4.4. Прикладной эхо-запрос (`CMD_DIAG_PING` / Method `7003`)

1. **Сервер отправляет пинг** в `srv/<SN>/rsp`:
```json
{
  "id": "ping_91823",
  "method_code": 7003
}
```
2. **Агент мгновенно отвечает** в `dev/<SN>/res`:
```json
{
  "correlationData": "ping_91823",
  "status_code": "200",
  "status": "pong",
  "role": "extra_service"
}
```

## 5. Требования к компонентам реализации

### 5.1. Агент `l4con` (`tools/l4con`)
- **Single-Instance Protection**: именованный мьютекс `Global\L4Con_SingleInstance_Mutex` (с корректной обработкой `ERROR_ACCESS_DENIED` между Session 0 и Session 1), блокирующий запуск параллельных процессов агента.
- **Zero-Dependency Win32 / C**: скомпилирован статически (`/MT`), без внешних runtime-зависимостей.
- **Поддержка 32-bit (x86) и 64-bit (x64)**: обязательна сборка для обеих платформ (`build.cmd`).
- **Служба Windows (SCM)**: имя `L4Con`, автозапуск `SERVICE_AUTO_START`, auto-recovery (5с, 10с, 30с).
- **Неинтерактивный запуск (`stdin = NUL`)**: запрет блокирующих интерактивных запросов.
- **Кодировки Windows**: автоматическое преобразование вывода OEM CP866 (cmd.exe) и CP1251 в стандартный UTF-8.
- **Безопасность (Blacklist)**: встроенная блокировка деструктивных команд (`format`, `diskpart`, `del /s /q c:\`, `shutdown` и т.д.).

### 5.2. Веб-интерфейс (`MenuBuilder/frontend/src/routes/devices/`)
- **Таблица устройств (`index.tsx`)**: единая кнопка действия «Управление» (открывает панель задач, событий, тегов и консоли).
- **Управление сессией (`DeviceConsoleTab.tsx`)**:
  - Сессия открывается вручную по кнопке **«Подключить»** / закрывается по кнопке **«Отключить»**.
  - Переключатель **«Сохранять сессию»** (default: `false`): определяет, завершать ли соединение (7002 + WS close) при переключении между внутренними вкладками формы.
  - При закрытии Drawer или уходе со страницы — безусловное завершение сеанса и закрытие WS.
- **Адаптация по тегу `sys`**:
  - `sys === "windows"`: полноценное CLI-управление (`cmd.exe` / `PowerShell`), быстрые пресеты, история команд.
  - `sys === "esp32"`: режим только **Live Logs**, скрытие/деактивация CLI-команд.
  - `sys` отсутствует: деактивация элементов управления, вывод предупреждающего Alert.
- **Удобство ввода (UX)**: автоматический возврат фокуса в поле ввода команд через `InputRef` при завершении выполнения.
- **Надежность отображения**: дедупликация фрагментов потока по монотонному `seq` и исключение повторных статусных сообщений.

### 5.3. Аренда и доступ к консоли

`superuser` и `l4desk_owner` могут получить `scope=console`; владелец L4Desk
ограничен устройствами собственного tenant. Для `l4desk_owner` диагностика WS
требует явный console lease и сверяет SN, tenant, пользователя, browser session и
роль аренды. Неявная console lease доступна только `superuser`. Роли admin,
user и viewer не получают console lease. Консоль взаимоисключена с video/input
на уровне app1; при конфликте возвращается `409 lease_taken`.

## 7. Варианты Тестирования Удаленной Консоли и Сквозные Тест-Кейсы (E2E & REST-RPC)

В подсистеме удалённой консоли и диагностики предусмотрено **3 уровня верификации**:

### 7.1. Вариант 1: Интерактивное тестирование через Web UI Console
* **Интерфейс**: панель «Управление» ➔ вкладка «Консоль» в `MenuBuilder/frontend` (`DeviceConsoleTab.tsx`).
* **Флоу**:
  1. Администратор нажимает «Подключить» (открывается WebSocket, отправляется пинг `7003`).
  2. Вводит команду (например, `l4sql tb_Variables` или `ipconfig`).
  3. В окне консоли отображается рабочая папка и команда (`C:\l4tools> l4sql tb_Variables`), затем потоковый вывод строк (`stdout`/`stderr`), и статус `[COMPLETED] Процесс завершён. Код возврата: 0`.
  4. При нажатии кнопки «Прервать» или отключении — отправляется `7002` (Cancel).

### 7.2. Вариант 2: Сквозное автоматизированное тестирование через REST-RPC API (`POST /api/v1/device-tasks/`)
Позволяет инициировать и валидировать команды удалённой диагностики программно без открытия браузера.

* **Шаг 1: Создание задачи**:
  ```http
  POST https://dev.leo4.ru/api/v1/device-tasks/?org_id=1
  Content-Type: application/json
  X-Org-Id: 1
  X-Role: admin
  X-Role-Id: 1

  {
    "device_id": 773,
    "ext_task_id": "test-task-01",
    "method_code": 7001,
    "priority": 0,
    "ttl": 5,
    "payload": {
      "command_line": "l4sql --limit 3 tb_Variables"
    }
  }
  ```
  *Ответ (`200 OK`)*: `{"id": "<task_uuid>", "created_at": 1788035386}`.

* **Шаг 2: Проверка статуса исполнения**:
  ```http
  GET https://dev.leo4.ru/api/v1/device-tasks/<task_uuid>?org_id=1
  X-Org-Id: 1
  X-Role: admin
  X-Role-Id: 1
  ```
  *Ответ (`200 OK`)*:
  ```json
  {
    "id": "<task_uuid>",
    "status": 3,
    "results": [
      {
        "status_code": 501,
        "result": {
          "status": "completed",
          "exit_code": 0,
          "duration_ms": 1546,
          "status_code": "200"
        }
      }
    ]
  }
  ```

### 7.3. Вариант 3: Локальное тестирование на терминале через MQTT
* Подключение тестовым клиентом к локальному Mosquitto (`127.0.0.1:1883`).
* Подписка на топики: `dev/{SN}/out` (потоковый вывод) и `dev/{SN}/res` (результат).
* Публикация в `srv/{SN}/rsp`:
  ```json
  {
    "id": "loc-01",
    "method_code": 7001,
    "session_id": "loc-sess-1",
    "command_line": "l4sql --limit 3 tb_Variables"
  }
  ```

### 7.4. Выявленные тест-кейсы и критические особенности среды

1. **Рабочая папка по умолчанию (Default CWD)**:
   * Служба Windows `L4Con` запускается в контексте `C:\Windows\system32`.
   * Агент `l4con` принудительно переключает рабочий каталог дочерних процессов в базовую папку `C:\l4tools`, чтобы команды выполнялись в контексте утилит и исключался вывод системных файлов Windows.
2. **Прозрачная видимость утилит (Auto-PATH)**:
   * `l4con` обогащает переменную среды `PATH` путями ко всем утилитам (`C:\l4tools\l4sql`, `C:\l4tools\l4pin`, `C:\l4tools\l4superv`, `C:\l4tools\leo4proxy`).
   * Тест: команда `l4sql tb_Variables` должна выполняться успешно без префикса `C:\l4tools\l4sql\`.
3. **Права учетной записи службы Windows (`NT AUTHORITY\SYSTEM`)**:
   * Служба `L4Con` работает под `LocalSystem`. При использовании Windows Authentication для MS SQL Server логин `NT AUTHORITY\СИСТЕМА` (`NT AUTHORITY\SYSTEM`) должен иметь права `db_datareader` и `EXECUTE` в целевой базе данных `Terminal`.
4. **Блокировка модифицирующих запросов (Read-Only Guard)**:
   * Тест-кейсы: `UPDATE`, `INSERT`, `DELETE`, `DROP`, `ALTER`, `TRUNCATE`, `SELECT INTO` должны блокироваться с `exit_code: 2`.
   * Хранимые процедуры: вызовы обычных процедур (`EXEC sp_ClearDB`) блокируются (`exit_code: 2`), разрешены только процедуры с префиксом `l4_` (`EXEC dbo.l4_...`).
5. **Таймауты и отмена**:
   * По истечении `ttl_sec` процесс гарантированно уничтожается с деревом дочерних процессов (`taskkill /F /T`), возвращая `exit_code: 124`.
   * При получении `7002` процесс прерывается с `exit_code: 130`.
