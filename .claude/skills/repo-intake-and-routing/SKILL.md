# Repo intake and routing

## Когда применять
В начале любой содержательной задачи. Для объяснения достаточно краткого intake;
это не разрешение на изменения, запуск тестов или раскрытие секретов.

## Порядок
1. Прочитай [AGENTS.md](../../../AGENTS.md), действующий запрос и локальные правила.
   Упоминание каталога в карточке не разрешает его исследование.
2. Классифицируй: docs, frontend, MenuBuilder backend, ProcessingBackend,
   shared/миграции, native Windows tools, infrastructure/deploy, cross-stack.
3. В [индексе](../../../.agent-context/README.md) выбери одну компонентную карточку
   и только контракты изменяемого flow. Не загружай все skills или docs.
4. Определи владельца данных/API, инициатора и потребителя события, владельца миграций.
   Если app1 вне доступного репозитория, запроси источник; не считай его проверенным.
5. Проверь дату, evidence level и риски карточки; открой только указанные первичные
   файлы затронутого контракта. При расхождении запиши факт и согласуй изменение.
6. До реализации зафиксируй intake. Для MQTT-клиента задай обязательный вопрос
   о типе согласно актуальным правилам; не выбирай тип по названию утилиты.

## Обязательный результат
```markdown
## Task intake
- Цель / тип задачи:
- Затронутые компоненты / границы работ:
- Владелец данных / контракта / миграций:
- Producer → transport → consumer:
- Инварианты:
- Риски / неизвестное:
- Минимальные карточки и файлы для исследования:
- Критерии готовности:
- Требуемая валидация / что не разрешено запускать:
```

Нет владельца, контракта, инвариантов или способа проверки — уточни до реализации.
