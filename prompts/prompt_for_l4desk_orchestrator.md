# Задача для Senior Software Architect

Изучи текущий репозиторий, его архитектуру, серверную часть, frontend, существующий пакет `l4tools`, компоненты `l4superv`, `l4desk`, механизмы доставки tools, роли пользователей, Video UI, существующую Console и контуры удалённого управления/видеотрансляции.

Твоя задача — **не реализовывать изменения самостоятельно**. Подготовь **два изолированных, самодостаточных и подробных промпта** для двух независимых агентов разработки:

1. Промпт для агента серверной разработки:
    - server-side;
    - API;
    - хранение состояния;
    - права;
    - lease/блокировки;
    - Video UI;
    - Console и удалённое управление.

2. Промпт для агента разработки tools-пакета:
    - разработка и рефакторинг `l4desk`;
    - необходимые изменения `l4superv`;
    - lifecycle и orchestration `ffmpeg`;
    - упаковка, доставка и deployment tools.

Каждый итоговый промпт должен содержать весь необходимый контекст, технические ограничения, цели, порядок исследования репозитория, критерии готовности, требования к тестированию и ожидаемый формат отчёта.

Агенты должны иметь возможность работать независимо: не ссылайся в одном промпте на другой и не предполагай, что агент получит дополнительный контекст устно.

Не придумывай структуру репозитория, API, топики, модели данных, имена модулей или способы deployment. Сначала найди соответствующие реализации в репозитории. Развивай существующие механизмы, если они уже есть, вместо создания параллельных решений.

## Целевая архитектурная модель

Не создавать отдельный бинарник или отдельный сервис-оркестратор FFmpeg.

Использовать и развивать существующую иерархию:

    l4superv
      └─ l4desk
           └─ ffmpeg.exe

### Роли компонентов

`l4superv` — системный Windows-супервизор:

- определяет активную интерактивную пользовательскую Windows-сессию;
- запускает `l4desk` в правильной user session;
- перезапускает `l4desk` при аварии;
- останавливает и очищает дерево процессов при logout, смене сессии, остановке или рестарте супервизора;
- использует Windows Job Object или эквивалентный существующий механизм для гарантированного завершения дочерних процессов.

`l4desk` — агент в интерактивной пользовательской сессии:

- принимает разрешённые команды удалённого управления видеотрансляцией;
- публикует список доступных desktop/display и камер;
- выбирает и хранит один активный источник трансляции;
- запускает, отслеживает, перезапускает и останавливает дочерний `ffmpeg`;
- исключает появление нескольких управляемых экземпляров `ffmpeg`;
- обеспечивает удалённый ввод исключительно для выбранного desktop;
- принимает команды ввода только при действующей эксклюзивной lease.

`ffmpeg.exe`:

- не является самостоятельной службой;
- не имеет независимого механизма автозапуска;
- должен быть дочерним процессом `l4desk`;
- должен полностью контролироваться lifecycle-механизмами `l4desk` и `l4superv`.

## Режимы видеотрансляции

Поддержать единую модель видеоисточников:

    desktop
    usb-camera
    stopped

Где:

- `desktop` — захват одного выбранного физического дисплея/desktop;
- `usb-camera` — захват одной выбранной USB-камеры;
- `stopped` — активная трансляция отсутствует.

Ограничения:

1. Для одного терминала допускается только одна активная видеотрансляция.
2. Одновременно может быть выбран только один источник: один desktop/display, одна USB-камера или иной явно разрешённый источник, если он существует в проекте.
3. При попытке старта нового источника во время активного старого необходимо выбрать и обосновать согласованную политику на основе существующего UX:
    - либо вернуть отказ с понятной причиной;
    - либо выполнить контролируемое переключение: остановка текущего источника, ожидание подтверждённого завершения, запуск нового.
4. Desktop-захват запускается только внутри корректной интерактивной user session Windows, не в Session 0.
5. USB-камера должна уметь транслироваться без подключения Remote Control.
6. Удалённое управление мышью/клавиатурой разрешено только в режиме `desktop`, но не в режиме `usb-camera`.

## Выбор одного desktop из нескольких

Терминал может иметь несколько физических экранов и/или несколько Windows-сессий.

Нужно:

- публиковать с терминала inventory доступных desktop/display;
- позволить оператору выбрать только один display как источник трансляции;
- захватывать только область выбранного display, а не весь виртуальный экран;
- связать выбранный display с конкретной пользовательской Windows-сессией;
- не допускать ввода в desktop, отличный от отображаемого в активной трансляции;
- учесть дисплеи с отрицательными координатами в virtual screen;
- использовать максимально стабильный идентификатор display, а не полагаться только на изменяемый номер `\\.\DISPLAYn`;
- предусмотреть локальную политику, определяющую разрешённые display, display только для просмотра и display, доступные для удалённого ввода.

Для активной desktop-сессии должны быть логически и технически связаны:

    terminal
    selectedDesktopId
    selectedSessionId
    streamInstanceId
    active video stream
    remote-control lease
    browser-user lease owner

Команда ввода должна отклоняться, если `desktopId`, `streamInstanceId` или lease не совпадают с текущей активной привязкой.

## Монопольность браузерного пользователя

Любое удалённое управление терминалом должно быть монопольным для одного браузерного пользователя.

Это требование распространяется на:

- существующую Console;
- включение и использование Remote Control;
- команды мыши и клавиатуры;
- запуск, остановку и переключение трансляции;
- трансляции desktop;
- трансляции камеры;
- любые другие существующие или будущие видеосессии терминала.

Требования:

1. Для одного терминала должна существовать одна общая эксклюзивная lease для удалённой интерактивной работы и видеоуправления.
2. Если lease уже принадлежит одному браузерному пользователю, любой другой пользователь должен получить явный отказ:
    - при подключении к Console;
    - при включении Remote Control;
    - при запуске, остановке или переключении трансляции;
    - при попытке получить доступ к существующей видеосессии, если просмотр включён в монопольную бизнес-операцию.
3. Отказ должен быть понятным в UI и API, без неявного подключения или частичного захвата управления.
4. Lease должна содержать:
    - владельца;
    - идентификатор пользовательской/браузерной сессии;
    - время выдачи;
    - TTL или heartbeat;
    - освобождение при logout, закрытии вкладки, разрыве WebSocket, истечении TTL и явном завершении;
    - безопасную обработку гонок конкурентных запросов.
5. Сначала найди и изучи существующую реализацию Console, WebSocket, MQTT/RPC, авторизации и блокировок/lease. Расширяй существующий механизм, не создавай второй независимый механизм.
6. Если в текущей системе есть многопользовательский read-only просмотр, явно зафиксируй это как вопрос бизнес-правил. Базовое требование для реализации: любая трансляция монопольно принадлежит одному браузерному пользователю.

## Права пользователей

Изучи текущую модель ролей, назначение прав и соответствующий UI.

Нужно доработать функциональность пользователя с `role = 3`, который назначает права пользователям с `role = 4` (`viewer`):

- добавить отдельную галочку/право `Видеонаблюдение`;
- определить и документировать, какие действия разрешает это право;
- по умолчанию считать, что это право даёт доступ к Video UI и просмотру разрешённой видеосессии;
- это право не должно давать возможность:
    - захватывать lease;
    - включать Remote Control;
    - отправлять команды мыши/клавиатуры;
    - запускать/останавливать поток без отдельного разрешения;
    - обходить монопольность другого пользователя;
- проверить и доработать backend authorization, API/WebSocket-проверки и frontend UI;
- не ограничиваться скрытием кнопок в интерфейсе;
- сохранить обратную совместимость с текущими ролями и назначенными правами.

## Надёжность FFmpeg

Логика orchestration должна быть встроена в `l4desk`.

Нужно обеспечить:

1. Только один управляемый экземпляр FFmpeg на терминал.
2. Сериализацию lifecycle:

       stopped → starting → running → stopping → stopped

   Дополнительные состояния:

       restarting
       failed
       source_unavailable
       session_unavailable

3. Идемпотентность команд:
    - повторный start не создаёт второй процесс;
    - stop несуществующего процесса возвращает корректный результат `already_stopped`;
    - повтор команды с тем же command ID безопасен.
4. Скрытый запуск FFmpeg, без видимого консольного окна и помех киоск-программе.
5. Перенаправление диагностических сообщений FFmpeg в ротационные логи.
6. Двухфазную остановку:
    - мягкое завершение FFmpeg;
    - ожидание в пределах timeout;
    - принудительное завершение Job Object или дерева процессов при timeout;
    - публикация состояния `stopped` только после фактического завершения процесса.
7. Защиту от orphan/lost FFmpeg:
    - глобальный mutex или другой межпроцессный lock;
    - Job Object;
    - reconciliation после рестарта агента;
    - проверку PID вместе с временем запуска, Session ID и признаком владения;
    - запрет на массовое небезопасное завершение процессов по имени `ffmpeg.exe`.
8. Контролируемый restart:
    - отличать intentional stop от crash;
    - применять ограниченный backoff;
    - ограничивать число рестартов;
    - исключать бесконечный restart loop при отсутствии камеры, недоступном desktop или ошибочной конфигурации.
9. Health-check:
    - проверять существование и состояние процесса;
    - проверять доступность источника;
    - проверять поступление кадров или прогресс FFmpeg;
    - проверять возможность отправки RTP в локальный ingress;
    - публиковать понятную диагностическую причину сбоя, остановки или рестарта.

Удалённо нельзя передавать:

- произвольные аргументы FFmpeg;
- shell-команды;
- пути к исполняемым файлам;
- произвольные Windows device name;
- непроверенные Session ID.

Сервер должен передавать только разрешённые логические идентификаторы: `sourceId`, `desktopId`, `cameraId`, `profile`. Их необходимо валидировать локально в `l4desk`.

## Упаковка FFmpeg в tools-пакет

Для агента tools-пакета обязательны следующие условия:

1. На машине разработки имеется каталог:

   `D:\ffmpeg`

   В нём находятся все файлы актуального дистрибутива FFmpeg.

2. Нужно исследовать текущий механизм сборки, упаковки, версионирования, публикации и развёртывания остальных tools.

3. Все необходимые файлы FFmpeg должны быть включены в ZIP-архив рядом с другими ZIP-архивами и артефактами tools-пакета.

4. При deployment на терминале FFmpeg должен устанавливаться в каталог:

   `C:\l4tools\ffmpeg`

5. `l4desk` должен запускать FFmpeg только из установленного tools-каталога и не должен использовать:
    - `D:\ffmpeg`;
    - системный `PATH`;
    - текущую директорию процесса;
    - произвольный локальный путь.

6. Необходимо предусмотреть:
    - проверку наличия `ffmpeg.exe`;
    - проверку версии и/или целостности по правилам проекта;
    - безопасное обновление;
    - обработку повреждённого или частично распакованного архива;
    - запрет на удаление или перезапись используемых файлов FFmpeg без контролируемой остановки активной трансляции.
