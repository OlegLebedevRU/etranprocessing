## Владение

PB — домен заказов/разрешений/решений и миграции. MB — JWT, роль 6, UI, API-ключи существующего контура. IoT — внешний API-фасад рядом с RPC, доставка команд, RAW и webhook. siplite — физическая операция, применённые права и устойчивое состояние NVS. Shared — только декларативные ORM.

## Контракт

ERP → IoT → PB; MB BFF → PB; PB → IoT RPC → siplite; siplite → PB HTTPS state/sync. RAW необязательны для бизнес-переходов. Новый MQTT-клиент не проектируется, новые числовые коды/топики не назначены.

Проект Scalar: `/lockers/docs`, схема `/lockers/openapi.json` публичного `/api/lockers/v1`; отдельно от существующего `/docs`. Device/service endpoints не публиковать в этой схеме. Маршруты ещё не реализованы.

## Инварианты

- Размещение автономно только по сохранённому разрешению PB на конкретный локер.
- После передачи разрешения отмена может запаздывать; administrative cancellation и device applied — отдельные факты.
- При неопределённом размещении клиент запрещён локально; изъятие по коду разрешено автономно.
- Подтверждение менеджера со слов оператора допустимо; оператор на устройстве только вводит код.
- Повторного открытия нет. Выдача фиксируется по открытию, ячейка свободна после закрытия и без fault.
- Позднее закрытие неопределённого размещения не разрешает клиента.
- Подтверждение пустоты — отдельное действие, обычная отмена не доказывает пустоту.
- Отсутствующая запись/старый снимок не освобождают ячейку; timestamps не определяют победителя гонки.
- Результаты сохраняются до PB ACK актуальной ревизии; это не очередь всех событий.
- Потеря NVS требует recovery, а не автоматического восстановления старых кодов.
- Все допустимые гонки документировать в контексте возникновения с действиями менеджера.

## Состояния

new → authorized → placing → stored → collected/withdrawn. Неопределённость: placement_uncertain; разрешение клиента только после применённого решения. Lifecycle, admin intent, sensor/allocation и delivery status независимы.

## Задел siplite

Локальный checkout `D:/esp32-workplace/sip`: `main/l4_input_processing.c` содержит auth lookup/open_cell/cell_map; `main/leo4_nvs.c` — запись с commit; `main/leo4_nvs_handler.c` — общий gateway. `auth_lockers` в примерах не означает готовый домен. Input/map buffers ограничены 16 байтами; NVS key до 15 ASCII. Полные ID/штрихкоды должны жить в значениях. Ввод и найденные данные нужно исключить из логов локеров.

## Неизвестное и проверки

IoT producer для новых endpoints не проверен; RPC/event registry и межсервисная API-key validation требуют сверки до реализации. Лимиты NVS, тайм-ауты, часы, защита кодов и recovery определяются при реализации. Ручные сценарии тестового запуска перечислены в архитектуре, формальный протокол приёмки отложен пользователем. Doc-only: не запускать backend/frontend/native проверки.
