## Текущий путь

`contact` — один процесс на Python 3.14, только стандартная библиотека,
без БД и отдельного почтового транспорта. Nginx перезаписывает `X-Real-IP`.
Оригинальный IP посетителя передаётся в серверную проверку SmartCaptcha.
Origin проверяется дополнительно; он не заменяет CAPTCHA и ограничение частоты.

Заполните игнорируемый `.env.contact` по `.env.example`:
`SMARTCAPTCHA_SERVER_KEY`, `EMAIL_GATEWAY_URL`, `CONTACT_OWNER_EMAIL`.
На сервере файл имеет mode 600 и исключён из build context.

Виджет использует публичный ключ и адрес скрипта из `yacaptcha.txt`.
Он подгружается при приближении к форме. Токен одноразовый; после неуспеха
виджет сбрасывается. [Документация методов SmartCaptcha](https://yandex.cloud/ru/docs/smartcaptcha/concepts/widget-methods).
Проверка выполняется сервером через `/validate`. Пользователь выбрал
отказ при сбое провайдера вместо разрешающего поведения исходного примера.

Владельцу отправляется сообщение и контакт посетителя. Посетителю отправляется
фиксированное подтверждение с темой и номером обращения. Произвольный текст
посетителя в подтверждение не включается. Вложения не принимаются.

Лимиты: 3 попытки за 10 минут/IP, 3 за сутки/email и 100 за сутки глобально.
Успешные request IDs кешируются на час. Состояние хранится в памяти одного
процесса и сбрасывается при перезапуске; запуск нескольких replicas требует
общего хранилища лимитов и идемпотентности. При неопределённом ответе sender
автоматических повторов нет; фактическая доставка проверяется получателем.

Текущий публичный контакт и получатель обращений — `info@l4desk.ru`.
Локальный `CONTACT_OWNER_EMAIL` обновлён по запросу пользователя.
Compose задаёт `CONTACT_OWNER_EMAIL` с публичным значением по умолчанию
`info@l4desk.ru`; это переопределение имеет приоритет над `.env.contact`.
Для смены ящика используйте окружение Compose или `.env`.
При публикации пересоздайте `contact`;
публичные mailto обновляются вместе со статикой `landing`.
Доставка на новый ящик в этой задаче не проверялась.

## Будущее изменение политики email sender

Пользователь разрешил использовать существующий sender без изменения
облачной политики в этой задаче. Локальная авторизация `yc` истекла;
тест принятия письма не доказывает ограничение источника на стороне шлюза.

1. Восстановить штатную авторизацию Yandex Cloud. Прочитать текущие gateway
   spec и функцию sender, сохранить ревьюируемую версию и rollback.
2. Зафиксировать действующий контракт, маршруты MenuBuilder/терминалов,
   механизм авторизации и реальные исходящие адреса потребителей.
3. Для `l4desk-landing` спроектировать отдельное правило server-to-server:
   проверяемая авторизация и, если поддерживается, allowlist исходящего IP.
   Ограничение Origin/CORS не является авторизацией сервера.
4. Ограничить новый канал нужными получателями/шаблонами и квотой;
   секрет хранить только в окружении relay и sender. Не менять старые
   маршруты и не расширять разрешения существующих потребителей.
5. Проверить отрицательные запросы без ключа/с неверным ключом/с чужого
   источника и произвольным получателем; проверить положительную доставку
   с сервера лендинга и регрессию действующих вызовов MenuBuilder.
6. Выпустить сначала совместимую политику sender, затем конфигурацию relay;
   подтвердить письмо с обоих контуров, удалить временные доступы.

Это отдельное последующее изменение, не выполненное ограничение текущего sender.
